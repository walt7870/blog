# 容器基础导览

容器相关工具经常出现在同一条操作链里，却不能互相替代。理解它们时，可以沿着三个问题追踪：谁接收操作，谁管理实例生命周期，谁最终创建进程。例如输入 `docker run` 后，CLI 把请求交给 Engine；在 Kubernetes 节点上，则通常由 kubelet 通过 CRI 请求运行时创建容器。

![Docker 与 Kubernetes 两条容器创建调用链](/container/runtime-control-paths.svg)

[核心概念](./concepts)先解释镜像、容器、可写层和卷，再说明 namespace 与 cgroup 各自约束什么。[运行时与工具边界](./runtimes)沿实际调用链介绍 Docker、containerd、OCI 运行时和本地虚拟机。[标准与接口边界](./standards)进一步区分镜像分发、进程启动、网络接入和存储挂载的合同。按这个顺序阅读，能把产品名称放回实际职责中。

## 从现象定位边界

| 现象 | 先确认的边界 |
| --- | --- |
| 同一镜像在另一台机器无法启动 | 目标平台、内核、设备与镜像是否匹配 |
| 停止后文件还在，重新创建后消失 | 是否删除了原容器，数据是否只在可写层 |
| 进程正在监听，但宿主机连不上 | 容器内监听地址、端口发布与宿主网络规则 |
| 配了资源限制，任务仍然失败 | CPU 节流、内存上限、进程退出与任务需求 |
| Kubernetes 节点没有 Docker 命令 | 节点实际采用的 CRI 运行时和管理入口 |

例如订单导出进程被内存限制终止后，重新启动能恢复进程，却不保证导出任务自动接着执行。需要结合任务状态、重复执行规则和持久化结果判断恢复是否正确。资源隔离解决运行约束，业务恢复还需要应用协议。

完成基础后，用 [Docker](../docker/)观察单机运行，再用 [Kubernetes](../kubernetes/)理解副本和调度。进程信号、父子关系和资源观察方法见 [Linux 进程](../../linux/process/)，容器并没有消除这些操作系统机制。

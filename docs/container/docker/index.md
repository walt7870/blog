# Docker 导览

订单 API 要在开发电脑和测试服务器上运行，首先需要解决两个问题：交付的程序是否相同，运行所需的配置和数据是否齐备。Docker 提供构建、分发与单机运行的管理入口；镜像固定程序内容，运行参数则描述端口、用户、资源、挂载和外部依赖。

![程序镜像、运行配置与数据保存的交付链路](/container/container-delivery-map.svg)

镜像标签可以移动，不能因为版本名相同就认定内容没变。发布时应记录实际摘要和平台，测试、预发及生产晋级同一份经过验证的制品。环境差异通过受控配置注入，密钥不进入镜像。

## 从订单服务进入各篇

| 当前工作 | 阅读入口 |
| --- | --- |
| 服务退出、访问失败或需要查看运行对象 | [常用命令](./command)：端点、状态、日志、exec 与清理范围 |
| 把源码和依赖变成交付制品 | [镜像构建与供应链](./image-build-supply-chain)：上下文、缓存、构建密钥、摘要与晋级 |
| 保存导出文件、连接数据库、组合服务 | [存储、网络与 Compose](./storage-network-compose)：挂载落点、服务发现、健康条件与重建 |
| 把已有 Java 应用放进运行镜像 | [Java 应用镜像](./java-application)：确定产物、用户权限、JVM 参数与停止行为 |

不清楚镜像、容器或运行时的关系时，先读[容器基础](../basic/)。这里聚焦 Docker 操作，不重复展开 OCI、CRI 与内核隔离机制。

## 完成一次可恢复的部署

先构建镜像并记录身份，再用明确的运行参数创建实例。验收不能停在 `docker ps` 显示运行中：还应验证监听端口、一次真实请求、失败日志、资源消耗和停止行为。订单导出服务还需要验证结果保存的位置，并在删除旧实例、创建新实例后再次读取结果。

如果一进入容器就安装依赖或修改程序，短期可能恢复服务，但重建后变更会丢失。应把长期修复写回源码、Dockerfile 或受控运行配置，再构建新制品。容器内操作用于观察和必要维护，不能替代可重复的交付过程。

## 先确认问题属于哪一层

连接不到 daemon 时先查 CLI context 和服务端；拉取失败查仓库与镜像平台；启动后退出查入口与应用日志；端口不通查监听、网络和发布；文件消失查挂载和生命周期。每次修改后用原失败请求复验，避免只看到一个检查命令成功就结束排查。

Docker Compose 适合本地开发、集成测试与单机组合部署。需要跨节点调度和失败副本补齐时，进入 [Kubernetes](../kubernetes/)，同时重新检查数据库、持久化与应用幂等约束。

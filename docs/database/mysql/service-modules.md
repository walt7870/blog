# MySQL 服务模块

一次订单查询的耗时可能来自连接池排队、SQL 执行、锁等待，也可能只是应用接收结果太慢。把这些阶段统称为“数据库慢”，往往会改错地方。本页以 MySQL 8.4、InnoDB 为基线，沿一条查询和一次库存更新说明模块职责；表结构与本地实例见 [MySQL 总览](./index.md)。

## 一条查询如何进入 InnoDB

例如查询 `SELECT available FROM inventory WHERE sku_id = 101`。应用先从自己的连接池借连接，再把 SQL 发给服务端会话。服务层完成解析、名称解析和权限检查，优化器选择访问路径，执行器通过存储引擎接口读取记录，最终把结果返回客户端。

![SQL 服务层与 InnoDB 读取链路](/database/mysql-query-path.svg)

普通一致性 SELECT 走读取路径，没有“查询成功就写 binlog”的步骤。权限、元数据变化和语句类型会影响实际处理顺序；这张图表达模块职责，不是每条语句都逐函数执行的源码调用栈。

## 连接、会话与线程

连接建立包含协议协商、可选的 TLS 和认证。账号匹配不仅看用户名，还看来源主机；认证通过后，会话保存当前数据库、字符集、事务隔离级别、用户变量和事务状态。相同 SQL 在不同会话上下文下，结果可能不同。

应用连接池复用的是客户端连接。MySQL 的连接数上限控制服务端接入规模，线程缓存复用已退出连接留下的线程资源，它们都不会替应用管理“借出和归还”。标准社区服务端通常按连接分配线程；MySQL Enterprise Thread Pool 是单独的企业功能，不能把线程缓存称为该线程池。

例如接口异常后没有归还连接，下一批请求会卡在应用池等待，MySQL 内部可能几乎没有正在执行的 SQL。反过来，长事务占用锁，即使池里还有空连接，也可能让大量更新排队。归还连接前应提交或回滚事务，并由连接池恢复会话状态，避免把上一个请求的状态带给下一个请求。

```sql
SELECT CONNECTION_ID(), DATABASE(), @@autocommit,
       @@transaction_isolation, @@session.time_zone;
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Threads_running';
SHOW GLOBAL STATUS LIKE 'Threads_created';
```

三个状态值分别帮助观察连接数、非休眠线程数和累计创建线程数。累计值要结合采样间隔计算变化，不能把启动以来的总数当作当前并发。查看其他账号会话及详细监控表还需要相应权限。

## 解析、优化与执行

解析器检查 SQL 结构，名称解析确定 `inventory` 和 `sku_id` 对应的对象。语法正确但列名不存在，会在真正读取记录前失败。服务端预处理语句可以保留语句结构并绑定参数；它不是“任意相同 SQL 都共享一个全局解析缓存”，元数据变化也可能触发重新预处理。

优化器结合统计信息、成本模型和可用索引，估算访问路径及连接顺序。它选择估算较优的候选计划，不保证找到现实运行中绝对最快的方案。数据倾斜、过期统计和参数分布都可能造成估算与实际行数不同。

```sql
EXPLAIN FORMAT=TREE
SELECT available FROM inventory WHERE sku_id = 101;

EXPLAIN ANALYZE
SELECT available FROM inventory WHERE sku_id = 101;
```

主键点查通常直接访问聚簇索引。换成没有合适索引的条件时，可能需要扫描大量记录。执行器按照计划向 InnoDB 请求记录、执行剩余过滤或排序，再按协议发送结果；客户端不及时读取大量结果，也会延长服务端的请求占用时间。具体索引规则见 [索引系统](./index-system.md)，行数误判和 SQL 改写见 [查询优化](./query-optimization.md)。

## Buffer Pool 缓存的是页

InnoDB 将数据页和索引页缓存在 Buffer Pool。命中时可以减少数据文件读取，未命中才需要加载相关页；执行器仍要完成可见性判断、过滤和结果组织。InnoDB 负责这些页的管理，不是文件系统替 MySQL 管理业务缓存。

| 机制 | 保存什么 | 不能推导出的结论 |
| --- | --- | --- |
| InnoDB Buffer Pool | 数据页、索引页等引擎工作数据 | 热页命中不代表返回旧 SQL 结果，也不代表查询无需计算 |
| 服务端预处理语句 | 可复用的语句结构与参数入口 | 不等于保存上次结果或永远复用同一执行计划 |
| 应用 Redis 缓存 | 由应用定义的详情、列表或计算结果 | 不自动与 MySQL 事务一致 |
| 历史 Query Cache | 旧版本按 SQL 缓存结果 | MySQL 8 已移除，8.4 不应再配置 `query_cache_size` |

因此，连续执行同一查询变快，可能是 Buffer Pool、操作系统缓存或其他运行状态变热，不能用这个现象证明 Query Cache 存在。普通 B+ 树索引存放在表空间内；InnoDB 自适应哈希索引是内存优化，8.4 默认关闭，不是一个独立的持久化“哈希索引文件”。

## 更新、提交与后台刷页

执行条件更新时，InnoDB 定位并锁定需要修改的索引记录，检查当前条件，维护 undo 和 redo，并修改 Buffer Pool 中的页。锁范围与访问路径、隔离级别有关，不能简化为“SQL 写一行就只锁一行”。普通快照读、锁定读和更新的可见性及等待行为不同，详见 [事务机制](./transaction-system.md)。

```sql
START TRANSACTION;
UPDATE inventory
SET available = available - 2
WHERE sku_id = 101 AND available >= 2;
SELECT ROW_COUNT() AS affected_rows;
ROLLBACK;
```

示例回滚以保留练习数据。真实事务还要验证数量、检查更新行数，并在订单写入成功后才提交。某条语句报错，不一定代表整个事务都已自动回滚；应用必须按错误类型明确处理事务，尤其不能捕获异常后继续提交剩余操作。

启用 binlog 时，服务层与 InnoDB 通过内部两阶段提交协调事务日志，使崩溃恢复后的引擎状态与 binlog 提交结果相容。组提交可以合并多事务的刷盘工作；并不是每条 UPDATE 都各自独立写一次磁盘。未修改数据的普通 SELECT 不走相同的写事务日志链路。

提交成功也不要求所有被修改的数据页已经写回表空间。redo 的先行日志与崩溃恢复允许数据页稍后刷盘；后台线程还会处理脏页、checkpoint 和历史版本清理。长事务持有旧快照会拖延 purge，空闲会话也可能保留未提交事务和锁。

如果客户端在提交后、收到响应前断网，数据库可能已提交。应用重试前应依据业务幂等键查询结果，不能把“没有收到成功”直接解释成“没有执行”。日志落盘策略和故障恢复见 [备份与恢复](./backup-recovery.md)。

## 按阶段定位问题

| 证据 | 更可能涉及的阶段 | 验证办法 |
| --- | --- | --- |
| 应用池等待增长，服务端负载不高 | 客户端连接使用 | 核对借还连接、异常分支和池内超时 |
| 连接直接失败 | 网络、TLS、认证、连接限制 | 保存客户端错误码，核对账号来源与服务端日志 |
| SQL 立即报语法或未知列 | 解析、名称解析 | 在相同版本、数据库和会话上下文复现 |
| 扫描行数远大于返回行数 | 访问路径与执行 | 对比 EXPLAIN 估算和实际执行，检查过滤与排序 |
| 更新等待，普通查询仍可返回 | 锁、事务或元数据锁 | 关联等待者和阻塞者，检查未提交事务，不能直接批量杀会话 |
| 提交延迟随存储延迟增长 | redo/binlog 刷盘、组提交 | 联合观察提交延迟、I/O、日志等待和并发 |

可从 `performance_schema.data_lock_waits`、`metadata_locks` 及 `sys` 视图继续关联会话与锁。Performance Schema 时间列统一按皮秒呈现，换成秒要除以 `1e12`；这不表示计时真的具有皮秒精度。监控开关、权限和采样窗口会影响可见数据，入口见 [监控与运维](./monitoring-operations.md)。

验证模块理解时，可以对照两种请求：主键 SELECT 解释计划、页读取和结果传输；库存 UPDATE 解释锁、条件检查、行数、提交与响应丢失。能把一个慢请求定位到具体阶段，再在修改后复测相同负载，才形成可用的排查闭环。

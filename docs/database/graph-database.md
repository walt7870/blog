# 图数据库

图数据库以节点和关系作为核心数据模型，适合处理实体之间的连接、路径和网络结构。关系型数据库可以通过关系表、`JOIN` 或递归查询表达网络；属性图数据库则直接提供节点、带方向的关系及路径匹配语法。优势是否成立，要看查询形状、索引、节点度数、数据规模和实现，不能只用“关系多”判断选型。

## 概念边界

图由节点、边和属性组成。节点表示实体，例如用户、账户、设备、订单、商品、知识条目；边表示实体之间的关系，例如购买、关注、转账、登录、归属、依赖；属性保存节点或边上的业务字段，例如时间、金额、权重、来源、状态。

图数据库适合回答“谁和谁有关”“通过哪些路径相关”“某个节点影响了哪些对象”“关系网络中是否存在异常模式”这类问题。部分产品支持 ACID 事务，也可以保存权威图事实；不能把图数据库一律视为缓存。如果查询主要是按主键读取、普通分页和报表聚合，且没有可变路径需求，关系型数据库或分析型数据库通常更容易落地。

## 适用场景

### 风控关系网络

金融、支付和电商风控经常需要识别设备、账号、手机号、银行卡、地址、IP 之间的复用关系。单次查询可能需要从一个用户出发，沿设备、支付工具、收货地址做多跳扩散，并计算关联节点的风险分。图数据库能直接表达这类关系链路。

![多个账号共用设备形成可解释的风险线索](/database/graph-shared-device.svg)

例如 U1001、U1002、U1003 在同一小时用过 D9001，查询可从账号沿登录关系走到设备，再反向找到其他账号。共用设备只是待核实的线索：门店共用终端、家庭设备或设备标识碰撞都可能产生正常关联。边上保留来源与时间，才能解释为什么被关联；不能把两跳连通直接判成欺诈。

### 权限与组织层级

组织、角色、资源、策略之间经常存在继承和覆盖关系。图模型可以把用户、部门、角色、菜单、接口、数据范围建成节点，把拥有、继承、授权、禁止建成关系，用路径查询解释某个权限来自哪里。是否授权还要执行拒绝优先级、租户边界和有效期规则，存在一条可达路径不等于拥有权限。

### 知识图谱

知识图谱关注实体、概念和语义关系，常用于搜索增强、问答、推荐和数据治理。例如“组件属于哪个系统”“指标由哪些字段计算”“报表依赖哪些数据表”等血缘问题，都适合用图结构表达。

### 推荐与相似关系

用户、商品、标签、行为之间天然形成网络。图数据库可以通过共同邻居、路径权重、PageRank、社区发现等算法辅助召回和解释推荐结果。对于大规模在线推荐，图数据库常作为关系探索或离线特征来源，而不是完整替代推荐引擎。

## 不适用场景

- 普通订单与账务系统已有成熟的关系模型和约束时，不应仅因存在用户关系就迁移主库；评估事务范围、约束和恢复能力后再决定事实的归属。
- 以大批量扫描、复杂聚合、宽表报表为核心的分析任务，应优先使用列式数据库、数据仓库或湖仓体系。
- 关系层数固定且数据量较小的普通后台查询，没有必要为了两三张表的关联引入图数据库。
- 对团队运维能力要求较高的场景，需要先评估备份恢复、监控告警、查询限流、数据导入和权限隔离能力。

## 数据建模

图建模应从查询问题反推，而不是把所有表机械转换成节点。节点和边的粒度会直接影响查询复杂度和写入成本。

| 建模问题 | 判断方式 |
| --- | --- |
| 什么建成节点 | 需要被独立查询、聚合、扩散或复用的对象 |
| 什么建成边 | 需要表达方向、权重、时间、来源或路径的关系 |
| 属性放节点还是边 | 描述实体本身放节点，描述一次关系事实放边 |
| 是否保留关系型主键 | 保留，用于和业务主库、日志、搜索索引对齐 |
| 是否冗余属性 | 高频过滤字段可以冗余，但要有同步和校验策略 |

例如风控场景中，用户、设备、手机号、银行卡适合作为节点；登录、绑定、支付、收货适合作为边；登录时间、支付金额、绑定来源适合作为边属性。一条边表示“最近登录”还是“一次登录事件”必须先定清：前者更新同一关系，后者每次事件都要有稳定编号。多方参与、需要独立生命周期的支付交易，也可以建成交易节点，而不是勉强塞进一条二元关系。

## 查询示例

不同图数据库的查询语言不完全相同。Neo4j 常用 Cypher，Apache TinkerPop 生态常用 Gremlin。下面使用 Neo4j 5.26 的 Cypher，在空的本地测试库中顺序执行。节点编号为虚构业务键；约束既支持按键查找，也防止并发导入创建同号节点。

```cypher
CREATE CONSTRAINT user_id IF NOT EXISTS FOR (u:User) REQUIRE u.id IS UNIQUE;
CREATE CONSTRAINT device_id IF NOT EXISTS FOR (d:Device) REQUIRE d.id IS UNIQUE;

MERGE (d:Device {id: 'D9001'})
WITH d
UNWIND ['U1001', 'U1002', 'U1003'] AS userId
MERGE (u:User {id: userId})
MERGE (u)-[r:LOGIN {event_id: 'E-' + userId}]->(d)
ON CREATE SET r.time = datetime('2026-10-01T10:00:00Z'), r.source = 'login-events';
```

查询十月一日内与 U1001 共用设备的其他账号，并返回可解释的中间设备：

```cypher
MATCH (u:User {id: 'U1001'})-[a:LOGIN]->(d:Device)<-[b:LOGIN]-(other:User)
WHERE other <> u
  AND a.time >= datetime('2026-10-01T00:00:00Z')
  AND a.time < datetime('2026-10-02T00:00:00Z')
  AND b.time >= datetime('2026-10-01T00:00:00Z')
  AND b.time < datetime('2026-10-02T00:00:00Z')
RETURN DISTINCT other.id AS userId, d.id AS deviceId
ORDER BY userId, deviceId;
```

结果为 `U1002、D9001` 和 `U1003、D9001`。方向与类型限定了关系含义，避免把关注、绑定等无关关系一起扩散。查询同一窗口内至少三个账号共用的设备：

```cypher
MATCH (d:Device)<-[r:LOGIN]-(u:User)
WHERE r.time >= datetime('2026-10-01T00:00:00Z')
  AND r.time < datetime('2026-10-02T00:00:00Z')
WITH d, count(DISTINCT u) AS userCount
WHERE userCount >= 3
RETURN d.id AS deviceId, userCount
ORDER BY userCount DESC, deviceId;
```

结果为 `D9001、3`。生产查询应先限定有索引的起点、关系类型、方向、跳数和时间窗口；公共设备等超级节点要单独治理。末尾 `LIMIT` 限制返回结果，并不保证上游扩散和聚合已经受限。用 `EXPLAIN` 看计划，用 `PROFILE` 执行并测量；不要对写入语句盲目 PROFILE，因为它会实际写入。

## 工程落地

在已有订单主库的系统中，可以通过 CDC、消息队列或离线任务生成供分析使用的关系图。这里图是派生视图，业务主库仍负责相应权威事实；若业务本身由图数据库维护事实，就按该产品的事务与恢复合同设计，不能套用同一种同步方案。

订单派生视图的同步关系见[数据库总览](./index.md)中的数据流图。CDC 负责捕获变化，Kafka 负责传输与保留事件，图构建器负责业务键映射和图写入，三者职责不同。

同步链路要处理幂等、乱序、删除、重复消息和补数。节点主键要稳定，事件边要有业务唯一编号，否则重复边会污染路径查询和关系计数。上面 MERGE 在顺序重放时复用同一关系，但不自动证明任意并发导入都能保持边的全局唯一性；生产可按产品能力施加关系唯一约束，或以唯一事件节点建模，并配合源端键和事务处理。

更新型关系还要用版本防止旧消息覆盖新状态，删除需要传播 tombstone 或等效状态。先成功提交图写入再确认消息位点，崩溃后的重复投递按幂等键消化；快照回填与增量衔接必须有位点或水位。验收比较限定窗口中的节点数、业务边数、删除记录和抽出的具体路径，不能只看消费端没有报错。

## 排查入口

| 现象 | 检查点 |
| --- | --- |
| 多跳查询变慢 | 起点是否命中索引、扩散层数是否过大、是否缺少关系方向过滤 |
| 查询结果爆炸 | 是否限制路径长度、关系类型、时间窗口和返回数量 |
| 关系缺失 | 同步任务是否失败、消息位点是否滞后、删除和更新是否被正确处理 |
| 关系重复 | 边唯一键是否稳定，导入任务是否幂等 |
| 结果解释困难 | 边上是否保留来源、时间、业务单号和置信度 |

## 选型

Neo4j 提供属性图、Cypher 与相关生态；部署能力、扩展方式和许可要按具体版本核对，不能简单用“只适合中小规模”定论。JanusGraph 通常与 Cassandra、HBase 等存储及搜索索引后端组合，必须一起评估事务、一致性与维护成本。ArangoDB 等多模型产品同时提供文档和图能力，也要验证深度路径查询、分布式事务范围和恢复工具是否符合业务。

选型时不要只比较查询语言和产品功能，还要验证导入速度、索引能力、备份恢复、权限模型、监控指标、查询超时控制和数据一致性策略。

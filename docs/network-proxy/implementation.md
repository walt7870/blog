# 网络代理实施总览

本专题的基础部署主线是 `sing-box + Trojan over TLS + Clash Verge / Mihomo`：远端 sing-box 直接终止 TLS 并校验代理账号，本机内核按规则连接远端，再由远端访问目标。systemd 与 Docker 是两种进程托管方式，选择其中一条完成；Nginx、WebSocket 和多节点并非这条主线的前置条件。

## 实施与停止条件

![代理从配置准备到业务验收的实施流程](/network-proxy/implementation-gates.svg)

例如让开发机访问外部下载 API，同时保留内部制品库直连：先写清两个域名的 DNS、出口与预期响应，再准备远端域名和证书。这样验证的目标是“两类请求各走预定路径”，而不是只看节点变绿。

| 阶段 | 操作入口 | 进入下一步的条件 |
| --- | --- | --- |
| 明确范围 | [基础原理](./fundamentals.md)、[组件链路](./components.md) | 明确谁使用、哪些流量进入代理、内网与DNS如何保留 |
| 准备身份 | [证书申请与续期](./certificate.md) | 域名指向正确，证书名称匹配，服务进程能读取证书且续期后有加载方式 |
| 部署远端 | [systemd](./server-systemd.md) 或 [Docker](./server-docker.md) | 配置检查通过、监听正确、认证日志正常，远端能访问代表性目标 |
| 应用客户端配置 | [用户管理](./user-management.md)、[Clash Verge](./clash-verge.md) | 节点凭据、TLS名称和端口一致；规则与代理组引用有效 |
| 验收与变更 | [运维与排查](./operations.md) | 显式代理、实际应用、内网绕过、错误凭据和服务重启均按预期运行 |

证书安装与续期属于控制配置，不能画成流量经过的第一跳。数据访问方向始终是“应用 → 本机内核 → 远端服务 → 目标”，客户端读取的是证书信任与服务器名称配置，不是远端私钥。

## 选择部署方式

已有 Linux 服务管理和 journal 运维习惯时，沿 systemd 方案阅读；已经用 Compose 维护服务目录、网络与挂载时，沿 Docker 方案阅读。两种方案都必须明确配置文件位置、证书读取权限、监听地址、日志上限和重启恢复方式。容器不会替代证书续期或端口放行，systemd 自启动也不等于业务可用。

不要在同一主机上让两套示例争用同一个监听端口。迁移时先在独立端口验证新服务，再切换客户端或入口，保留旧配置和服务版本用于恢复。账号新增、密码轮换和停用的具体命令由用户管理页承接，避免部署文档各自维护一套互相冲突的流程。

## 验收请求与失败证据

客户端已配置本机 HTTP 代理 `127.0.0.1:7890` 后，可从显式代理开始，替换成自己的可控目标：

```bash
curl --proxy http://127.0.0.1:7890 --noproxy '' \
  --connect-timeout 5 --max-time 20 -I https://example.com/
```

这只能验证当前请求。随后用实际浏览器或开发工具访问外部 API，检查连接记录中的规则和出站；再访问内部制品库，确认仍使用企业 DNS 与内网出口。若请求没有出现在内核中，先检查应用代理设置和 `NO_PROXY`；若远端认证失败，核对账号；若已到达目标但返回 401/403，再检查业务权限。

还要用错误凭据验证拒绝访问，并重启服务检查配置、证书挂载和监听能否恢复。把测试目标、时间、配置版本、命中规则和响应结果一起记录。切换后出现失败时先恢复上一版配置，再根据分层证据修复，不能靠连续重启掩盖原因。

## 扩展路线

主线通过后，再按具体问题扩展：HTTP 网关共用入口前先读[协议、插件与传输](./protocol-stack.md)确认兼容；高延迟或丢包问题先做[跨境链路诊断](./cross-border-diagnosis.md)，再考虑[Hysteria2 与 TCP 兜底](./hysteria2-practice.md)。新增一层组件，就增加对应的配置、监控与恢复责任；没有测量结果时不预设它会更快。

# 嵌入式与工业通信协议

一台温控设备可能在板内用 I²C 读温度，经 RS-485 把寄存器值送到网关，再由网关用 MQTT 上传。三段协议分别解决芯片接线、现场传输和远程消息交付，彼此不能替换。资源受限设备还要同时考虑 RAM、电池、线缆距离、干扰、实时性与失效恢复。

本文按"距离"和"用途"分类介绍：板内总线 → 现场总线 → 工业以太网 → 无线 IoT。

## 一、UART 与串口

UART（Universal Asynchronous Receiver/Transmitter）是收发异步串行数据的硬件单元。日常所说的串口可能指 UART 接口，也可能指加了 RS-232/RS-485 收发器的完整端口，接线前必须确认电气标准。

### 物理与电平

UART 本身是协议，不规定电平。常见的物理层标准：

| 标准         | 电平                | 距离      | 用途                     |
| ---------- | ----------------- | ------- | ---------------------- |
| CMOS/TTL 串口 | 常见 3.3V、5V，也有 1.8V | 板内短走线 | MCU、调试口，确认输入耐压 |
| RS-232 | 单端正负电压、逻辑与 TTL 不同 | 随速率和线缆变化 | 点对点仪表、传统 PC 串口 |
| RS-422 | 差分，单驱动器、多接收器 | 距离与速率互相制约 | 长线点对多点，双向需两对线 |
| RS-485 | 差分，可有多个驱动器 | 距离与速率互相制约 | 常用两线半双工现场总线 |
| USB-Serial | USB 转 TTL（CH340 等） | USB 距离  | 现代电脑没有 RS-232，用转换芯片调试 |

### 协议帧格式

```
 起始位  数据位（5~9）  校验位（可选）  停止位（1/1.5/2）
   0      D0...Dn         P              1
```

最常见的配置叫 `8N1`：8 数据位、无校验、1 停止位。

### 关键参数

- **波特率**：每秒符号数。常用 9600、115200、921600。两端必须一致
- **错误检测**：奇偶校验非常弱，工程上一般在应用层加 CRC
- **流控**：硬件流控用 RTS/CTS 两根线，软件流控用 XON/XOFF 字符

### 代码示例（Linux）

以下是配置片段，调用前检查 `open` 和 `tcgetattr` 返回值；调用后检查 `tcsetattr`、`write` 和 `read`。`cfmakeraw` 清除继承的输入转换和软件流控，不能只改 `c_lflag` 就认为已经完整进入原始模式。

```c
#include <termios.h>
#include <fcntl.h>
#include <unistd.h>

int fd = open("/dev/ttyUSB0", O_RDWR | O_NOCTTY);
struct termios tty;
tcgetattr(fd, &tty);
cfmakeraw(&tty);
cfsetispeed(&tty, B115200);
cfsetospeed(&tty, B115200);
tty.c_cflag = (tty.c_cflag & ~CSIZE) | CS8;  // 8 数据位
tty.c_cflag &= ~PARENB;                       // 无校验
tty.c_cflag &= ~CSTOPB;                       // 1 停止位
tty.c_cflag &= ~CRTSCTS;                      // 不使用硬件流控
tty.c_cflag |= CLOCAL | CREAD;
tty.c_cc[VMIN] = 0;
tty.c_cc[VTIME] = 10;                        // 最长等 1 秒，超时可返回 0
tcsetattr(fd, TCSANOW, &tty);

write(fd, "AT\r\n", 4);
char buf[64];
ssize_t n = read(fd, buf, sizeof(buf));
// n > 0 时只处理这 n 个字节，不把 buf 当作已补零的字符串
close(fd);
```

一次读取不保证收到完整的 AT 响应，生产程序要按结束标记或长度累积报文，并处理短写与信号中断。调试时先短接兼容电平的 TX/RX 做本机回环，再接设备，区分驱动、接线与应用协议问题。

调试工具：`screen /dev/ttyUSB0 115200`、`minicom`、`picocom`、Windows 上的 SSCOM、SecureCRT。

### 典型应用

- MCU 调试日志（`printf` 重定向到串口）
- AT 指令控制模块（GSM、Wi-Fi、蓝牙模块）
- GPS NMEA 协议
- 工业仪表（套 RS-485）
- 老 PC 与单片机通信

## 二、RS-485

RS-485 定义差分电气接口，不规定 UART 帧、站号或主从调度。它常用来承载 UART 字节流和 Modbus RTU，也能承载其他协议；仅接上 A/B 线并不能让多个节点协调发送。

### 关键特性

- **差分传输**：接收器判断 A/B 电压差，但共模电压仍须在收发器允许范围内，必要时使用参考地或隔离。
- **方向控制**：常见两线半双工一次只能一个驱动器发送；四线连接可以实现全双工。
- **节点负载**：传统指标是 32 单位负载，低单位负载收发器可增加节点数，实际还受偏置、线长和速率限制。
- **拓扑与端接**：主干两端按线缆特性阻抗端接，常见 120Ω；避免长支线、星形连接和每个节点都加端接。

### 软件视角

操作系统通常仍暴露串口，但方向切换需要驱动或硬件支持。手动控制 DE 时，要等最后一个停止位真正发送完成再切回接收，不能仅凭 `write()` 返回就撤掉驱动；Linux 驱动支持时可使用 RS-485 ioctl，自动方向模块则由硬件处理。A/B 命名在产品间可能不同，应按设备说明核对极性。

### 典型应用

- Modbus RTU（工业现场最广泛的协议）
- BACnet MS/TP（楼宇自控）
- DMX512（舞台灯光）
- 电表抄表、传感器组网

## 三、I²C

I²C（Inter-Integrated Circuit，发音"I-squared-C"）由飞利浦发明，专为板内芯片间低速通信设计。

### 物理层

只用两根线：

- **SDA**（数据线）
- **SCL**（时钟线）

常用的 Standard/Fast 等双向模式使用开漏与上拉，电阻值要结合电源、电容、上升时间和器件灌电流计算，不能统一指定 4.7kΩ。开漏允许共享线路，但多控制器同时发起时仍需要仲裁；超高速单向 UFm 使用不同的推挽规则。

### 协议要点

- **主从模型**：主机生成时钟，从机被寻址才说话
- **地址寻址**：每个从机有 7 位（或 10 位）地址
- **起始/停止条件**：SCL 高时 SDA 下降沿表示开始，SCL 高时 SDA 上升沿表示停止
- **应答（ACK）**：每发完一字节，接收方拉低 SDA 一个时钟表示已收到

### 速率

| 模式               | 速率        |
| ---------------- | --------- |
| Standard         | 100 kbps  |
| Fast             | 400 kbps  |
| Fast Plus        | 1 Mbps    |
| High Speed       | 3.4 Mbps  |
| Ultra Fast (单向)  | 5 Mbps    |

### 代码示例（Arduino）

```cpp
#include <Wire.h>

void setup() {
  Wire.begin();              // 主机模式
  Serial.begin(115200);
}

void loop() {
  Wire.beginTransmission(0x68);   // DS3231 RTC 地址
  Wire.write(0x00);                // 寄存器地址
  Wire.endTransmission(false);     // 重启动条件，不释放总线
  Wire.requestFrom(0x68, 7);       // 读 7 字节
  while (Wire.available()) {
    Serial.print(Wire.read(), HEX);
  }
  delay(1000);
}
```

### 典型应用

- 板内传感器（BME280 温湿度、MPU6050 陀螺仪、各种 ADC/DAC）
- 实时时钟（DS3231、PCF8563）
- EEPROM（24Cxx 系列）
- HDMI EDID（显示器告诉电脑自己的分辨率）

### 工程注意

- **地址冲突**：固定地址相同的设备需要地址引脚、可编程地址、复用器或独立总线；同型号不必然只能挂一个。
- **总线挂死**：SDA 持续低时可按器件规范尝试最多 9 个恢复时钟并发 STOP；SCL 被持续拉低时，软件时钟恢复可能无效，需要复位或受控断电。
- **上拉电阻**：线长增加可能需要更强上拉，但不能低于器件灌电流允许的阻值；电容过大时应缩短走线、降速或使用专用扩展器。

## 四、SPI

SPI（Serial Peripheral Interface）由摩托罗拉发明，速度比 I²C 快得多，没有寻址，每个从机独立片选。

### 物理层

四根线：

- **SCLK**：时钟（主机发出）
- **MOSI**：Master Out Slave In，主到从
- **MISO**：Master In Slave Out，从到主
- **CS / SS**：片选（每个从机一根，主机拉低选中）

### 协议要点

- **全双工**：MOSI 和 MISO 同时工作，主机发一个字节的同时就收一个字节
- **无寻址、无 ACK**：主机直接拉低 CS 开始通信，时钟一来就移位
- **四种模式**：CPOL（时钟极性）和 CPHA（时钟相位）的 4 种组合，主从必须匹配

### 速度

工程上常见 1~50 MHz，可以跑到上百 MHz。比 I²C 快 1~2 个数量级。

### 代码示例（STM32 HAL）

```c
// hspi1 已由板级代码初始化；这里只展示一次片选事务
uint8_t tx[] = {0x9F};   // Read JEDEC ID
uint8_t rx[3] = {0};

HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_RESET);
HAL_StatusTypeDef result = HAL_SPI_Transmit(&hspi1, tx, 1, 100);
if (result == HAL_OK) {
    result = HAL_SPI_Receive(&hspi1, rx, 3, 100);
}
HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_SET);
// 检查 result；无论成功失败都先释放片选，再决定重试
```

### 典型应用

- SPI Flash（W25Q 系列）
- SD 卡（SPI 模式）
- 高速 ADC/DAC
- TFT 显示屏（ST7789、ILI9341）
- 以太网芯片（W5500）、CAN 控制器（MCP2515）

### I²C vs SPI

| 维度       | I²C            | SPI         |
| -------- | -------------- | ----------- |
| 信号线数（不含地/电源） | 2 | 3 + N 根片选 |
| 速度       | 100k~3.4M      | 数十 Mbps     |
| 双工       | 半双工            | 全双工         |
| 寻址       | 总线地址           | 片选          |
| 多从机扩展 | 需地址不冲突并满足电容限制 | 常见共享三线、独立片选，未选设备需释放 MISO |
| 板上走线     | 简单             | 多           |

简单来说：低速、多从机、想省线选 I²C；高速、点对点选 SPI。

## 五、1-Wire

只用一根线（加一根地线，外加可选的电源线，或直接寄生供电），由 Dallas / Maxim 推出。

### 关键特性

- 一根数据线既供电又传输（寄生供电模式）
- 每个 1-Wire 器件出厂烧录唯一 64 位 ROM ID
- 节点数与线长、拓扑、电容和供电方式有关，需验证最远节点波形与转换时供电

### 经典器件

- **DS18B20**：数字温度传感器，业余电子爱好者的最爱
- **DS2401**：电子序列号（标识不等于防克隆认证）
- **iButton**：早年门禁、考勤的"钥匙扣"

实测代码用 OneWire 库（Arduino 生态）几行就能读温度，工程上一般作为温度传感方案的备选项。

## 六、CAN 总线

CAN（Controller Area Network）是 Bosch 为汽车设计的总线协议，已经是汽车电子的事实标准。

### 物理层

常见高速 CAN 使用 CAN_H 和 CAN_L 差分线，主干两端 120Ω 端接。经典 CAN 常用最高 1 Mbit/s；CAN FD 可在数据阶段切换更高速率，但仲裁阶段仍使用约定的标称速率。可用速度受收发器、线长、支线和采样点约束，不能把数据阶段速率套给整帧。

### 协议特点

- **多主**：任何节点都可以主动发送，不需要主机
- **基于消息**：每个报文有 11 位（标准帧）或 29 位（扩展帧）ID，没有"目的地址"概念，谁感兴趣谁过滤
- **位仲裁**：多节点同时发，ID 越小（0 越多）优先级越高，靠"显性 0 覆盖隐性 1"在物理层完成无损仲裁
- **强 CRC + 自动重传**：硬件级错误检测和恢复
- **错误界定**：节点频繁出错会被自动隔离

### 报文结构（标准帧）

```
SOF | ID(11) | RTR | IDE | r0 | DLC(4) | DATA(0~8B) | CRC | ACK | EOF
```

数据载荷只有 8 字节（CAN-FD 扩展到 64 字节）。听上去很少，但车载场景里"发动机转速"、"车速"这种信号几个字节足够。

### 上层协议

CAN 物理层之上还有应用层协议栈：

- **OBD-II / UDS**：汽车诊断（连 ELM327 那个就是它）
- **J1939**：商用车（卡车、客车、工程车辆）
- **CANopen**：工业自动化、机器人
- **DeviceNet**：工业 I/O

### 代码示例（SocketCAN，Linux）

```bash
# 启动 CAN 接口
sudo ip link set can0 type can bitrate 500000
sudo ip link set up can0

# 发送
cansend can0 123#DEADBEEF

# 监听
candump can0
```

```c
#include <linux/can.h>
struct can_frame f = {.can_id = 0x123, .can_dlc = 4,
                      .data = {0xDE,0xAD,0xBE,0xEF}};
write(sock, &f, sizeof(f));
```

### 典型应用

- 汽车 ECU（发动机、变速箱、ABS、车身控制）
- 工业机器人
- 楼宇电梯
- 农业、工程机械

## 七、Modbus

Modbus 使用紧凑的数据模型读取线圈和寄存器。实现难点常在帧边界、串口方向、超时、异常响应和厂商寄存器映射，不能只完成一次读寄存器就认为具备稳定的现场通信能力。

### 三种变体

| 变体        | 物理层    | 编码      | 用途              |
| --------- | ------ | ------- | --------------- |
| Modbus RTU | RS-485 | 二进制     | 现场总线，最常见         |
| Modbus ASCII | RS-485 | ASCII   | 老设备             |
| Modbus TCP | TCP/IP  | 二进制 + MBAP 头 | 工厂上位机、SCADA      |

### 协议模型

主从、请求-响应。主机发请求，从机回响应。基本数据模型只有四种：

| 区  | 名称              | 操作             |
| -- | --------------- | -------------- |
| 0X | Coils           | 读/写离散量（线圈）     |
| 1X | Discrete Inputs | 只读离散量          |
| 3X | Input Registers | 只读寄存器          |
| 4X | Holding Registers | 读/写寄存器        |

### 报文示例（功能码 03，读保持寄存器）

请求：

```
01 03 00 00 00 02 C4 0B
└┘ └┘ └─┬─┘ └─┬─┘ └─┬─┘
站号 功能 起始地址 数量  CRC
```

响应：

```
01 03 04 00 0A 00 14 DA 3E
└┘ └┘ └┘ └─┬─┘ └─┬─┘ └─┬─┘
站号 功能 字节数 寄存器1 寄存器2 CRC
```

### 工程要点

- **串口合同**：按设备说明统一站号、波特率、数据位、校验和停止位；规范的 RTU 字符为 11 位，常见 `8E1`，无校验时使用 `8N2`，不要直接沿用上面的通用 `8N1` 调试片段。
- **帧间隔**：RTU 帧之间至少静默 3.5 个字符时间；帧内间隔超过 1.5 个字符时间应判为不完整帧。高于 19200 bit/s 时，规范建议分别使用固定 1.75 ms 与 750 µs，另设整次响应超时。
- **CRC**：必须算对，错一位整帧丢
- **大端字节序**：寄存器内 16 位是大端，但跨寄存器的 32 位浮点数厂家各不相同，要测
- **从站超时丢线**：现场最常见故障是线接触不良，软件要能容忍

示例请求从 PDU 地址 `0` 读取两个保持寄存器，文档标号可能写作 `40001`，不能直接把 `40001` 填进线上起始地址。CRC 字节低位在前，响应值为十进制 10 和 20。Modbus TCP 用 MBAP 长度和事务号组织报文，不携带 RTU CRC；TCP 提供流传输，但不会确认寄存器写入已经产生业务效果。RTU 与 TCP 的重复写入都要结合设备语义处理。

## 八、Profibus / Profinet

西门子家族。

- **Profibus DP**：基于 RS-485 的现场总线，PLC 与 IO 模块通信。是 1990 年代的主力，正在被 Profinet 替代
- **Profinet**：基于工业以太网，支持实时（RT）和等时实时（IRT）。带 PROFIsafe 可做安全控制
- **设备能力**：RT 与 IRT 的要求不同；只有需要 IRT 调度与同步的链路才要求对应设备能力，普通以太网可达不代表满足实时指标。

PLC 工程师的世界，软件层一般用 TIA Portal 配置，开发者一般不直接处理报文。

## 九、EtherCAT

由倍福（Beckhoff）发起的工业以太网协议，目标是"以太网的连接 + 现场总线的实时性"。

### 工作原理

主站发送包含过程数据的帧，从站控制器在帧经过时读取或写入自己的数据，不必每个节点都完整缓存再转发。一个周期可以包含多帧；实际周期和同步精度取决于节点数量、载荷、拓扑、主站调度和 Distributed Clocks 配置，不能固定承诺 100µs。

### 适用场景

- 运动控制（多轴伺服同步）
- 高速数据采集
- 半导体设备

### 工程现状

EtherCAT 主站开源选项：SOEM、IgH EtherCAT Master。从站需要专用 ASIC（ET1100、ET1200）或集成了 ESC 的 SoC。

## 十、OPC UA

OPC Unified Architecture，工业 4.0 / 工业互联网时代的"语义通信"层。

### 它解决什么

PLC 之间的协议（Profinet、EtherCAT）解决的是"实时控制"，而 MES、ERP、云平台需要的是"语义化的数据"。OPC UA 提供：

- **统一信息模型**：电机不只是几个寄存器，而是有"转速属性、温度属性、报警事件、控制方法"的对象
- **跨平台**：基于 TCP/IP 或 HTTPS，Windows / Linux / 嵌入式都能跑
- **安全**：内置 X.509 证书、签名、加密
- **发现机制**：客户端可以遍历服务器的对象树

### 部署形态

- **Client/Server**：传统模型，类似 OPC Classic
- **Pub/Sub**：可采用 UDP、MQTT 等映射，选型时核对编码、传输配置与实现支持，不把能连 Broker 等同于信息模型和安全配置已互通。

实现：开源有 open62541（C/C++）、Eclipse Milo（Java）、node-opcua、asyncua（Python）。

## 十一、车载补充：LIN / FlexRay / 车载以太网

- **LIN**：单线、低速（最高 20 kbps）、低成本，挂在 CAN 主干下做"末梢"。比如车窗、座椅这种对实时性要求不高的子系统
- **FlexRay**：早期高安全性总线（10 Mbps、双通道、时间触发），用于线控转向/制动等 X-by-Wire 系统
- **车载以太网（100BASE-T1 / 1000BASE-T1）**：单对双绞线的以太网，正在取代部分高带宽场景。智能驾驶域控制器、摄像头数据传输都在用
- **SOME/IP**：基于 IP 的车载服务发现与 RPC 协议，AUTOSAR 生态的"中间件"

## 十二、无线 IoT 协议

### BLE（蓝牙低功耗）

- 短距离（10~100m）、低功耗（纽扣电池能撑数月）
- 协议栈复杂，但 GATT 模型很统一
- 常见用法：手机 App ↔ 智能硬件、可穿戴设备
- BLE Mesh 让多个 BLE 设备组成网状网

### Zigbee

- 基于 IEEE 802.15.4
- 支持 Mesh，路由器节点转发数据，休眠终端通常不承担转发
- 智能家居（米家、Aqara、Hue）的主流协议

### LoRa / LoRaWAN

- LPWAN（低功耗广域网）代表，距离数公里至十几公里
- 速率、覆盖取决于区域参数、带宽、扩频因子和现场链路预算，地下与金属遮挡环境必须实测
- 网关汇聚到 LoRaWAN 服务器，再到云
- 农业传感器、智慧路灯、远程抄表

### NB-IoT / Cat-M1

- 蜂窝制式，运营商网络覆盖
- 模组直接和 4G/5G 基站通信，不用自建网关
- 共享单车、定位手表、烟感

### Thread / Matter

- Thread：低功耗 IPv6 Mesh，基于 802.15.4，Apple HomeKit、Google Home 都在推
- Matter（原 CHIP）：跨厂商应用层标准，可经 Wi-Fi、Thread、Ethernet 的 IP 网络运行；BLE 常用于配网，不是常规业务承载路径
- 设备互通仍受 Matter 版本、设备类型、控制器功能和认证范围影响；Thread 设备接入家庭 IP 网络还需要边界路由器

### MQTT

虽然定义在应用层，但在 IoT 场景里和上面这些无线协议天然搭配：

- 发布/订阅模型，topic 树形结构
- QoS 三档（0/1/2）
- 适合长连接、低带宽、不稳定网络
- 物联网平台（AWS IoT、阿里云 IoT、HiveMQ）几乎都用 MQTT 做接入

## 十三、选型建议

| 场景需求                    | 推荐协议                              |
| ----------------------- | --------------------------------- |
| 板内 MCU 调试日志              | UART (TTL)                        |
| 板内传感器（少量、低速）            | I²C                               |
| 板内 SD 卡 / Flash / 显示屏   | SPI                               |
| 一根线挂温度传感器               | 1-Wire                            |
| 工厂车间多机长距离通信             | RS-485 + Modbus RTU              |
| 工厂上位机 ↔ PLC             | Modbus TCP / OPC UA               |
| 汽车电子                    | CAN / CAN-FD / 车载以太网              |
| 汽车末梢传感器                 | LIN                               |
| 高速运动控制                  | EtherCAT                          |
| 工业 4.0、设备数据上云           | OPC UA                            |
| 智能家居（手机/网关→设备）          | BLE / Zigbee / Thread / Matter    |
| 远距离低速传感（农业、抄表）          | LoRaWAN / NB-IoT                  |
| 设备数据接入云端 IoT 平台         | MQTT                              |

## 十四、和互联网协议的关系

嵌入式协议和互联网协议越来越融合：

- **网关化**：Modbus RTU 设备 → 网关 → MQTT → 云
- **协议转换**：Profinet ↔ OPC UA ↔ Kafka
- **TSN（时间敏感网络）**：通过时间同步、调度和流量整形等机制控制延迟；需要端点、交换机和全路径配置配合，不是打开单个开关就保证硬实时。

![温度采集从现场总线到云端的合同边界](/protocol/industrial-gateway-flow.svg)

例如温度寄存器读取为 `235`，网关按设备合同解释成 `23.5°C`，附带采样时间和质量标记后发布到 MQTT。CRC 正确只证明这一帧通过了差错检测，不证明单位、地址和时间正确；Broker 已确认也不证明云端规则已执行。断网时网关需有界缓存，恢复后按序号去重，过期温度不能当作当前值参与控制。

联调按三段验收：先核对现场接线、站号、波特率与原始寄存器；再核对网关的字节序、倍率、时间戳和离线缓存；最后断开上云网络，检查重连补发与命令幂等。云端写操作还应有授权和设备侧保护，不能仅因 CRC 或 MQTT QoS 正确就允许执行控制动作。

# 网络容量、并发与性能

“一台服务器能承担多少并发”没有脱离环境的固定答案。连接数、每秒新建连接、请求吞吐、消息扇出和网络带宽是不同容量维度，必须分别建模。

这一篇先用一个常被问到的数字把连接数这条线走通：很多人会脱口而出“65535”，因为端口号是 16 位，最大到 65535。顺着一条连接从建立到长期保持的过程看，它要依次通过端口、文件描述符、内存、CPU 和内核队列几道关卡，65535 只出现在第一道，而且主要卡的是客户端。读完后，你应该能说清某台服务器的连接上限卡在哪一道，以及调高一个参数后瓶颈会移到哪里。后半篇再讨论吞吐、扇出、背压和中间设备。

![一条连接要依次通过的五道关卡](/protocol/connection-capacity-gates.svg)

图里的五道关卡是串联的：实际能承载的连接数，由最先被触碰的那一道决定。下面按顺序逐道展开，贯穿案例是一台面向手机 App 的长连接推送网关，客户端连上后长期保持，每 30 秒发一次心跳。

## 端口：65535 是谁的上限

TCP 连接由四元组唯一标识：

```text
source IP + source port + destination IP + destination port
```

推送网关只监听 443 一个端口。所有客户端连接的“目标 IP + 目标端口”都相同，区分它们靠的是客户端各自的 IP 和临时端口。只算 IPv4，单个监听端口理论上可以对应 2³² 个客户端地址 × 2¹⁶ 个端口，约 2.8 × 10¹⁴ 种组合，远在其他关卡之前用不完。所以服务端的连接数从来不是被 65535 卡住的。

端口真正会耗尽的是发起连接的一方。客户端或代理用同一个源 IP 连同一个“目标 IP + 端口”时，四元组里只剩源端口一个变量。Linux 自动分配的临时端口范围由 `ip_local_port_range` 决定，常见默认是 32768–60999，约 2.8 万个；主动关闭的连接还会在 `TIME_WAIT` 里占住端口约 60 秒。网关如果作为反向代理，用一个出口 IP 连同一个上游地址，就会在这里先碰到上限，表现为 `connect()` 返回 `EADDRNOTAVAIL`。

```bash
sysctl net.ipv4.ip_local_port_range
sysctl net.ipv4.ip_local_reserved_ports
ss -tan state time-wait | wc -l
```

增加客户端源 IP、连接多个上游地址，都能扩大四元组空间。连接池复用通常比持续创建短连接更有效。

## 文件描述符：默认额度只有一千左右

Linux 把网络连接也当作文件管理，每条已建立的 Socket 占用进程的一个文件描述符（fd）。fd 有三层额度：

| 层级 | 位置 | 常见默认 | 超限时 |
|---|---|---|---|
| 进程软限制 | `ulimit -Sn`、systemd 的 `LimitNOFILE=` | 1024 | `accept()` 返回 `EMFILE` |
| 进程硬限制 | `ulimit -Hn`；不能超过 `fs.nr_open` | systemd 240 起的服务为 524288 | 软限制无法再调高 |
| 系统总量 | `fs.file-max` | 按内存大小自动计算 | 返回 `ENFILE` |

软限制停在 1024，是为了兼容老的 `select()`：它无法处理编号 ≥ 1024 的 fd。推送网关若直接用默认配置启动，连上一千条左右就会开始报 `EMFILE`，此时内存和 CPU 还几乎是空的。这就是“全默认只能撑几千连接”的主要原因（监听 Socket、日志文件和上游连接也各占一个 fd）。

```bash
ulimit -Sn
ulimit -Hn
sysctl fs.nr_open fs.file-max
cat /proc/sys/fs/file-nr
cat /proc/PID/limits | grep 'open files'
```

最后一条看的是正在运行的进程实际拿到的额度。Shell、systemd 与容器运行时各有一套配置，在终端里改了 `ulimit` 不会作用到 systemd 启动的服务。只提高 fd 额度也不会增加内存、端口、连接跟踪和应用处理能力，瓶颈会移到下一道。

## 内存：空闲连接很便宜，堆积数据的连接很贵

fd 放开后，内存通常是长连接服务的核心约束。一条连接可能包含：

- 内核 Socket 与 TCP 控制块。
- 发送、接收和重传队列。
- TLS 会话与加密缓冲。
- 应用 Session、解析器、定时器和消息队列。
- 分配器元数据与内存碎片。

这些部分的大小差别很大。一条建立后没有数据往来的空闲连接，内核里主要是几个固定对象（Socket、TCP 控制块、文件和目录项等），常见内核上合计约 3～4 KB。收发缓冲是按需分配的：有数据在途或对端读得慢时，单连接缓冲会按 `tcp_rmem` / `tcp_wmem` 的范围增长到几十 KB 乃至 MB 级；系统所有 TCP 缓冲的总量再受 `tcp_mem`（单位是内存页）约束，超过压力线后内核会收紧分配并开始丢包。

用推送网关算一笔账。下面是教学估算，数字需要用实测替换：

```text
给连接用的内存预算：8 GiB = 8,388,608 KiB

只算内核空闲对象（按 3.5 KiB）：
  8,388,608 ÷ 3.5   ≈ 240 万条

加上应用层每连接状态（Session、TLS、读写缓冲，按 20 KiB）：
  8,388,608 ÷ 23.5  ≈ 36 万条

36 万条里有 1% 的客户端读得慢，每条积压 256 KiB 未发送数据：
  3,600 × 256 KiB   ≈ 900 MiB
```

同样 8 GiB，按“每连接 4 KB”估出的上百万条，到了真实应用里可能只剩几十万；少量慢客户端又能吃掉上百 MB。所以容量估算要用测量值：

```text
memory ≈ connections × average bytes per connection + shared overhead
```

空闲连接、活跃连接和慢客户端的成本差异很大，不能用一个固定的“每连接几 KB”覆盖所有工作负载。测量时先建立一批空闲连接，比较前后的 Socket 内存和 slab 占用，再让一部分连接持续收发，看缓冲增长：

```bash
cat /proc/net/sockstat
sysctl net.ipv4.tcp_mem net.ipv4.tcp_rmem net.ipv4.tcp_wmem
ss -tm
slabtop -o
```

`/proc/net/sockstat` 里 `TCP: ... mem` 一项的单位是页，与 `tcp_mem` 可以直接比较。

## CPU 与事件模型：连得上之后还要跑得动

连接建好不是摆设：握手、心跳、收发包、TLS 加解密和业务处理都要消耗 CPU。空闲连接本身几乎不占 CPU，但长连接服务总会有周期性流量。推送网关保持 100 万条连接、每 30 秒一次心跳，仅心跳就是每秒约 3.3 万次请求，再加上对应的 ACK 报文。

处理模型决定了这些 CPU 花在哪里。一条连接配一个线程时，几十万条连接意味着几十万个线程，调度切换和线程栈会先压垮机器；用 `epoll` 这类事件驱动模型，少量线程就能同时等待大量 fd，只在某条连接有数据时处理它。阻塞、非阻塞与事件循环的细节见 [TCP、UDP 与 Socket](./transport-socket.md)。

CPU 最容易出问题的时刻是重连风暴。网关重启或网络抖动后，100 万个客户端如果都在 60 秒内重连，就是每秒约 1.7 万次新建连接和 TLS 握手，远高于平时的新建速率；握手排队超时又会触发客户端再次重试。连接数上限再高也挡不住这一波。客户端重连要加随机抖动和指数退避，服务端分批滚动重启，并对新建速率限流。

## 内核队列：握手完成后还要排队等 accept

三次握手完成的连接先进入监听 Socket 的 accept 队列，等应用调用 `accept()` 取走。队列长度取应用传给 `listen()` 的 backlog 与 `net.core.somaxconn` 中较小的一个；`somaxconn` 从 Linux 5.4 起默认 4096，之前是 128。半连接（收到 SYN、尚未完成握手）另有 `tcp_max_syn_backlog` 控制。应用自己的 backlog 也要检查，例如 Nginx 在 Linux 上默认是 511。

队列满时新握手会被丢弃，客户端看到的是建连超时，而服务端 CPU 和内存可能都还有余量：

```bash
ss -lnt             # 监听行的 Recv-Q 是当前排队数，Send-Q 是队列上限
nstat -az TcpExtListenOverflows TcpExtListenDrops
```

两个计数器持续增长，说明应用取连接的速度跟不上，或者队列太短。经过 NAT 或防火墙时，`nf_conntrack_max` 等连接跟踪上限也属于这一道，见后面的中间设备容量。

## 默认配置与长连接网关的对比

把五道关卡放在一起，同一台机器的两种配置差别如下。右列是长连接网关的示例取值，需要按压测结果调整：

| 关卡 | 全默认 | 长连接网关示例 |
|---|---|---|
| 进程 fd | 软限制 1024 | `LimitNOFILE=1048576` |
| 系统 fd | `fs.file-max` 自动值 | 确认大于所有进程 fd 之和 |
| 处理模型 | 一连接一线程 | `epoll` 事件循环，少量工作线程 |
| 内存 | 不设预算 | 按实测每连接内存设上限，每连接队列有界 |
| accept 队列 | `somaxconn` 4096，应用 backlog 511 | 两者同步调大并监控溢出计数 |
| 重连 | 客户端立即重试 | 随机抖动、指数退避、新建限流 |
| 上限表现 | 一千左右报 `EMFILE` | 受内存预算和心跳 CPU 约束 |

以 systemd 管理的服务为例，fd 额度写在服务的覆盖配置里，内核参数写在 `/etc/sysctl.d/`。下面的服务名 `gateway` 是占位：

```ini
# /etc/systemd/system/gateway.service.d/limits.conf
[Service]
LimitNOFILE=1048576
```

```ini
# /etc/sysctl.d/90-gateway.conf
net.core.somaxconn = 8192
net.ipv4.tcp_max_syn_backlog = 8192
```

```bash
sudo sysctl --system
sudo systemctl daemon-reload
sudo systemctl restart gateway
cat /proc/$(pidof gateway)/limits | grep 'open files'
```

最后一条应显示软、硬限制都是 1048576；如果仍是 1024，说明配置没有作用到这个进程，检查覆盖文件路径和服务名。`LimitNOFILE` 不能超过 `fs.nr_open`（默认 1048576），要更高时先调大 `fs.nr_open`。`somaxconn` 只是上限，应用自己的 backlog 参数也要同步调大才会生效。

这样配置后，连接数的上限才回到内存预算和 CPU 上。能否达到某个具体数字，取决于实测的每连接内存、心跳频率和新建速率，需要按后文的压测模型验证。

## 三个不同指标

| 指标 | 主要成本 | 常见瓶颈 |
|---|---|---|
| 并发连接数 | 状态、fd、内存、心跳 | fd、Socket 内存、conntrack |
| 每秒新建连接 | SYN、对象分配、TLS | CPU、队列、证书运算 |
| 请求或消息吞吐 | 解析、业务、复制、下游 | CPU、线程池、数据库、网卡 |

百万空闲连接不代表能每秒建立百万连接，也不代表每条连接都能持续高吞吐。

## 带宽、包率与消息扇出

基础带宽模型：

```text
出站字节/秒 ≈ 每秒产生的事件数 × 每事件接收人数 × 每份消息字节数
也可按接收者统计：活跃连接数 × 每连接每秒收件数 × 每份消息字节数
```

还要加上 Ethernet、IP、TCP/UDP、TLS 和应用 Header。小消息场景可能先受每秒包数与系统调用影响，大消息场景更容易受网卡带宽和内存复制影响。

一次消息广播给十万连接，不能只按入口消息速率估算；真正出站负载要乘以扇出，并考虑序列化是否能够共享。

例如订单状态每秒产生 100 条事件，每条 500 字节，平均推送给 20 个订阅者，则正文出站约 `100 × 20 × 500 = 1,000,000 B/s`，即约 `8 Mbit/s`。如果已按每个订阅者的收件速率统计，就不能再乘一次扇出。压缩、批量打包和协议头会改变实际网卡流量，最终仍要测量。

## 慢消费者与背压

当生产速度超过网络或客户端消费速度，数据会堆积在：

![慢消费者的队列积压与背压边界](/protocol/connection-backpressure.svg)

假设某客户端每秒入队 20 条、只能处理 5 条，每条 1 KiB，则净积压为每秒 15 KiB。一条有 1 MiB 上限的队列约 68 秒就会填满，协议头和对象开销还会缩短这个时间。提高服务器连接数上限无法改变这条连接的收支差。

每条连接必须有队列上限，并明确超限策略：

- 丢弃已经过期的旧状态。
- 合并同一对象的多次更新。
- 暂停上游生产。
- 降低订阅频率或消息精度。
- 关闭长期无法追上的连接。

无限队列只是把背压变成内存故障。

订单“当前状态”可以按订单 ID 合并为最新值，支付流水则不能静默丢弃；后者需要持久化日志和消费游标，超过实时窗口时要求客户端从日志恢复。先确定数据能否丢弃，再决定队列超限行为。

## 中间设备容量

端到端容量由链路中最小上限决定：

```text
客户端端口池
→ NAT 映射
→ 防火墙 conntrack
→ 负载均衡
→ 代理连接池
→ 服务器 Socket
→ 应用与下游
```

只压测服务器环回地址无法验证真实生产链路。NAT、云负载均衡和防火墙都有并发连接、每秒新建、超时与端口限制。

## 代理与连接池

反向代理接收客户端连接后，通常复用另一组上游连接。客户端有一万连接，不代表每个后端也需要一万连接。

HTTP/1.1 上游连接通常限制同时在途请求；HTTP/2 可以在一条连接上并发多个 Stream。连接池过小会排队，过大则可能压垮后端或制造端口压力。

应同时观察：

- 活跃与空闲上游连接。
- 等待连接池的请求数。
- 每连接并发 Stream。
- 建连、TLS、首字节与总耗时。
- 重试次数和实际 Attempt 数。

## DNS、CDN 与缓存容量

CDN 通过 Cache Key、TTL 和验证请求减少回源。错误的 Key 可能串内容，Key 过细则命中率过低。

缓存容量不能只看命中率，还要看：

- 热点对象是否在失效瞬间引发回源洪峰。
- 大对象是否驱逐大量小对象。
- `Vary`、Cookie 和 Query 是否造成碎片化。
- 过期对象能否在源站异常时提供 Stale 响应。

## 可复现压测模型

压测报告至少记录：

| 类别 | 必要参数 |
|---|---|
| 环境 | CPU、内存、网卡、内核、容器限制 |
| 连接 | 总数、每秒新建、TLS、空闲比例 |
| 消息 | 大小、频率、方向、扇出、压缩 |
| 网络 | RTT、带宽、丢包、抖动、MTU |
| 应用 | 工作线程、队列、下游依赖 |
| 结果 | P50/P95/P99、错误率、资源和失败点 |

测试应逐步增加负载，使用尾延迟和错误率作为停止条件，并保留安全余量。只报告“成功建立多少连接”无法用于生产容量规划。

这里的命令适用于 Linux；`sar`、`pidstat` 来自 sysstat，`perf` 还需要相应内核支持和采样权限。替换真实 PID，先定位队列或资源增长，再选择采样工具。

```bash
ss -s
ss -ti
sar -n DEV,TCP,ETCP 1
pidstat -t -p PID 1
perf top -p PID
```

容量异常最终仍要回到证据链。下一篇 [网络排障方法与案例](./troubleshooting.md) 给出从客户端到服务端逐层收敛的流程。

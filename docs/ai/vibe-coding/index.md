# AI 编程工程化

AI 可以帮助试想法，也可以读代码、调用工具并完成多步修改。这个专题用“后台订单导出”说明：怎样把自然语言需求交给 AI，并用项目事实、权限和独立验证判断结果。开发周期、敏捷与 DevOps 的组合关系见[开发方法总览](/docs/design/develop-pattern/)。

![规格、上下文、Agent、Harness 和团队反馈的协作关系](/ai/vibe-coding-position-map.svg)

这些能力可以组合使用。一次小修复也需要验证；一开始使用 Agent 就需要限定工具权限。Vibe Coding 适合用测试数据探索需求，Spec-Driven 用可检查的规格约束实现，二者都不能替代权限控制和测试。

## 从当前问题选择入口

| 当前问题 | 应形成的结果 | 阅读入口 |
| --- | --- | --- |
| 还不知道导出按钮和筛选流程是否合用 | 可试用原型，以及试用后确认的业务需求 | [Vibe Coding](./vibe-coding.md) |
| AI 总在猜字段、范围和完成标准 | 写清目标、范围、禁区和验收的任务说明 | [提示词工程](./prompt-engineering.md) |
| 代码能生成，却接不上现有系统 | 页面、接口、权限、字段和测试组成的上下文包 | [上下文工程](./context-engineering.md) |
| 希望 AI 连续修改和验证 | 能定位失败、修复并交出证据的工具循环 | [工具与 Agent](./tool-agent-engineering.md) |
| 担心改错文件、读到生产数据或越权执行 | 运行时权限、隔离环境、CI 门禁和恢复入口 | [Harness 工程](./harness-engineering.md) |
| 需求、实现、测试经常各说各话 | 共享规格及可执行的成功、拒绝和失败示例 | [Spec-Driven](./spec-driven.md) |
| 多个项目反复漏同类问题 | 可复用模板、测试、检查项和维护责任 | [组织流程](./organizational-engineering.md) |
| 需要串起一个完整功能 | 从需求到构建、评审、发布和恢复的交付链路 | [项目实战](./project-practice.md) |

## 例子：小林需要每月对账

小林最初只说“订单加个导出”。先用虚构订单做原型，试用后发现她要导出的是整个月的筛选结果，不是当前页，还要保留金额精度。原型解决了流程是否合用的问题，真实数据的边界仍需单独确定。

![订单导出原型的试用、判断与反馈](/ai/vibe-order-export-loop.svg)

准备接入后台时，团队把规则写进规格：服务端只查当前租户订单，检查 `order:export` 权限，按字段白名单生成 CSV，超量时拒绝并提示缩小范围。Agent 读取现有查询与权限代码后实现，测试则尝试无权限、跨租户和超量请求。能下载文件只是成功路径，拒绝路径也通过才有交付证据。

文件要异步生成时，还要设计任务状态、下载时重新鉴权和文件过期。此时先调整规格与验证，再让 Agent 实现。上线后若导出拖慢数据库，应在服务端停止接收新导出，处置运行中的任务，再根据日志补充容量测试；只隐藏按钮或回滚前端不能停止已有请求。

完整代码入口、CI 示例和发布检查见[项目实战](./project-practice.md)。

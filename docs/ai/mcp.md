# MCP

MCP（Model Context Protocol）是一种让 AI 客户端接入外部工具和数据源的协议。它关注的不是“模型如何生成回答”，而是“模型所在的客户端怎样以统一方式发现工具、读取资源、调用能力”。

可以把 MCP 理解为 AI 工具生态里的统一插座：客户端不需要为每个数据库、文件系统、业务 API 都写一套私有接法，而是通过 MCP Server 暴露标准能力。

![MCP 架构](/ai/mcp-architecture.svg)

## 与其他模块的关系

- 大语言模型负责理解和生成，见 [大语言模型](./llm/)。
- 智能体负责组织多步任务，见 [智能体](./agent.md)。
- Skill 负责告诉 Agent 什么时候、怎样使用工具，见 [Agent Skill](./skill/)。

MCP 标准化连接与消息合同，不自动保证任务目标正确。业务授权、执行策略、必要的用户确认和审计仍由应用与服务端承担。以下传输和消息示例以 **2025-11-25 协议版本**为范围；接入时以双方实际协商的版本和能力为准。

## 基本架构

| 角色 | 作用 | 例子 |
| --- | --- | --- |
| Host（宿主应用） | 承载交互、模型及连接管理，决定哪些内容进入上下文 | IDE、桌面助手、命令行代理 |
| MCP Client | 宿主内部的协议客户端，每条连接面向一个 Server | 协商能力、列出工具、发起调用 |
| MCP Server | 封装外部能力 | 文件读取、数据库查询、业务 API |
| 外部资源 | 真正的数据或系统 | 仓库、数据库、工单、搜索、云服务 |

MCP Server 像一个受控服务台。它不应该把整个系统无差别暴露给模型，而应该把能力拆成明确、可审计、权限受限的工具。

本地 `stdio` 通常由宿主启动 Server 子进程，通过标准输入输出传递按行分隔的 JSON-RPC 消息；普通日志写到 `stderr`，不能把启动提示混进 `stdout`。远程服务常用 Streamable HTTP，向 MCP 端点发送 POST，响应可以是 JSON 或 SSE 流；客户端也可使用 GET 监听服务端消息。Streamable HTTP 可以使用 SSE，但不等同于早期独立 SSE 端点的旧传输。

本地进程按启动用户的系统权限运行，并不因为使用 stdio 就自动进入沙箱。HTTP 服务需要鉴权、Origin 检查和合理监听地址；凭据由受控连接配置提供，不放在模型工具参数里。

## 从连接到一次订单查询

客户端先发送 `initialize`，协商协议版本、能力和实现信息；收到可接受的结果后发送 `notifications/initialized`。之后再使用双方支持的功能。例如 Server 声明 `tools` 能力，Client 才通过 `tools/list` 获取工具定义，模型提出调用意图后由宿主按权限策略决定是否发送 `tools/call`。

![MCP 初始化、发现、业务鉴权和结果返回的消息时序](/ai/mcp-tool-call-sequence.svg)

下面是初始化与工具发现完成后，一次工具调用的消息示意，不是可直接运行的完整客户端。`id` 用来关联 JSON-RPC 请求与响应，不是用户身份，也不是业务幂等键。

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "query_order_status",
    "arguments": { "order_id": "A102" }
  }
}
```

Server 从连接或会话确定身份，调用订单服务检查归属，再返回必要字段。Host 校验结果并决定是否放入模型上下文；“已发货”只是查询时状态，不证明包裹已经签收。

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "content": [{ "type": "text", "text": "{\"order_id\":\"A102\",\"status\":\"shipped\"}" }],
    "isError": false
  }
}
```

工具定义中的 `inputSchema` 约束参数，`outputSchema` 可约束 `structuredContent`。这两者与模型厂商的结构化输出功能不同；即使 JSON 形状合法，也需要检查订单归属、状态含义和字段范围。

## MCP 能暴露什么

常见能力包括：

- 工具：执行一个动作，例如查询订单、搜索文档、创建工单。
- 资源：读取一类内容，例如文件、数据库表、知识库页面。
- 提示模板：提供固定任务入口，例如代码审查模板、摘要模板。

工具更像按钮，资源更像资料柜，提示模板更像标准表单。三者可以组合，但职责不同，也不要求每个 Server 都实现全部能力。资源 URI 不必等于公开网页地址，Server 仍需限制读取范围。

## 什么时候需要 MCP

适合使用 MCP：

- 多个 AI 客户端都要访问同一类内部工具。
- 工具需要统一权限、审计和参数校验。
- 希望把数据库、文件、业务系统以标准方式暴露给 Agent。
- 不希望每个客户端都维护一套私有插件。

不一定需要 MCP：

- 只是一次性脚本或本地临时命令。
- 工具只服务一个固定应用，且已有稳定私有集成。
- 数据不能被模型侧读取，必须通过后端固定流程处理。

## 从一个只读工具开始

设计 MCP Server 可先做范围明确的只读查询工具，练清协议、参数、权限和返回结构。只读仍可能泄露订单或个人信息，也可能产生访问日志与调用费用；它只减少业务写入风险，不免除数据授权。

以“查询订单状态”为例，工具边界可以这样定：

| 项目 | 设计方式 |
| --- | --- |
| 工具名 | `query_order_status` |
| 输入 | `order_id`，必须是订单号格式 |
| 权限 | 当前用户必须有订单查看权限 |
| 返回 | 订单状态、支付状态、发货状态、必要时间字段 |
| 不返回 | 手机号、详细地址、用户备注、内部风控备注 |
| 错误 | 内部区分参数、权限、资源和超时；对外按策略合并无权访问与不存在，避免枚举订单 |

这类工具的重点不是把数据库能力原样暴露出去，而是把业务动作封装成窄接口。模型只表达“想查订单状态”，真正的校验、查询、脱敏和审计由 Server 完成。

只读工具稳定后，再考虑写操作。写操作需要处理幂等、适用的确认策略、审计、补偿与环境隔离。是否每次弹窗取决于已有授权和业务风险；不能把确认提示当作服务端鉴权。工单确认与超时恢复见[工单处理助手](./practice/agent-project.md)。

## 一个具体场景

假设要做“订单客服助手”：

1. 用户问：“这笔订单为什么还没发货？”
2. 模型需要订单状态，但不能直接访问数据库。
3. MCP Server 暴露一个 `query_order_status` 工具，只允许按订单号查询必要字段。
4. 客户端把工具结果放回上下文。
5. 模型基于订单状态和发货规则生成答复。

这里的关键不是“模型更聪明”，而是外部数据以安全、可控、可追踪的方式进入上下文。

## 设计 MCP Server 的原则

### 工具要小而明确

不要暴露“执行任意 SQL”这类过宽工具。更稳妥的是暴露受控动作：

- 查询订单状态。
- 查询用户最近工单。
- 搜索知识库文章。
- 创建一条草稿回复。

工具越接近业务动作，越容易限制参数、审计结果和做权限控制。

### 权限要最小化

只读能完成任务，就不要给写权限。只需要订单状态，就不要返回完整用户信息。只需要某个目录，就不要开放整个文件系统。

### 结果要适合模型使用

工具返回不要过长。应包含完成任务需要的字段、必要状态和错误信息。长日志、长表格、长文档应支持分页、过滤或摘要。

### 分清协议错误与工具失败

未知工具、畸形请求或服务端协议处理错误可返回 JSON-RPC `error`；调用进入工具后发生的业务失败、上游 API 失败或参数值不合规，可以在正常 JSON-RPC `result` 中返回 `isError: true`。HTTP 200 或收到 `result` 都不能单独证明业务成功，应用要读取工具结果合同。错误详情要足以恢复，同时避免泄露内部堆栈、凭据或其他用户资源。

连接中断、HTTP 超时和取消通知也不能证明写操作没有发生。协议请求 ID、HTTP 会话 ID、SSE 事件 ID、业务幂等键各有用途，不能互相替代。若工具有副作用，先按业务操作 ID 回查，再按约定重试。进度通知不能无限延长总执行预算。

## 安全边界

MCP 带来的风险主要来自“模型能触达外部系统”。需要重点处理：

- 凭证不进入对话和日志。
- 工具参数做白名单和类型校验。
- 写操作需要幂等设计和与已有授权一致的确认策略。
- 访问结果脱敏。
- 调用日志可审计。
- 不同环境使用不同权限。

MCP Server 不应把模型当成可信调用方。模型产生的是意图，Server 负责验证这个意图能不能执行。

## 排查路径

| 现象 | 优先检查 |
| --- | --- |
| 客户端看不到工具 | 进程/端点可达、initialize是否成功、tools能力、tools/list分页与权限过滤 |
| stdio 一连接就解析失败 | stdout是否混入启动日志，消息是否完整且按行分隔；诊断日志看stderr |
| 工具调用失败 | 先分HTTP/JSON-RPC错误与result.isError，再查schema、权限和上游Trace |
| 列表刚有工具，调用却称不存在 | 连接与工具列表是否变化，是否处理listChanged并重新发现 |
| 返回太长污染上下文 | 是否需要分页、过滤、摘要或字段裁剪 |
| 模型误用工具 | 工具命名是否清楚、描述是否准确、Skill 是否补充流程 |
| 权限过大 | 是否拆分只读/写入工具，是否按环境隔离凭证 |

## 总结

MCP 的价值是标准化连接外部世界。它把工具和资源包装成 AI 客户端可发现、可调用、可审计的能力。设计 MCP 时重点不是接得越多越好，而是工具边界清楚、权限最小、返回可用、失败可判断。

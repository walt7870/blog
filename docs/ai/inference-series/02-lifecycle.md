# 02. 从输入到逐步生成

上一篇认识了模型中的参数，以及应用怎样把问题和资料送进去。这一篇继续追问：机器拿到文字后，究竟怎样算出一段回答？我们先看文字如何成为计算的输入，再逐步接出“先提交申请”，最后解释聊天窗口里两种不同的等待。

## 文字先变成编号

计算机需要把输入转成数字才能进行模型计算。语言模型通常先将文字切成小片段，再按一张固定的词表，把每个片段对应到一个编号。这种片段叫 **token**，负责切分与编号的程序叫分词器。

用一个简化的教学词表，可以把问题画成：

```text
文字：  年假  ·  怎么  ·  申请  ·  ？
编号：   21      83      46      9
```

这里的编号由我们随意选取，方便跟踪位置。真实模型有自己的词表和切分规则：一个 token 可能是一部分词、一个标点，也可能覆盖几个汉字。同一句话换一个模型，得到的 token 数量也可能变化。

这些编号还会通过模型中的一张数值表，变成一组组用于计算的数字。你可以先记住这个过程：**文字片段 → 编号 → 数值运算**。因此，服务统计输入长度时，通常按 token 数计量。

## 每轮先选出下一段

模型处理输入后，会为词表中的候选计算分数，再转换成选择概率。例如，对“年假怎么申请？”给出第一段回答时，可能出现这样的教学结果：

| 下一个片段 | 示例概率 |
| --- | ---: |
| 先 | 60% |
| 请 | 30% |
| 可以 | 10% |

这些数字展示选择过程。真实词表通常有数万乃至更多候选；这里先只放三个，并采用“每次选概率最高的一项”的规则。

选到“先”以后，模型把它加在已经处理的内容后面，再计算下一段。新一轮的输入已经包含“先”，所以候选也随之变化，可能轮到“提交”排在前面。继续一次，就得到“申请”。

<InferenceLab mode="generation" />

这就是逐步生成的关键：**已经选出的结果，会参与下一轮计算。** 一句话越写越长，后面的选择就建立在更长的历史上。上面的实验使用预先写好的候选概率，点击时只推进教学过程；真实模型每轮都要重新执行数值计算。

也因此，前面生成了错误内容，后面可能继续沿着它往下写。涉及申请条件、日期或金额时，应用需要让结果与资料核对，必要时重新生成。

## 为什么开头会先等一下

开始回答之前，问题、制度片段和聊天记录都已经给定，模型要先处理这批输入。这个阶段叫 **预填充（prefill）**。输入中的位置已经确定，可以成批组织计算。

第一个回答片段选出后，模型继续利用已有内容，一步步生成后续片段。这个阶段叫 **解码（decode）**。对于这里讨论的常规逐步生成，后一步需要等前一步的选择结果。

<InferenceFigure name="read-then-write" alt="模型先处理已有输入，再根据此前结果逐步生成后续文字" />

读一整本制度与读一句问题，输入工作量不同；生成两句话与生成两页文字，后续轮数也不同。它们分别影响不同阶段的耗时。

模型还会保存一部分已算过的中间结果，让下一轮接着用。这些状态占用内存或显存，第 3、4 篇再展开它们的大小与复用方法。

## 开始得慢，和说得慢

现在观察聊天窗口，可以把等待分成两段：发送后多久出现第一个结果，以及开始之后后续片段来得是否及时。

<InferenceFigure name="latency-ruler" alt="发送问题到首个结果的等待，以及后续生成片段之间的间隔" />

例如，下面两种情况完整耗时都是 5 秒，感觉却不同：

- 先等 4 秒，再用 1 秒显示完回答：应检查输入处理和此前的等待。
- 等 1 秒就开始，再花 4 秒陆续显示：应检查生成阶段与输出长度。

工程上常把客户端发出请求到第一个生成 token 的时间叫 **TTFT，首 token 时间**。其中除了模型处理输入，也可能包含网络、应用准备资料和排队。后续片段的间隔，则反映回答开始后的流畅程度。

流式返回把已产生的片段陆续交给页面，用户可以提早读到内容。网络一次可能送来几个 token，页面上“一块块出现”的节奏还会受传输与渲染影响。

## 回答在什么时候结束

生成到适当位置时，模型可以选出特殊的“结束”标记，程序据此停止。服务还可以设置最长输出长度，用户也可以中途点击停止。

三种结束方式需要分别看：模型正常结束通常表示本轮生成完成；长度上限可能把一句话截在半路；用户取消则需要应用把停止通知传到正在计算的服务。否则窗口停了，后台还可能继续做活。

<details>
<summary>测量时怎样区分网络包与生成 token？</summary>

首个网络包可能只携带角色信息，推理模型也可能先输出思考字段，再输出正文。计时时应先约定观察的是第一个生成 token 还是第一个正文片段。单个网络块可以带多个 token，精确的逐 token 间隔需要相应的服务端事件支持。

常见的平均每输出 token 耗时为 `(完整耗时 - 首 token 时间) / (输出 token 数 - 1)`，适用于输出超过一个 token 的请求。还需要观察中途长停顿；仅看平均值会把它们摊平。

</details>

一次回答到这里可以串起来了：文字变成 token 编号，模型处理已有输入，选出下一段，再带着新结果继续计算，直到结束。第一次等待与后续生成对应不同工作，排查慢在哪里时也应该分别观察。

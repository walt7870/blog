# 大模型推理与部署

推理是模型训练完以后，真正响应请求、生成回答的过程。做大模型应用时，推理会以几种方式影响你的设计：回答要等多久才开始出现，长资料塞进上下文要付出什么代价，同样的问题为什么两次回答不同，自己部署一个模型需要几张卡。这一页先帮你判断推理问题落在哪一层、该由谁负责，再给出应用开发者最常碰到的几个概念，每个概念的详细推导都在[大模型推理优化](../llm-inference/)系列里，文中给出对应章节。

以退款助手为例：用户问“我上周的订单能退吗”，应用先检索退款规则、查询订单，再把规则、订单和问题拼成上下文交给模型，模型逐个 token 生成回答，应用把回答流式推送给用户，最后记录日志。前两步和最后两步是应用的事；中间“把上下文变成一个个 token”的部分，就是推理。

## 先分清：调用接口还是自己部署

| | 调用模型服务商的接口 | 自己部署开源模型 |
| --- | --- | --- |
| 推理由谁负责 | 服务商：显卡、引擎、调度、扩容都不用管 | 你：要选引擎、配显卡、压测、监控 |
| 你能控制的 | 模型选择、提示词、采样参数、输出长度、是否流式 | 以上全部，加上量化、批大小、缓存策略、部署位置 |
| 成本怎么算 | 按输入和输出 token 计费 | 按显卡时长计费，利用率越高越划算 |
| 适合的情况 | 起步阶段、流量不稳定、需要最强的模型 | 数据不能出内网、流量稳定且大、需要定制模型 |

大多数应用从调用接口开始。即使不自己部署，下面几个概念也值得了解，因为它们决定了接口的延迟和账单。需要自己部署时，先按系列推荐的顺序读第 1—7 篇，做一遍[实践：用 vLLM 跑起资料助手](../llm-inference/vllm-quickstart.md)，再按需要挑第三到第五部分。

## 一次请求慢在哪里

![Prefill、逐步解码与KV缓存内存的组成](/ai/kv-cache-memory-contract.svg)

模型生成分两个阶段。**Prefill** 一次性读完整个输入，建立缓存，决定了第一个字出现前要等多久（**TTFT**，首 token 延迟）；**Decode** 每一步只生成一个 token，决定了之后的文字以什么速度往外冒（**TPOT**，每个输出 token 的时间）。比如 TPOT 是 20 毫秒，生成 500 个 token 的回答大约要 10 秒。两者的瓶颈不同：Prefill 主要受算力限制，输入越长越慢；Decode 主要受显存带宽限制，每一步都要把模型参数和历史缓存读一遍。

这对应用设计有直接影响：

- 塞进上下文的资料越多，用户等第一个字就越久；
- 要求的回答越长，总耗时越接近“输出长度 × TPOT”；
- 两件事要分开测。只看端到端的平均耗时，分不清是检索慢、排队慢、Prefill 慢还是生成慢。

原理见系列[第 2 篇](../llm-inference/02-prefill-decode.md)；各个指标的定义和陷阱，比如平均值为什么会掩盖尾部延迟，见[第 5 篇](../llm-inference/05-metrics.md)。

## KV Cache：长上下文贵在哪里

Decode 每生成一个 token，都要用到前面所有位置的 Key 和 Value 向量。把它们存下来不再重算，就是 **KV Cache**。缓存避免了重复计算，但当前 token 仍要和历史上的每一个位置计算注意力，所以上下文越长，每一步还是越慢。

它的代价是显存，大小可以直接算：

```text
KV 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 每个数的字节数 × token 数
```

以 Llama-3.1-8B 为例（32 层、8 个 KV 头、每头 128 维、BF16 每个数 2 字节），每个 token 占 128 KiB，一个 4096 token 的请求占 512 MiB，四个这样的请求同时进行就是 2 GiB。模型权重本身（8B 模型 BF16 约 16 GB）是固定开销，显存扣掉权重和运行开销后剩下的部分，除以每个请求的 KV，就是能同时进行的请求数上限。所以自己部署时，很多时候先撞上的是显存，而不是算力。

公式里用的是 **KV 头数**，不是注意力头数。现在的模型大多用 GQA（分组查询注意力）：让几个注意力头共用一组 K 和 V，缓存因此小了几倍。Llama-3.1-8B 有 32 个注意力头、8 个 KV 头，缓存只有不共用时的四分之一。还有一些模型结构会进一步压缩缓存，要按实际实现另算。详细的账本见[第 3 篇](../llm-inference/03-kv-cache.md)和[第 4 篇](../llm-inference/04-memory-budget.md)。

对应用来说，结论是：**长上下文不是免费的。** 上下文越长，首字越慢、显存越紧、单次请求越贵，模型也更容易被无关内容干扰。先检索、过滤、摘要，把真正相关的资料交给模型，通常比把整本手册塞进去效果更好也更便宜。

## 前缀缓存：相同的开头只算一次

很多请求的开头是一样的：同一段系统提示、同一份制度文档、同一段对话历史。推理引擎和不少模型服务商会把这些开头的 KV 保留下来，下一个请求开头一致时直接复用，跳过这部分的 Prefill。效果是首字更快，服务商通常还会对命中缓存的输入 token 打折。

要命中缓存，有几个条件，设计提示词时就要考虑：

- **开头必须逐 token 完全一致。** 把每次都变的内容（当前时间、用户名、检索结果）放在后面，把固定不变的系统提示和文档放在前面。开头插入一个时间戳，后面的全部失效。
- **模型和相关配置要一致。** 换了模型版本，或者换了挂在模型上的微调适配器（如 LoRA，见[训练与微调](./training.md)），缓存不能复用。
- **改了中间就只能复用到改动之前。** 修改了制度文档的某一段，这一段之后的缓存都要重算。

服务商的缓存规则（最短长度、保留多久、怎样计费）各不相同，以它的接口文档和返回的用量统计为准。引擎内部怎样实现，见[第 10 篇](../llm-inference/10-prefix-cache.md)。

这里的“缓存”是推理中间状态的缓存，不是答案缓存。应用层如果缓存回答本身，要按用户和权限分区，并在源数据变化时失效，否则会把一个人的订单信息返回给另一个人。

## 采样参数：为什么两次回答不同

模型每一步输出的是所有候选 token 的概率，**采样参数**决定怎样从中选一个：

- `temperature` 越低越保守，设为 0 通常就是每次选概率最高的；
- `top_p`、`top_k` 砍掉长尾里不靠谱的候选；
- `max_tokens`（新接口里叫 `max_completion_tokens`）限制输出长度，返回结果里 `finish_reason` 为 `length` 表示被截断，应用要按“不完整”处理；
- `stop` 指定停止词。

退款助手这类要求准确的场景，温度设低一些。即使温度为 0，服务端多次请求的结果也可能不完全相同：请求和别的请求拼在一起计算时，浮点运算的顺序会变。应用不能依赖“同样的输入一定得到同样的输出”；需要严格可复现时，可以用引擎的确定性模式，代价是性能。详见[第 7 篇](../llm-inference/07-request-path.md)。

## 流式输出：更早看到，但不等于更快算完

流式输出让模型边生成边返回，用户在第一个 token 生成后就能看到内容。它不减少总计算量，只是把等待拆开了；如果用户中途取消、而服务能及时停止，可以省下后续的生成。

流式输出有几条应用层的规则：

- **首字延迟按“第一个有效内容”算**，不是第一个网络字节。检索、排队和 Prefill 都算在里面。
- **未完成的结构化输出不能执行。** JSON 可以流式传输，但在完整解析并通过校验之前，不能拿片段去调用工具或修改数据。退款助手生成的退款请求，即使格式完整，也要由服务端单独校验权限和金额后再执行。
- **中途失败要如实标记。** 已经显示了一部分内容后出错，要告诉用户回答不完整，不能悄悄换一次重试的结果拼接上去，当作同一个回答。
- **取消要传到推理服务。** 用户关掉页面后，如果取消没有传下去，服务会继续为没人看的请求生成，白白占着资源。

## 量化：文件小了不一定更快

量化用更少的位数存储模型的参数，比如从 16 位降到 8 位或 4 位，目的是省显存、提速、降成本。自己部署时它是最常用的手段之一，也最容易被误解：

- 权重变小，不代表总显存同比例下降。KV Cache 是否量化要单独设置，运行开销也还在。
- 文件小了一半，不代表推理快一倍。要有对应的低位计算内核，不然反量化和数据搬运会抵消收益。
- 位数越低，效果越可能下降，而且不同任务的敏感度不同。量化后要用真实任务重新评估，不能只看模型能否启动。

各种格式（INT4、FP8、W4A16 等）分别压缩了什么、什么时候真的更快，见[第 14 篇](../llm-inference/14-quantization.md)。数值格式本身的原理在[模型数值精度](../precision/)专题。

## 多人同时用：批处理与调度

GPU 一次处理一个请求很浪费：Decode 每一步都要读一遍全部参数，在批不太大时，读一次只服务一个人和读一次服务几十个人，耗时差别不大。所以推理服务会把多个请求合成一批计算，**连续批处理**更进一步，每一步都可以加入新请求、移出已结束的请求，不用等一整批都说完。

代价是排队。人越多，每个人分到的资源越少，TPOT 变慢，显存满了还要有人等待。在线对话要控制排队时间；离线批量处理（比如给一万份文档生成摘要）则可以把批开大，换取吞吐和成本。原理见[第 9 篇](../llm-inference/09-continuous-batching.md)。

## MoE 模型的部署

MoE（混合专家）模型参数很多，但每个 token 只激活其中一部分“专家”，所以计算量比同样大小的普通模型小。部署时要注意：

- 全部参数仍然要放进显存，省的是计算，不是存储；
- 专家分布在不同的卡上时，每一步都要在卡之间交换数据；
- 某些专家被频繁选中时会过载，监控要看各专家的负载，而不只是整体 GPU 利用率。

专家并行的做法和代价见[第 16 篇](../llm-inference/16-distributed.md)。

## 按场景看重点

| 场景 | 推理上优先关注 | 应用上优先关注 |
| --- | --- | --- |
| 内部问答 | 长资料的首字延迟，前缀缓存命中 | 检索质量、引用来源、权限控制 |
| 代码生成 | 长上下文的显存与延迟，输出速度 | 用测试和工具验证生成结果 |
| 客服对话 | 首字延迟的尾部分位数，稳定的采样设置 | 统一口径、安全过滤、转人工 |
| 批量摘要 | 吞吐和单位成本，可以开大批 | 失败重试、结果抽检 |
| 高敏数据 | 私有化部署，显卡和引擎选型 | 审计、脱敏、访问控制 |

## 小结

推理决定了应用能多快、多稳、多便宜地拿到回答。首字延迟看 Prefill 和输入长度，生成速度看 Decode 和并发；长上下文贵在 KV Cache；把固定内容放在提示开头能命中前缀缓存；采样参数决定输出的随机性，但温度为 0 也不保证完全一致；流式输出要处理未完成内容和取消；量化省显存，但速度和质量都要实测。

这些结论的推导和数字，以及自己部署模型的完整步骤，在[大模型推理优化](../llm-inference/)系列里。服务上线后的发布、监控与降级，见 [AI 工程化：模型服务与部署](../engineering/serving-deployment.md)。

# 大模型推理与部署

推理是模型上线后真正响应请求的过程。用户看到的是一段回答，系统背后要处理上下文拼装、token 生成、缓存、并发、延迟、显存、成本和安全边界。

深入原理与实操可阅读[大模型推理优化](../llm-inference/)系列：从 Prefill 与 Decode、KV Cache、显存账本和 Roofline 讲起，覆盖 PagedAttention、连续批处理、前缀缓存、量化、投机解码、分布式与 P/D 分离，以及 vLLM、SGLang、压测和生产部署。

## 推理链路

一次请求通常经过：

1. 接收用户输入。
2. 拼接系统规则、历史对话、检索资料和工具结果。
3. Token 化。
4. 模型逐 token 生成。
5. 流式返回或完整返回。
6. 记录日志、指标和安全审计。

这条链路里，模型只是核心计算部分。上下文构造、限流、重试、超时、输出过滤同样影响最终体验。

## 关键指标

| 指标 | 含义 | 影响 |
| --- | --- | --- |
| 首 token 延迟 | 从请求到第一个 token 返回的时间 | 影响用户等待感 |
| 生成速度 | 每秒生成多少 token | 影响长回答体验 |
| 吞吐 | 单位时间处理多少请求 | 影响服务容量 |
| 上下文长度 | 单次请求可输入多少 token | 影响资料承载能力 |
| 显存占用 | 模型运行需要多少 GPU 内存 | 影响部署成本 |
| 成本 | 每次请求消耗的计算资源 | 影响商业可持续性 |

## KV Cache

常见因果 Transformer 先对输入执行 Prefill，构建各层历史位置的 Key 和 Value；Decode 每步为新位置计算状态并读取历史 KV。缓存避免重复计算历史 K/V，但仍要计算当前 Query 对历史位置的注意力，长上下文不会因此变成固定成本。

![Prefill、逐步解码与KV缓存内存的组成](/ai/kv-cache-memory-contract.svg)

它带来的收益是生成更快，代价是占用更多显存。长上下文、多并发场景下，KV Cache 往往是服务容量的关键瓶颈。

对常规全注意力、每层相同 KV 头配置，可估算 `缓存字节 = 2 × 层数 × KV头数 × 头维度 × 已缓存长度 × 并发序列数 × 每元素字节`。假设32层、8个KV头、头维128、4096个位置、单序列、每元素2字节，结果为536870912字节，即512 MiB。4个同长序列约2 GiB，尚未包含分页块浪费、运行缓冲、激活和模型权重。这里用KV头数而非Query头数；滑动窗口、跨层共享或压缩潜在注意力等结构需要按实际实现另算。

权重量化不会自动把KV也量化，缓存类型要单独核对。前缀复用要求模型、适配器、Token序列、位置及相关配置兼容；在中间修改政策后，不能继续使用原前缀后面的状态。供应商的缓存能力和计费以接口为准，缓存仍要遵守租户隔离和访问权限。

## 量化

量化用更低精度表示模型权重或计算结果，目标是降低显存和计算成本。

常见取舍：

- 更低位宽通常减少权重存储，但总显存还受缓存、激活和运行时影响。
- 精度越低，效果越可能下降。
- 不同任务对量化敏感度不同。

量化后必须重新评估真实任务，不要只看模型能否启动。

若运行时缺少对应低位算子，反量化和数据搬运可能抵消收益；不能由“文件小了一半”推断“推理快一倍”。比较时固定硬件、输入输出长度分布和并发，检查质量、首Token、每步解码及端到端延迟。

## 批处理

批处理把多个请求合并在一起执行，提高硬件利用率。它适合高并发服务，但会引入排队等待。

在线交互型应用要控制等待时间；离线批量处理则可以更重视吞吐。

## 流式输出

流式输出边生成边返回，单靠传输方式不减少同一完整序列的生成计算；用户取消后若运行时支持及时停止，则可以省去后续生成。首Token仍可能受检索、排队和Prefill影响，不能用首个网络字节代替首个有效结果延迟。

对话、写作、代码生成可以先展示临时片段。JSON也可以流式传输，但未完成解析和schema校验的片段不能作为执行命令；工具调用还需完成授权和业务校验。已显示部分内容后发生失败，应标记结果未完成，不能悄悄拼接另一次重试当成同一回答。

## MoE 部署关注点

MoE 模型每次只激活部分专家，看起来推理成本低，但部署并不简单：

- 专家分布在不同设备时会产生通信成本。
- 路由不均衡会造成部分专家过载。
- 批处理需要考虑不同请求激活专家不同。
- 监控要看专家负载，而不只是整体 GPU 利用率。

MoE 的价值来自大参数容量和稀疏激活，但工程复杂度也更高。

## 上下文成本

长上下文不是免费能力。上下文越长：

- 首 token 延迟可能更高。
- KV Cache 占用更大。
- 模型更容易被噪音干扰。
- 单次请求成本更高。

更稳妥的做法是先检索、过滤、摘要，再把高质量上下文交给模型。

## 部署选型

| 场景 | 关注重点 |
| --- | --- |
| 内部问答 | 检索质量、引用来源、权限控制 |
| 代码生成 | 长上下文、工具验证、输出速度 |
| 客服对话 | 首 token 延迟、稳定口径、安全过滤 |
| 批量摘要 | 吞吐、成本、失败重试 |
| 高敏数据 | 私有化部署、审计、脱敏 |

## 总结

推理部署关注的是模型如何稳定、快速、可控地服务真实请求。KV Cache、量化、批处理、流式输出、上下文裁剪和 MoE 调度都在解决同一个问题：在效果、延迟、吞吐和成本之间取得平衡。

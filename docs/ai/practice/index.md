# AI 项目实践

项目实践把任务、数据、模型、评估、服务和反馈串成闭环。先选一个能判断结果对错的业务问题：给运营一份候选名单、把不合格产品送往复核、回答有出处的政策问题，或者创建用户确认过的工单。四类项目对应不同能力，不要求先训练模型再开发知识库或 Agent。

![从业务输出选择预测、视觉、知识库或工单助手项目](/ai/practice-project-routes.svg)

## 按目标选择项目

| 输出目标 | 项目 | 主要能力 | 验收标准 |
| --- | --- | --- | --- |
| 候选名单 | [用户流失预测](./machine-learning-project.md) | 时间快照、特征、排序和错误成本 | 未来数据不进入输入，名单规模对应运营容量 |
| 图片判定 | [产品质量分类](./vision-project.md) | 标注、迁移学习、预处理、复核 | 同一产品不跨数据集，严重缺陷单独验收 |
| 有出处的回答 | [企业知识库问答](../first-ai-app.md) | 检索、引用、拒答、访问控制 | 证据支持具体结论，无依据时说明缺口 |
| 可回读的业务记录 | [工单处理助手](./agent-project.md) | 工具、状态、权限、幂等 | 确认绑定草稿版本，超时先查结果 |

例如“退款多久到账”先做知识库查询；“请帮我提交订单 A102 的售后工单”才增加业务写入。如果规则固定、步骤清楚，先用确定性工作流，等到确实需要依据中间结果选择追问或工具时再增加 Agent。模型不需要获得整个后台的操作能力。

已有工具闭环后，如果任务需要批量查询、跨会话继续或等待远端作业，进入 [Agent 长任务：状态、恢复与验收](./long-running-agent.md)。它用订单报告贯穿步骤依赖、状态持久化、超时回查和预算停止，并提供独立进程恢复的本地实验。

## 把交付物变成可复核证据

README 应写清谁在什么时点使用输出、输入来自哪里、哪些情况停止处理。训练项目保留数据快照、切分清单、特征和模型版本；应用项目保留资料版本、工具合同和任务状态。两类项目都需要错误样例、部署配置及回退办法，不能只交一个 Notebook 或调用脚本。

以工单助手为例，评估报告里的“成功”应能对应草稿、确认版本、操作 ID 和最终工单回读。以流失预测为例，应能从某天的名单找到当时可用的特征及两周后成熟的标签。记录这些关系，才能区分模型错误、数据延迟和业务接口失败。

| 交付物 | 可复核的内容 |
| --- | --- |
| 任务与输入合同 | 候选用户、缺陷标签、可见资料或允许工具的范围 |
| 基线和改进记录 | 同一评估集、同一业务容量下，改进了什么、退化在哪里 |
| 错误样例 | 一个具体输入、实际输出、预期结果和错误发生的环节 |
| 发布与恢复说明 | 工件版本、停止条件、回滚步骤及已产生业务写入的处理方式 |

## 从最小闭环开始

知识应用可从 [LangChain 离线 RAG 示例](../applications/langchain/03-rag-from-zero.md)起步，再看[工具与工作流示例](../applications/langchain/04-tools-workflows-agents.md)。这些示例用于验证检索和路由，不等同于真实工单系统已接通。训练项目先复用[框架实践](../deep-learning/framework-practice.md)熟悉数据、训练、保存和重载，再换成有权限使用的业务数据。

第一轮先固定输入与输出，记录基线和失败例；第二轮只改一个可验证的环节；最后再增加线上流量、权限和恢复能力。具体上线门槛由业务风险决定，教学数据上的指标不直接替代生产验收。

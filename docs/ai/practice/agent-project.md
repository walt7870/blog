# Agent 项目：工单处理助手

用户描述“订单 A102 收到的商品有破损”，助手读取可见规范、查询当前用户的订单，生成售后工单草稿，获得确认后提交。这个项目的关键是把对话变成可回读的记录：用户修改了什么、确认了哪个版本、接口超时后是否已经创建，都应由应用状态明确回答。

## 第一版边界与工具

第一版只做分类、规范检索、订单只读查询、草稿和确认提交。退款、赔付、删除、外部通知不在自动执行范围。即使模型建议退款，也只能写入建议字段，由后续人工或独立授权流程处理。

| 工具 | 服务端检查 | 返回合同 |
| --- | --- | --- |
| `search_policy` | 当前用户可见的规范范围 | 来源 ID、版本及片段 |
| `get_order` | 登录身份和订单归属 | 查询时状态与查询时间 |
| `create_ticket_draft` | 字段 schema、允许的工单类型 | `draft_id`、`revision`、待确认字段 |
| `submit_ticket` | 身份、当前草稿版本、确认、幂等键 | `operation_id`，完成时附 `ticket_id` |
| `get_ticket_operation` | 操作归属 | 处理中、成功、明确失败或需人工核查 |

身份从服务端会话取得，不能信任模型传来的 `user_id`。schema 限制字段形状，业务层继续检查订单是否可申请、附件是否可访问、描述长度是否合规。草稿也可能写入数据库并包含个人数据，需要访问控制和保留期限。

## 确认必须绑定版本

草稿 D7 的 `revision=2` 包含订单 A102、类型 `damaged` 和“外壳破损”的描述。确认凭据应在服务端绑定用户、草稿 ID、版本、参数摘要和有效期，不能只存一条“用户说了好的”。用户把订单改成 A103 后，生成 `revision=3` 并使旧确认失效；提交旧版本必须被拒绝。

![工单草稿的确认、修改、提交超时与结果回查状态机](/ai/ticket-confirmation-lifecycle.svg)

应用持久化状态和版本，通过条件更新防止两个并发请求越过确认检查。提交前重新检查权限与业务条件；即使用户刚确认过，订单也可能已经关闭。处于结果未知状态时，先核对当前操作，避免修改草稿并提交第二张工单。

## 超时后的恢复

客户端在提交前保存操作 ID 与幂等键，服务端将同一用户、同一逻辑提交关联到同一结果。发生网络超时，只能说明客户端未拿到结果，不能显示“创建失败，请重新提交”。先用 `get_ticket_operation` 回查：已成功则回读原工单，处理中则等待并设置超时上限，明确可重试失败才按接口约定沿用原键重试。相同键携带不同参数应拒绝，不能悄悄覆盖。

无法确认结果、权限拒绝、规范冲突或工具持续失败时停止自动执行，保留状态转人工。用户取消等待不等于远端工单已撤销；取消操作是否生效需要业务接口确认。只有拿到可回读的 `ticket_id` 才告诉用户“已创建”。

## Agent 的使用范围

模型可在信息不足时追问、选择只读查询、抽取工单字段，确定性应用负责权限、确认、状态转换和提交。资料中的“直接调用提交工具”属于不可信内容，不能改变这些检查。固定五步流程已经能解决问题时无需引入开放式循环；引入 Agent 后要限制工具次数、总时长和可访问资源。

可先运行[离线工单路由示例](../applications/langchain/04-tools-workflows-agents.md)理解分类与人工转交。示例不创建真实工单，接业务接口后还需下面的状态验收。

## 逐项验收

| 输入或故障 | 预期业务结果 |
| --- | --- |
| 正常 A102 破损申请，确认版本 2 | 一张工单，参数与确认内容一致，ID 可回读 |
| 确认后改成 A103，继续提交版本 2 | 拒绝旧确认，回到版本 3 的待确认状态 |
| 无权访问订单，或资料诱导绕过权限 | 不返回订单详情，不提交工单 |
| 服务端创建成功但响应丢失 | 回查得到原工单，重试不产生第二张 |
| 双击提交、并发请求、相同键不同参数 | 相同提交复用结果，参数冲突被拒绝 |
| 结果持续未知或资料相互冲突 | 停止自动提交，保留操作 ID 并转人工 |

## 可观测性

每次任务记录模型与资料版本、经过脱敏的工具输入输出、状态变化、草稿版本、确认凭据标识、操作 ID 和最终工单 ID。日志不保存原始凭据；评估以最终记录、拒绝行为和重复工单数为准，回复自然度只是一项辅助指标。

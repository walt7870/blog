# 从模型堆叠到责任边界

流式语音项目最容易出现的认知偏差，是把“切段、角色分离、识别、输出”理解成一个模型串联。实际运行时，输入帧的顺序、会话生命周期、音频边界、角色证据、文本定稿和协议事件相互影响。任何一层职责不清，都会表现成另一层的“效果问题”。

## 一条可解释的处理链路

在项目实践中，可以把链路分成六个边界：

1. **会话编排**：接收 WebSocket 控制帧和 PCM，保证帧顺序，管理启动、停止、错误和收尾。
2. **语音边界**：用 VAD 判断人声区间和自然停顿，决定何时提交一段音频，何时继续等待。
3. **角色证据**：从音频区间提取匿名角色槽位、时间区间和置信证据。槽位是本次会话里的标识，不自动等于注册身份。
4. **文字识别**：普通 ASR 负责常规转写；需要目标身份或指定角色时，目标 ASR 在明确的角色区间或门控条件下工作。
5. **结果合并**：把文字、时间范围和角色证据合并成内部句子对象，决定 Preview、Final 和未知角色的语义。
6. **协议输出**：将已冻结结果映射到既有事件和字段路径，负责序列化、发送和终止事件。

## 为什么要把角色证据和目标身份判断分开

角色分离回答的是“这段声音更像哪一个会话内的角色”；目标身份识别回答的是“这段声音是否属于预先登记的目标说话人”。两者的输入、误差和失败语义不同：

| 层次 | 典型输出 | 不能直接推出的结论 |
| --- | --- | --- |
| 角色分离 | 匿名槽位、时间区间、角色切换 | 槽位就是某个真实姓名 |
| 声纹或目标身份判断 | 与登记参考的匹配结果、门控状态 | 所有非目标说话人内容都已被过滤 |
| 目标 ASR | 目标角色范围内的文字 | 角色范围外的内容一定被识别正确 |
| 协议合并 | 带角色标记的句子事件 | 文字和角色都达到了业务质量 |

因此，日志和测试报告中应分别记录 `role_slot`、`target_gate`、`text_result` 和 `final_state` 等概念。不要用“角色数正确”替代“目标身份过滤正确”，也不要用“协议字段非空”替代“文本准确”。

## 兼容旧协议的内部演进方式

当内部模型或调度策略变化时，优先保持以下稳定面：

- 外层事件名称和完成语义不变。
- 原有字段的类型、路径和缺省值保持兼容。
- 新模型的匿名角色证据先进入内部对象，再由适配层写入原有角色字段。
- 异步修订只影响尚未 Final 的结果；Final 后进入只读状态。
- 新增诊断信息可以写入内部日志或调试接口，不把调用方解析链路强制迁移到新事件。

这种做法把“模型替换”和“协议迁移”拆开，既可以更换推理后端，也不会把客户端升级变成服务端修复的前置条件。

## 排查时先问哪一层

遇到现象时，按以下顺序缩小范围：

| 现象 | 首先检查 | 不要直接归因于 |
| --- | --- | --- |
| 没有任何句子输出 | 会话准入、首帧参数、PCM 顺序、VAD 是否产生区间 | 角色模型精度 |
| 有文字但角色为空 | 角色证据生成、合并时机、协议映射 | 调用方没有消费新事件 |
| 角色数量正确但串人 | 时间区间、重叠处理、身份门控、人工标注 | 模型“已经稳定” |
| 末字缺失 | VAD 尾部、提交时机、EOF 缓存归属、Final 定稿 | WebSocket 网络抖动 |
| Final 正常但未结束 | 停止状态机、剩余缓存、terminal 发送条件 | 页面显示 |

先找到违反边界的那一层，再决定是否调整模型参数。这样能避免用一个层面的补丁掩盖另一个层面的状态错误。

## 小结

一条可靠的语音链路，应当能回答四个问题：谁接收帧、谁决定边界、谁产生证据、谁冻结并输出结果。模块名称可以变化，责任边界和可验证输出不能模糊。

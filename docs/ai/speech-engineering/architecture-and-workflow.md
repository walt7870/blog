# 端到端流程架构

流式语音服务同时处理音频、控制命令、模型任务和验证证据。只画模型调用图，通常看不出谁负责结束会话、哪一步可以修改结果、一次变更如何进入部署。因此，架构图应把数据流、控制流、状态流和证据流放在同一张图上。

![语音服务端到端流程架构](/ai/speech-engineering/voice-end-to-end-architecture.svg)

## 四条流分别解决什么问题

| 流程 | 主要对象 | 需要回答的问题 |
| --- | --- | --- |
| 数据流 | PCM、音频段、文字、角色区间 | 数据经过哪些处理，在哪一步改变形态 |
| 控制流 | start、stop、EOF、错误和重试 | 谁能改变会话状态，失败后如何收敛 |
| 状态流 | Created、Receiving、Finalizing、Closed | 哪些事件可以到达，哪些结果已经冻结 |
| 证据流 | 用例、原始事件、指标、工件摘要 | 结论如何复现，部署版本如何追溯 |

四条流不应由同一个对象隐式承担。音频处理器可以产生段完成事件，但不应该直接决定外部会话何时关闭；验证脚本可以收集事件，但不应该修改服务运行状态。

## 一次请求的时序

### 接入阶段

调用方建立长连接并发送启动参数。会话编排器先校验采样率、声道、处理模式和必要控制字段，再创建本次会话的上下文。参数不完整时，应在模型调用前返回可识别的错误，避免把输入问题误报成模型失败。

### 处理阶段

PCM 帧进入有序缓冲区后，由 VAD 产生语音区间和停顿边界。达到提交条件的音频段进入识别任务；角色证据和文字识别可以并行，但结果都必须带有段标识和时间范围，最后由合并器按顺序组装。

以会议转写为例，第一段正在识别时，第二段仍在收音，角色模块可能已经处理了覆盖两段的上下文。因此，会话对象、音频段对象和模型任务对象需要各自的生命周期。会话的 `Receiving` 不代表没有识别任务，单个段已经 Final 也不代表整场会议结束。

### 定稿阶段

合并器先产生可变的 Preview，待音频段和关联任务完成后生成 Final。Final 需要携带明确的句子标识，进入只读集合；后续诊断信息可以追加到日志，但不能静默覆盖调用方已经消费的字段。

### 收尾阶段

stop 或 EOF 到来后，会话进入 Finalizing：先提交尾部缓存，再等待 in-flight 任务，最后发送 terminal 并关闭连接。任何分支都不应绕过 Finalizing 直接发送 terminal。

## 推荐的状态机

```text
Created
  -> Receiving
  -> Draining
  -> Closed

任意阶段发生不可恢复错误 -> Failed -> Closed
```

这里的 `Draining` 表示停止接收新音频并排空已接收任务，包含前文的 Finalizing 收尾过程。段状态单独维护：`Collecting -> Sealed -> Queued -> Running -> Finalized`。会话处于 Receiving 时，可以同时存在多个不同状态的段。

状态转换由会话编排器统一执行，模型 worker 返回成功、失败或超时结果。已经接受的任务必须完成、取消或明确失败后，会话才能关闭；连接断开不代表原生推理已经停止，释放资源要以实际任务退出为准。

## 并行完成与有序发布

会议中的短句可能比前面的长句先完成。模型 worker 可以并行，但协议输出应按既有契约决定顺序。若调用方按句子序号拼接结果，就需要一个有界发布缓冲，记录已完成结果和下一条待发布序号。

不能无限等待某个失败段：到达该段截止时间后，应发布协议允许的错误或降级结果，再推进序号。降级结果必须保留未知角色、缺失文本等真实状态，不能伪造一个非零角色使协议检查通过。Preview、Final 和错误也应使用同一段标识，防止页面把两次尝试当成两句话。

| 对象 | 建议标识 | 所有权与不变量 |
| --- | --- | --- |
| 会话 | session_id、generation | 重连创建新代际；旧任务不能写入新会话 |
| 音频段 | segment_id、start_sample、end_sample | 样本范围采用半开区间，封口后不可变 |
| 模型任务 | job_id、attempt | 每次尝试独立计时；重试共用原始截止时间 |
| 输出句子 | sentence_id、revision、finalized | Final 在本协议契约内只提交一次 |

这些是设计示例字段，不代表任何既有接口。实际接入应由适配层映射，不能要求调用方为内部对象升级协议。

## 从变更到部署的流程

```text
需求或缺陷
  -> 影响面分析
  -> 小样本定向回归
  -> 完整矩阵回归
  -> 构建并生成摘要
  -> 目标环境 smoke
  -> 分阶段发布
  -> 线上只读核对
  -> 归档 manifest 与回滚点
```

每一步都有独立的停止条件：影响面不清楚时不扩大回归；定向回归失败时不构建发布包；目标环境 smoke 未通过时不切换流量。回滚点应指向经过验证的历史工件，而不是某个模糊的“上个版本”目录。

## 问题如何沿架构定位

| 观察到的现象 | 首查的流程 | 典型边界 |
| --- | --- | --- |
| 没有句子 | 控制流和数据流 | 会话准入、首帧、PCM 顺序、VAD |
| 句子有文字但无角色 | 数据流和合并状态 | 角色证据、段标识、适配层 |
| 文字或角色在 Final 后变化 | 状态流 | Final 冻结、异步回写、重复提交 |
| 停止后连接迟迟不关闭 | 控制流和收尾状态 | 尾部缓存、in-flight、terminal |
| 新版本无法在目标环境启动 | 证据流和部署流 | 工件摘要、运行时、设备映射 |

先确定现象属于哪条流，再进入对应模块。架构图的价值不在于把组件画得更多，而在于让排查入口稳定、让变更影响可计算。

## 小结

流式语音系统应把“数据怎么走”“状态怎么变”“控制谁负责”和“证据如何留下”同时设计。模型可以替换，四条流之间的边界和状态收敛规则应保持清晰。

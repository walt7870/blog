# 从代码变更到部署交接

私有化语音项目的部署对象不只有镜像。部署方接收的是一组相互约束的内容：源码版本、模型与运行时、硬件基线、启动参数、协议文档、授权文件、校验摘要和验证结论。任何一项脱离其他项单独流转，接手者都很难判断“这个包为什么能在目标环境运行”。

## 先锁定目标环境基线

部署前把硬件和软件组合写成不可歧义的基线：

| 类别 | 应记录的内容 |
| --- | --- |
| 硬件 | 芯片型号、物理设备编号、容器内逻辑设备映射 |
| 驱动 | 驱动版本、固件版本、加速库版本 |
| 系统 | 操作系统发行版、内核和 CPU 架构 |
| 容器 | Docker/Podman 版本、运行时、共享内存和只读约束 |
| 服务 | 镜像摘要、源码提交、启动参数、监听协议和路径 |
| 模型 | 模型摘要、加载位置、精度或格式、设备占用 |

“在本机通过”只能说明本机组合可运行，不能替代目标环境验证。设备映射、驱动兼容和只读根目录等差异，往往会在首次启动或重启时才暴露。

## 按变更类型选择部署路径

把每次部署先分流，可以避免重复构建，也能防止文档修订误触发模型和镜像变更：

| 变更类型 | 需要重新验证的内容 | 适合的路径 |
| --- | --- | --- |
| 代码、模型、镜像或授权变化 | 构建、启动、功能回归、专项回归、摘要和部署包 | 完整部署 |
| 只改操作手册、接口文档或附件 | 工件摘要不变、文档内容、ZIP 编码和包内校验 | 文档/附件修订 |
| 只改通知文案或排版 | 草稿内容和附件引用 | 通知修订 |

分流记录应写入当次 manifest，避免同事看到一个新日期就误以为镜像已经重建。

## 工件和证据绑定

推荐让以下对象都指向同一份 manifest：

```text
源码提交 ─┐
模型摘要 ─┼─> manifest.json ─> 验证报告
环境基线 ─┤                    ├─> 镜像 SHA-256
启动参数 ─┘                    └─> 部署附件 ZIP SHA-256
```

部署包中保留：

- 操作手册和当前接口文档。
- 镜像或外部镜像下载信息及其 SHA-256。
- 校验脚本和校验结果示例。
- 授权文件和公钥（按项目的安全规则提供）。
- 本次变更摘要和验证范围。

临时下载链接、凭据和内部原音不进入长期知识库或公共文章。链接失效后，应根据 manifest 和对象摘要重新生成，而不是修改历史摘要。

## 接手文档的最小内容

一份能真正帮助接手者的文档，至少回答：

1. 代码在哪个仓库、哪个分支，当前提交是什么。
2. 当前链路启用了哪些后端，哪些是历史或兼容分支。
3. 既有协议的稳定字段和不能改变的行为是什么。
4. 如何启动、如何检查实际监听进程和镜像摘要。
5. 最小 smoke、专项回归和完整交付验证分别怎么跑。
6. 当前结论的证据根在哪里，哪些结论仍然需要现场复核。
7. 出现问题时，如何回滚到上一个可验证工件。

接手文档要区分“事实”“推断”和“待现场复核”。目录名、旧报告和历史镜像标签都不能直接当作线上状态。

## 部署前质量门

在生成部署包之前，至少检查：

- 协议事件顺序、Final 冻结和 terminal 行为通过。
- 目标环境启动、重启和设备映射通过。
- 质量回归覆盖本次变更影响的样本矩阵。
- 镜像、压缩包和关键文件摘要已记录并可回读。
- 包内中文文件名、脚本参数和文档路径在目标环境可用。
- 验证报告清楚区分通过、未通过和未验证。

任何一项证据不足，都应缩小交付范围或标记为待验证，而不是用另一项通过结果替代。

## 小结

部署的核心是可追溯和可复核：同一份 manifest 连接代码、环境、工件和结论；接手者能按文档复现关键检查；部署方拿到的包能验证自己运行的确实是被验收过的版本。

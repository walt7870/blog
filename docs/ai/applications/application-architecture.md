# AI 应用架构

AI 应用架构的关键，是把不确定的模型输出放在可验证、可限制、可恢复的系统中。模型适合做语义理解和候选生成，程序负责权限、事务、状态和最终约束。

## 一条生产请求

![退款助手的一次请求与动作边界](/ai/ai-application-architecture.svg)

用户问“我的退款到账了吗”，应用先确认身份和订单归属，再分别查询退款政策与支付系统的退款记录。政策解释预计时限，业务 API 提供该笔退款的真实状态；不能用“通常3–5个工作日”推断这笔退款已到账。

模型拿到最少必要的查询结果后组织说明，应用检查引用、退款状态与输出字段。若用户进一步要求催办，则进入独立动作网关，重新校验权限、确认和幂等键，创建后回读工单 ID。上下文里出现“已催办”字样不能替代业务写入结果。

## 上下文构建

上下文可能包含：

- 当前用户输入和必要的对话历史。
- 用户权限和业务状态。
- 检索到的资料及来源。
- 工具返回的结构化结果。
- 输出格式和流程规则。

上下文应按任务动态构建。无关历史、重复规则和完整数据库结果会增加成本并干扰模型。

## 状态管理

对话历史不等于业务状态。订单是否支付、工单是否创建、审批是否完成，应来自业务数据库；模型生成的文字不能作为事实来源。

多步骤任务需要显式记录：

- 当前目标和阶段。
- 已执行工具及结果。
- 待确认动作。
- 重试次数和停止原因。
- 可恢复的检查点。

持久化检查点保存的是执行进度，不与外部业务数据库自动形成事务。节点重放时可能再次调用工具：例如创建工单的响应丢失，恢复后应按同一幂等键查询或重试，不能换一个键再创建。状态里保留 `pending/confirmed/unknown` 等结果类别，比仅保存一段模型对话更容易恢复。

## 失败分类

| 失败层 | 示例 | 处理 |
| --- | --- | --- |
| 输入 | 缺少订单号 | 追问或提示格式 |
| 权限 | 用户无权查询 | 拒绝并审计 |
| 检索 | 没找到可信资料 | 拒答或转人工 |
| 模型 | 格式错误、内容不完整 | 校验、有限重试或降级 |
| 工具 | 超时、参数错、业务冲突 | 分类错误并按规则处理 |
| 下游 | 消息或存储失败 | 幂等重试和补偿 |

## 确定性边界

以下逻辑应由程序控制：

- 身份认证和数据权限。
- 金额、库存、事务和状态流转。
- 写操作确认和幂等。
- 法律、合规和硬性业务规则。
- 结果 schema 和字段校验。

模型可以解释用户意图、生成候选参数和组织说明，但不能成为这些规则的唯一执行者。

## 缓存与成本

可缓存内容包括稳定 Embedding、公共检索结果和重复前缀。低温度分类也不天然确定；若缓存模型结果，键应包含模型、模板、输入和相关策略版本。公共政策可按文档版本缓存，个人退款状态则必须隔离用户与租户，并采用业务允许的有效期，不能让旧缓存替代当前状态校验。

## 验收一次失败恢复

为同一请求模拟三种情形：政策未命中时回答资料不足；查单 API 超时时明确状态暂不可确认；创建工单成功但响应丢失时，使用原幂等键回读。检查业务表中只有一张工单，日志能串联请求 ID、模型版本和工具结果，且没有记录密钥或完整客户文本。这比只验证模型能返回一句退款说明更接近上线要求。

## 版本

一次输出由模型、Prompt、上下文模板、索引、工具 schema 和业务代码共同决定。它们都要进入版本记录，才能复现问题并安全回滚。

架构成熟度不取决于组件数量，而取决于每一步是否有明确责任、失败处理和验证闭环。

# 嵌入式开发

环境监测节点每隔 15 分钟醒来，读取温湿度、发送数据，再回到休眠。看似只有几步，实际会跨过电源、传感器、总线、任务调度、网络与固件升级。程序打印“发送成功”，可能只表示数据进了发送队列；休眠函数已经执行，整板也可能仍被电源指示灯消耗着数毫安。

嵌入式开发把软件行为落实到物理设备，关注的不只是计算结果，还包括响应时间、电气条件、资源寿命与异常恢复。目标可以是运行裸机或 RTOS 的 MCU，也可以是运行 Linux 的 SoC，不能用“都只有几 KB 内存”概括整个领域。

## 从什么问题进入

| 当前问题 | 阅读入口 | 需要带走的判断 |
| --- | --- | --- |
| 接线后没有响应，担心电平不匹配 | [电子电路基础](./electronics.md) | 电源、回流、输入阈值与驱动电流是否满足规格 |
| 不知道芯片是否够用 | [微控制器](./mcu.md)、[硬件设计](./hardware-design.md) | 引脚复用、内存、时钟、功耗和供应是否同时成立 |
| 编译成功但程序不启动 | [C 编程](./c-programming.md)、[工具链](./toolchain.md) | 向量表、链接地址、启动初始化和目标 ABI 是否匹配 |
| 传感器偶发读错或 DMA 数据异常 | [外设驱动](./peripherals.md) | 总线时序、缓冲区归属、完成通知与错误恢复 |
| 联网时控制任务响应变差 | [RTOS](./rtos.md)、[通信协议](./communication.md) | 阻塞、队列、优先级与协议确认的实际含义 |
| 需要网关、升级或电池寿命评估 | [Linux](./linux-embedded.md)、[项目案例](./projects.md) | 系统边界、掉电一致性与可测量的功耗预算 |
| 要在具体开发板上落地 | [平台实战](./platforms.md)、[能力进阶](./career.md) | 固定工程输入，用复现和验证证据确认能力 |

## 用三个交付物组织学习

第一步做一个能重复启动的采集板：使用带正规文档和调试接口的开发板，先验证供电、串口和一种传感器。记录板号、芯片完整料号、固件提交、串口参数与采集周期。能连续运行并解释故障，比同时接十个模块更有价值。

第二步把采集和上报拆开。拔掉网线或关闭接入点时，采集仍按周期执行；发送队列有容量上限，满了以后按业务选择丢弃旧采样、落盘或降低采样频率。不要让无限重连阻塞控制任务。RTOS 是实现隔离的一种手段，简单的非阻塞状态机也可以满足需求。

第三步处理现场恢复：在下载中、写入中和首次启动时分别断电，证明设备还能进入可恢复状态；测量完整采集周期的电流积分，核对低温和弱网下的预算。原型“动起来”与产品能长期维护是不同的验收范围。

## 开发板如何选择

| 方向 | 可考虑的平台 | 购买前核对 |
| --- | --- | --- |
| 学习 Cortex-M 与有线外设 | STM32 Nucleo / Discovery | 完整板号、调试器、原理图和目标外设引脚 |
| Wi-Fi 或 BLE 节点 | ESP32-C3 / S3 开发板 | 具体芯片无线能力、SDK 目标、天线和峰值供电 |
| 电池传感器 | 低功耗 STM32 / Nordic 开发板 | 调试器、稳压器和 LED 能否隔离测量 |
| Linux 网关 | 树莓派或有完整 BSP 的 SoC 板 | 镜像、内核支持、串口、存储寿命和供电 |

不要按开发板售价推算产品 BOM，也不要把 CPU 架构当作外设兼容承诺。相同内核的芯片仍可能有不同寄存器、启动映射、DMA 可访问内存和勘误。关于工程方法与协作，可继续阅读[开发方式](/docs/design/develop-pattern/)；本专题重点解释设备内部如何运行及如何验证。

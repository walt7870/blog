# 职业发展与进阶

嵌入式能力可以通过独立交付和故障定位来验证。会调用传感器 API，与能解释偶发 NAK、证明恢复不丢数据，是不同的能力；工作年限不能直接换算成熟度。本页用可检查的产物组织进阶路径。

![从单模块验证到系统决策的证据链](/embedded/engineering-capability-path.svg)

## 选择一个主方向

| 方向 | 日常对象 | 适合展示的成果 |
| --- | --- | --- |
| MCU 应用与驱动 | 中断、DMA、外设、RTOS | 完整驱动、时序测量、溢出与恢复测试 |
| Linux BSP 与系统 | 启动链、设备树、内核、根文件系统 | 固定构建、板级支持、启动与更新恢复 |
| IoT 与设备安全 | 配网、协议、身份、OTA | 断网恢复、命令去重、密钥与升级信任链 |
| 控制与机器人 | 采样、反馈、执行器与截止期 | 响应曲线、过载降级、失效停止 |
| 硬件与验证 | 原理图、PCB、电源、信号与测试 | 约束表、测量记录、首板问题闭环 |

先在一个方向建立深度，再扩展相邻边界。FPGA、射频、功能安全等有各自方法，不能因为“都是嵌入式”就把工具熟悉程度当作相同能力。

## 分阶段的达成标志

模块阶段应能在新板上重建工程，确认电源、时钟与引脚，完成一个有错误返回的传感器驱动。提交不仅有 `main.c`，还包括目标料号、工具链、接线、测试输入、预期波形与恢复步骤。故障时能够区分没有供电、地址错误、时序不满足和解析错误。

系统阶段应能给出任务与队列上限、最坏响应预算、内存归属和持久化边界。通信断开不阻塞关键控制，队列满不会无限增长，关键任务停止能被监督器发现。OTA 的试启动与数据迁移要有失败注入证据，不能只展示成功演示视频。

方案阶段应能比较不同芯片/系统的总成本、功耗、长期支持与供应风险，写明采用方案和拒绝方案的依据。需要功能安全时，能区分安全机制、工具/组件认证与产品整体论证，明确具体版本与证书适用范围。技术决策应允许后续按实测推翻，而不是只列技术名词。

## 把故障转为可复用实践

例如设备每次无线发送后偶发重启，不要只记录“换了电容”。先保存板号、固件、复位原因与复现条件，抓供电电压和发射时刻，排除栈溢出与看门狗；再比较电源能力、布线和电池内阻。修复后用原条件、低电压和温度边界重测，记录还未覆盖的条件。

一份完整案例应连起来解释触发场景、证据、根因、取舍、失败反例与验收范围。公开时去掉客户身份和秘密，但保留因果链、单位、版本与约束，否则经验会退化成“注意稳定性”的空话。

## 代码、测试与开源协作

协议解析和控制逻辑可以在主机验证，驱动与调度需要目标板，系统可靠性还需长时与故障注入。把测试层次写清，不把主机测试数当作硬件可靠性指标。读 FreeRTOS、Zephyr、RT-Thread 或 Linux 子系统源码时，从实际调用链切入，跟踪一次数据到达和错误返回，比单纯按文件顺序通读更容易建立模型。

开源贡献可从可复现的问题、测试和文档修正开始，再提交驱动或机制改进。遵循目标项目的版本、许可和评审要求，只公开有权分享的代码与数据。作品集可以展示原始波形、真实界面与有范围的验证结果，保留构建与复现实验入口。

# Rust 发展历程

Rust从Graydon Hoare发起的个人项目发展为社区协作的系统语言，Mozilla早期提供支持。它持续围绕资源控制、内存安全、并发约束和工具链改进演进；理解这段历史有助于区分语言保证、发布通道与Edition。

![Rust稳定发布与Edition关键节点](/rust/stability-timeline.svg)

## 从实验到稳定

| 时间 | 节点 | 对工程的含义 |
| --- | --- | --- |
| 2006年前后 | 个人项目起步 | 探索系统语言的安全与资源控制 |
| 2009—2010 | Mozilla支持并逐步公开 | 在浏览器等复杂系统中验证设计 |
| 2015-05-15 | Rust1.0发布 | 进入稳定兼容承诺阶段 |
| 2018-12-06 | Rust1.31与2018 Edition | 新Edition逐步整理模块与语言规则 |
| 2021-10-21 | Rust1.56与2021 Edition | 通过迁移机制继续调整语义 |
| 2025-02-20 | Rust1.85与2024 Edition | 年份名称与实际发布日期并不相同 |

2018 Edition引入了异步关键字相关基础，但`async/await`直到Rust1.39才稳定，不能把两者写成同一次发布。相同地，“2024 Edition”是语言规则集合的名称，不能推断它在2024年就已随稳定编译器正式可用。

## 编译器、Edition与MSRV

一个依赖图可以包含不同Edition的crate。编译器版本决定支持哪些语法和API，Edition选择该crate采用哪组兼容规则，`rust-version`声明最低支持的Rust版本。三者需要分别核对。

```toml
[package]
name = "order-core"
version = "0.1.0"
edition = "2024"
rust-version = "1.85"
```

这个声明要求至少能支持2024 Edition的工具链，但不证明全部依赖和代码都能在1.85运行；CI仍需用MSRV与当前固定工具链分别验证。新引入的标准库API可能再次提高最低要求。

## 发布通道与迁移

Stable用于依赖已稳定能力的项目；Beta用于提前发现下一版兼容问题；Nightly提供实验性特性与工具。Rust通常约六周发布一次稳定版，项目不应因“跟随stable”就省略升级回归。

升级编译器与迁移Edition可以分开进行。先固定版本、运行旧Edition测试，再在独立分支评估`cargo fix --edition`、审查差异、修改清单并重跑测试。自动修改处理的是可机械迁移部分，外部宏、FFI、安全假设与平台支持仍需人工确认。

## 治理与长期维护

Rust项目团队通过公开设计、RFC与实现流程推进语言；Rust Foundation提供资金、法律与基础设施等支持。基金会、语言团队和具体crate维护者的职责不同，采用某个crate仍需核对其维护状态、许可证与平台支持。

对维护者更有用的历史经验，是区分“稳定承诺”与“无需验证”：工具诊断、依赖最低版本、目标平台和安全默认值都会继续变化。具体升级步骤见[工具链与工程实践](./tooling.md)。

# Rust 的优势与代价

Rust的价值应放在具体失败方式中评估。例如日志解析器接收不可信字节，开发者既希望避免越界和释放后使用，又需要控制分配、超时和输入规模。Rust能用安全接口帮助前一类问题，后一类仍依赖算法和资源预算。

![Rust语言保证、运行时成本与验收边界](/rust/safety-boundaries.svg)

## 内存安全的范围

安全Rust配合正确实现的底层库，可以阻止许多悬垂引用、重复释放和数据竞争。`unsafe`代码、FFI与有缺陷的底层实现需要单独审查；编译器不会自动证明原始指针来自有效内存。

没有通用GC不等于不分配、不泄漏或不暂停。`Box`分配堆内存，`Arc`维护原子引用计数，`Mutex`可能等待；引用计数环和主动遗忘资源仍会泄漏，进程终止也不保证执行析构。RAII适合正常作用域退出时释放文件和锁，持久化结果仍需显式处理写入与同步错误。

## 性能与抽象

泛型常通过单态化生成具体实现，迭代器可被优化成循环；实际结果取决于优化器、数据布局和调用方式。动态Trait对象会引入间接调用，过多单态化也可能增加二进制体积与编译时间。

评价一个解析器时，先固定输入规模、错误比例、目标CPU和构建profile，再比较吞吐、尾延迟、分配次数和内存峰值。不能因为换了语言就承诺比原实现快，更不能用debug与release的差异当作语言收益。

## 并发与错误

`Send/Sync`约束跨线程移动和共享，减少底层数据竞争；它们不会判断订单是否重复扣款。两个线程先读取库存再分别扣减，即使每一步加锁，也可能出现业务竞态，需要把检查与更新放在同一事务或临界区。

`Result`使可恢复错误出现在类型中，`?`传播失败；忽略`Result`默认通常产生`must_use`警告，并非所有情况都无法编译。代码审查与CI要确认错误得到处理，而不是用`let _ =`把警告静音后当作成功。

## 工程与分发

Cargo、rustfmt、Clippy、rustdoc提供统一入口，减少自定义构建约定，但依赖的`build.rs`和过程宏仍会在构建机执行。锁文件固定解析图，不能替代工具链、系统库、编译目标和供应链审查。

原生二进制便于CLI分发，但不自动跨系统运行。Linux目标可能依赖glibc版本、OpenSSL或CPU指令，Windows和macOS还涉及运行库、签名与平台权限；交叉编译成功后仍要在目标环境验证。

## 采用方式

| 试点 | 验证内容 | 不合适时的判断 |
| --- | --- | --- |
| 独立CLI | 错误输出、退出码、文件边界、目标机运行 | 部署依赖或维护成本超过收益 |
| 协议解析模块 | 畸形输入、规模上限、模糊测试 | 算法复杂度或FFI边界未解决 |
| 服务热点 | 相同负载下的延迟、内存、取消与恢复 | 瓶颈仍在外部数据库或网络 |

先以稳定接口引入一个边界清晰的模块，保留原实现回归与回退，再决定是否扩大。语言学习、编译耗时、库成熟度和团队排错能力都是实际成本，见[项目实战](./project-practice.md)与[生态选型](./ecosystem.md)。

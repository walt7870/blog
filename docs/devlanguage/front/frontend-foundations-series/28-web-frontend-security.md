# Web 前端安全：输入、会话、浏览器策略与构建

商品名称进入文本节点时只是内容，进入未经处理的 HTML 或脚本上下文时就可能改变页面行为。安全边界要跟着数据和权限走：页面输入、会话请求、第三方资源、构建安装各有不同的执行位置。

## 内容先判断用途，再选择写入方式

纯商品名称使用 `textContent` 或框架的默认文本插值。下面的尖括号应按字面显示，不生成 em 元素。

```html
<p id="name"></p>
<script>
document.querySelector("#name").textContent = "<em>茶杯</em>";
</script>
```

确实需要富文本时，使用维护中的清洗库并限定允许标签、属性和协议；服务端和客户端处理规则要匹配。HTML 转义、URL 协议校验与脚本字符串安全不是同一件事，把一种“转义函数”到处套用会漏掉上下文。

框架默认插值不能保护所有逃生入口，例如直接注入 HTML、危险链接或第三方组件。接口响应和数据库内容同样可能是不可信输入，不能因为它来自自己的 API 就跳过边界检查。

## XSS 与 CSRF 利用的条件不同

XSS 让不可信脚本在站点上下文运行，可能读取可访问数据或代用户发动作。HttpOnly 可以阻止脚本直接读取相应 Cookie，却不能阻止已运行的脚本通过浏览器发送带会话的请求。

CSRF 利用浏览器自动携带的身份，诱导跨站请求。服务端写接口应结合会话、CSRF token、Origin等来源检查及业务权限处理；不能用 GET 执行修改。SameSite 限制的是“站”维度，和同源不是同一概念，同站不同子域仍需按实际信任边界判断。

CORS 主要限制脚本读取跨源响应，也会对部分请求预检；简单跨源请求仍可能到达服务端。因此“没有开放CORS”不能当成完整的 CSRF 防护。敏感写入的最终授权和防伪造检查必须在服务端发生。

## CSP需要与真实页面资源匹配

下面是只使用同源外部脚本、外部样式及资源的简单静态应用响应头示例，不能原样套到存在内联脚本、外部字体或跨源接口的页面。

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
```

浏览器会阻止不符合策略的脚本和资源。若确有内联内容，可以使用匹配内容的 hash，或由服务器为每份响应生成不可预测 nonce，并同步到许可脚本；不能把固定 nonce 写成全站常量。frame-ancestors 需要通过响应头发送，不能指望 meta 覆盖所有头部指令。

先用 Report-Only 观察再收紧是常见部署路径，但 Report-Only 不会真正阻止执行。不要为了消除报错直接加入宽泛的 unsafe-inline 或任意来源。CSP 是补充防线，不能代替正确的文本处理、清洗和权限判断。

## 凭据位置与会话生命周期一起设计

Secure、HttpOnly 和 SameSite 各有职责；还需考虑域、路径、过期、退出撤销与刷新策略。localStorage 中的令牌可被同源脚本读取；内存令牌在刷新后丢失；Cookie 会受自动携带和 CSRF 约束。没有一种存放位置能单独解决全部威胁。

日志与前端监控不应记录完整令牌、Cookie、密码、原始表单和带敏感查询参数的 URL。浏览器构建变量是用户可读取的数据，密钥应留在服务端受控调用边界。

## 依赖在构建机上也拥有执行机会

依赖包安装脚本可以运行在开发机或 CI，第三方脚本则可能在浏览器以页面权限运行。审查新增依赖、锁文件变化、生命周期脚本和发布来源，给 CI 最小权限并避免把发布凭据暴露给不受信任的构建。

锁文件完整性证明下载内容与记录一致，不证明内容无恶意。漏洞扫描覆盖已知风险，不能代替版本审查、使用路径分析和运行隔离。

## 按失效边界验收

在独立测试页验证尖括号被当文本；通过响应头测试 CSP 允许的同源外部脚本与被阻止的内联脚本；检查登录写接口缺少 token、来源不符、身份无权限时确实失败。涉及会话的测试只能在受控环境使用测试账号与数据。

若页面出现 CSP 违规，先定位具体指令和资源，再决定调整资源或策略；若跨源请求失败，区分浏览器读权限与服务端是否已经执行。安全结果应写清验证范围，不能把控制台没有报错当成完整安全验收。

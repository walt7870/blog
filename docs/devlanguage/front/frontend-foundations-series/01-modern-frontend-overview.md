# 现代前端技术全景：Web 平台、工程化与框架生态

做一个商品详情页，需要显示商品、适配手机、处理“加入购物车”，还要能构建和上线。这些工作发生在不同环境：开发机运行 Node.js 和构建工具，浏览器运行下载到的页面代码，服务端保存价格、库存和订单。先分清这些位置，才容易判断一个工具解决哪类问题。

![前端开发构建与用户运行的边界](/front/frontend-foundations-series/ep01-flow.svg)

## 开发机产生什么，浏览器运行什么

开发者编辑组件、TypeScript 和 CSS，包管理器按锁文件安装依赖，构建工具转换代码并输出 HTML、CSS、JavaScript 和资源文件。类型检查、Lint 和测试提供不同反馈；不能因为构建成功就认定类型和业务都正确。例如 Vite 的常规 TypeScript 转换会擦除类型，类型检查需要独立执行。

部署后，浏览器通过 URL 获取产物。静态站点可由 CDN 或 Web 服务器提供文件；SSR 应用还需要服务端在请求时生成 HTML。浏览器不会自动运行开发机的 npm 命令，也不会理解尚未转换的任意框架源码。Node.js 既可以是开发工具宿主，也可以是 SSR 服务宿主，要按实际进程判断职责。

## 一个商品页中的责任分配

HTML 定义商品标题、价格、图片与按钮。CSS 决定商品图和购买区的排列、窄屏换行和焦点样式。JavaScript 监听按钮、发送购物车请求并显示成功或失败。DOM、事件和 Fetch 属于浏览器提供的 Web API，JavaScript 通过它们操作页面和网络。

框架把这套交互组织为组件和状态更新。例如库存从 1 变为 0 后，商品组件显示“暂时缺货”。这不意味着框架拥有最终库存：真正加入购物车或下单时，服务端仍要校验商品、价格、权限和库存。浏览器里的禁用按钮只改善交互，不能建立业务授权。

## 工具增加在哪一层

TypeScript 约束开发时的数据使用方式，运行时的接口响应仍需要校验。组件框架减少手动同步 DOM 的负担，但不能替代语义 HTML 和键盘操作。SSR 可以提前生成内容，但后续交互还可能需要浏览器加载脚本并完成 hydration。每增加一项技术，都应明确它改变的输入、产物和运行位置。

小型说明页可以直接使用 HTML、CSS 和少量脚本；有筛选、编辑、权限和多页面协作的后台，组件、路由、测试和统一数据层更有价值。选型以交互复杂度、团队经验和部署约束为依据，不要求所有页面拥有同一套重型工具。

## 用实际故障验证全景

如果“加入购物车”一直转圈，先在 Network 确认是否发出请求，再检查状态码与响应合同。如果响应已经成功，检查脚本是否抛错、状态是否更新、DOM 是否被样式遮住。若线上请求仍指向本机地址，再回到构建配置和产物查环境变量。这样每一步都对应明确环境，而不是在浏览器、框架和服务器之间反复猜测。

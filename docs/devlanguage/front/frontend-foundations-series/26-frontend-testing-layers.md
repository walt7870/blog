# 前端测试分层：每种证据能覆盖什么

商品编辑提交后出现绿色“成功”，并不能证明数据库已经保存。测试必须明确真实运行了哪些组件、替换了哪些服务、最终检查了什么。分层是为了让错误在合适位置被发现，不是给所有项目凑齐固定数量的测试。

![同一商品保存需求在不同范围中的验证](/front/frontend-foundations-series/ep26-flow.svg)

## 用同一需求划分验证范围

| 范围 | 商品编辑的断言 | 主要局限 |
| --- | --- | --- |
| 单元 | 页码解析、金额单位、草稿校验 | 不证明组件绑定正确 |
| 组件 | 输入、点击、禁用、错误与焦点 | 取决于DOM环境和替代依赖 |
| 集成 | 路由ID、查询缓存、保存服务共同运行 | 被mock的接口不能证明服务端实现 |
| 端到端 | 受控完整环境登录、编辑、刷新后回读 | 成本和环境依赖较高 |
| 视觉回归 | 固定数据与字体下明暗、窄屏差异 | 不能证明动作和数据正确 |

组件测试可以运行在真实浏览器，不必一定更轻；端到端测试也可能替换第三方支付等边界。名称本身不够，报告中应说明执行范围。布局、焦点和浏览器安全行为不要仅凭模拟 DOM 判断。

## 让断言针对业务合同

下面使用 Node 内置测试，假设 `readPage` 来自 [应用架构](./25-frontend-application-architecture) 的 `route.js`，项目已启用 ESM。运行 `node --test route.test.js`。

```js
// route.test.js
import test from "node:test";
import assert from "node:assert/strict";
import { readPage } from "./route.js";

test("缺省页与合法页", () => {
  assert.equal(readPage("/products"), 1);
  assert.equal(readPage("/products?page=2"), 2);
});
test("拒绝部分数字、负值与不安全整数", () => {
  for (const value of ["2abc", "-1", "0", "1.5", "9007199254740992"]) {
    assert.equal(readPage("/products?page=" + value), 1);
  }
});
```

若把实现改成 `parseInt(value)`，2abc 会被当成2，此测试就应失败。这比只检查函数被调用一次更接近需求。断言不能只是复制实现公式；要来自约定的输入与结果。

## 组件测试观察用户能感知的变化

名称为空时提交应显示错误、关联字段并把焦点放到输入；输入修正后错误消失；提交过程中按钮状态正确，失败后保留输入并能再试。优先按角色、名称和标签定位，减少依赖内部类名和节点层级。

对异步结果等待明确条件，例如状态从“保存中”变为“已保存”，不依赖固定两秒暂停。时间、随机数和网络延迟可以在夹具中控制；如果用假的响应，明确它只验证组件面对这种响应的行为。

原生事件、焦点和表单校验有浏览器语义；用脚本直接调用处理函数不能证明键盘用户能完成流程。真实浏览器测试也要确认实际布局宽度，不能只相信配置请求了某个手机尺寸。

## 集成验证连接处，端到端验证落地结果

集成测试让商品路由、数据层、表单和提交逻辑共同运行，故意安排旧请求较慢、保存返回412或后台刷新，检查没有串资源、覆盖草稿或丢失冲突提示。

端到端路径应在专用测试环境使用可清理数据：创建测试商品，进入编辑页，提交名称，刷新或重新进入后回读服务端结果。若只是拦截请求并返回成功，得到的是前端流程证据，不能宣称真实持久化通过。支付、短信等外部动作要使用对应沙箱和受控替代。

## 视觉回归要审查基线

固定字体、浏览器、数据、主题与实际视口，等待图片完成，控制动画和时间内容，再保存基线。截图差异需要人工判断是预期设计变化还是回归，不能出现差异就自动更新基线。

除了整页截图，还需查看长标题、表格、错误文本、图示放大和固定工具栏等局部。截图不明显的横向溢出可用实际布局宽度与 scrollWidth 辅助断言；颜色对比、读屏名称和键盘顺序仍需另行验证。

## 失败要能复现，成功要有范围

一次 CI 失败应保存输入、版本、失败步骤、控制台或网络证据；重试只能帮助识别波动，不能把重试成功当成根因已解决。覆盖率用于发现遗漏，不宜作为“全部正确”的单一门槛。

优先覆盖高风险合同、真实故障回归和关键路径。修复后至少证明原始反例失败、新实现通过，避免只为改动后的代码补一组永远绿色的断言。完整工具入口见 [质量工具链](./21-frontend-quality-toolchain)，专题实践见 [测试策略](../testing/)。

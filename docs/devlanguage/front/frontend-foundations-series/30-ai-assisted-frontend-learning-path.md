# AI 辅助前端工程：任务合同、验证与学习路线

让 AI “做一个商品编辑页”，容易得到外观完整却缺少权限、错误恢复和状态边界的页面。把需求拆成可观察的行为，给出现有代码与运行入口，才能判断生成结果是否适合项目。

![从任务合同到代码、验证和可追踪交付](/front/frontend-foundations-series/ep30-flow.svg)

## 先说清任务与现有边界

以给商品列表增加名称筛选为例，任务不只是出现一个输入框。需要明确筛选发生在本地还是服务器、状态是否进入 URL、翻页如何重置、无结果如何显示，以及请求失败后能否保留条件。

下面的任务记录可以和代码一起审查，路径应替换为项目真实入口，不能只把它当一段通用提示词。

```text
目标：商品列表支持名称筛选，刷新和后退能恢复条件。
现状：沿用现有路由、查询层、组件库和测试入口。
行为：
- 条件写入URL；改变条件时回到第1页。
- 旧请求晚返回时不能覆盖新结果。
- 加载、无结果、失败和重新尝试都有明确反馈。
- 键盘可完成输入与提交，错误不清空条件。
验收：
- 已有检查通过，新增行为用例覆盖竞态和URL恢复。
- 按实际布局宽度检查桌面与窄屏，查看明暗截图。
- 说明执行命令、验证范围和仍依赖的真实接口合同。
```

上下文应包括真实 package.json、锁文件、相关路由和组件示例、接口数据形状及现有失败记录。只提供截图不能推导真实字段和权限；给整个仓库的所有文件也不等于有效上下文，重点是让相关依赖和约束可定位。

## 按风险选择协作方式

| 工作 | 合适的协作范围 | 验收重点 |
| --- | --- | --- |
| 探索交互原型 | 快速生成多个候选并实际体验 | 不把假数据演示当正式接口 |
| 现有页面小改 | 先读相关链路，再限定文件修改 | 回归原行为和局部可恢复状态 |
| 跨路由、数据层改造 | 先写任务合同与分步计划 | 迁移顺序、兼容和每步证据 |
| 反复安装、运行和排错 | Agent按受控工具执行 | 命令范围、依赖变更与真实退出结果 |
| 发布和权限变更 | 受控交付流程 | 目标环境、版本、回滚及授权边界 |

Vibe Coding、规范驱动和 Agentic Coding 描述的是不同协作维度，可以组合使用。原型阶段强调探索，正式改造增加合同和验证，代理执行重复任务；不是选中一个名字后就不再需要工程判断。完整分类见 [开发方法](../../../design/develop-pattern/) 与 [AI编程实践](../../../ai/vibe-coding/)。

## 让证据覆盖生成代码容易遗漏的部分

类型检查发现类型关系问题，运行时校验发现错误 JSON，行为测试检查状态变化，真实浏览器检查键盘、布局、焦点与资源。它们不会自动互相代替。生成代码和生成测试还可能共享同一错误假设，应从业务合同独立构造反例。

例如筛选框看似正常，旧响应却覆盖了新列表；测试若始终同步返回，就发现不了问题。安排“第一次请求慢、第二次快”，断言最后只显示第二组结果，才覆盖了实际风险。

对 AI 的解释也要验证：不存在的配置项、过时框架 API、从未执行的命令和读取不到的文件，都不能成为完成依据。审查最终 diff、依赖增删、资源路径和构建产物，记录通过与未验证的具体范围。

## 学习围绕能完成的任务推进

| 阶段 | 实际任务 | 达成标志 |
| --- | --- | --- |
| Web平台 | 语义表单与响应式商品卡 | 能用键盘操作，并解释层叠与布局 |
| 浏览器机制 | 请求列表、取消与本地偏好 | 能定位HTTP、解析、竞态和存储失败 |
| 工程化 | TS、依赖和Vite构建 | 能区分检查、转换、运行与部署产物 |
| 组件与应用 | 路由、共享数量与编辑草稿 | 能解释状态归属和冲突恢复 |
| 交付 | 测试、性能、安全与发布 | 能从实际证据定位并回滚一次回归 |

AI 可以解释陌生代码、补夹具、比较方案和做机械迁移，但每完成一项都应能独立说明输入、状态和失败方式。若连错误发生在浏览器还是构建机都分不清，先回到对应基础实验，比继续生成更多代码有效。

## 把一次改动交付完整

一个可审查的结果应包含实际修改、可运行入口、必要图示、验证命令和范围、失败恢复及版本标识。需要真实服务才能确认的行为，单独保留为待验，不把受控夹具冒充生产验收。

从 [系列导读](./) 选择尚不能独立解释的环节，再用同一商品业务逐步验证。目标是能读懂并维护生成结果，而不是积累一批无法判断是否正确的页面。

# Web 渲染架构：HTML 来源与交互激活

商品介绍可以提前生成并缓存，库存需要实时查询，购物车按钮需要客户端事件。一个页面可以同时使用多种策略。判断渲染架构时，先分清“HTML在哪里生成”和“哪些区域需要客户端代码”，它们不是同一道选择题。

## CSR、SSR 与 SSG 比较的是生成位置和时机

| 策略 | 首次访问的主要内容如何出现 | 适合的场景 | 需要处理的成本 |
| --- | --- | --- | --- |
| CSR | 浏览器加载脚本与数据后生成 | 登录后工作台、持续交互界面 | 脚本失败、加载瀑布、主线程执行 |
| 请求时SSR | 服务端处理请求时生成HTML | 个性化或较新内容的首屏 | 服务端延迟、缓存隔离与容量 |
| SSG | 构建阶段生成HTML，访问时分发 | 文档、文章和稳定产品介绍 | 构建规模、内容更新时间与失效 |

SSR 的结果也可以缓存，因此并非每次访问都重新渲染；SSG 页面也可以请求实时数据，因此并非所有内容永远固定。客户端路由切换还可能使用不同于首次访问的加载方式。要明确比较的是首次导航、后续切换还是后台刷新。

SSR 不一定更快：慢数据源会推高首字节时间，大量 hydration 仍可能阻塞交互。CSR 也不等于所有 HTML 都完全空白，它可以提供基础结构、静态说明和渐进增强。应实际检查响应正文和运行后的 DOM。

## Hydration 连接已有DOM与客户端组件

服务端或构建阶段先产出内容，浏览器的客户端组件再复用已有 DOM、建立状态和事件关系，这是常见的 hydration 路径。原生链接可以在组件激活前导航，而自定义交互按钮可能要等待脚本。

客户端第一次计算应和已有 HTML 对应。直接在首轮渲染中使用随机数、当前时区日期、浏览器窗口宽度或仅客户端可读的存储，会产生不一致。处理方式通常是传递稳定初始数据，或将依赖浏览器环境的变化安排在挂载后，并预留空间控制布局偏移。

服务端不能直接使用 window、document 或当前浏览器的 localStorage。用户状态也不能放在跨请求共享的模块变量中。数据序列化到 HTML 时还需要安全转义，避免把商品名称等不可信字符串拼成脚本。

## Islands 决定激活哪些区域

Islands 把交互集中到独立区域：正文保持静态，评论、搜索或购物车作为需要激活的组件。它可以结合构建时生成，也可以结合请求时渲染，并不是和 SSR、SSG 并列的第四种生成时间。

按可见、空闲或用户操作延后激活，能减少首屏脚本压力，但也可能延迟首次点击。多个岛之间共享购物车时还要设计消息或状态通道；不能假设每个岛独立就不再需要协调。

纯静态 HTML 不必 hydration；需要传统表单提交的页面，也可以由服务器完成动作。反过来，页面采用 SSR 不代表整个页面都必须加载同样多的客户端代码。先数清实际交互区域，再分配脚本预算。

## 商品页可以混合使用

商品说明在构建或缓存更新时生成；价格和库存按适当新鲜度查询；登录后的购物车按用户身份读取。公开说明可由 CDN 共享，个人购物车不能混进公共缓存。库存展示只是提示，最终下单仍由服务端事务判断。

如果用陈旧缓存加后台更新，应明确展示时间或更新状态；如果价格变化会影响支付，提交后以服务端确认结果为准。渲染方式解决内容出现的位置，不代替权限、并发控制和交易一致性。

## 从实际响应验证策略

以本站文档为例，构建产物中已经包含文章文字与图片引用；客户端脚本再负责站内导航、主题及图片预览。验证时先看文档响应是否含标题和正文，再观察脚本完成前后哪些行为可用。

| 观察 | 能得出的结论 |
| --- | --- |
| 响应HTML已有商品说明 | 内容由服务端或构建产出，不能仅凭此区分SSR和SSG |
| 首轮只见容器，脚本后出现列表 | 该列表依赖客户端生成 |
| 可见按钮点击没有反应 | 继续查激活时机、脚本错误和事件，不能只判定网络慢 |
| hydration不匹配 | 比较双方初始数据、环境分支与HTML合法性 |
| 禁用脚本仍能阅读 | 证明相应静态内容可读，不证明所有业务交互可用 |

最终用用户路径验收：首次进入能否读内容、首次操作是否响应、刷新深链接是否成功、登录内容是否隔离、旧版本资源是否仍可加载。首屏指标与交互指标分开观察，见 [性能工程](./27-web-performance-engineering)。

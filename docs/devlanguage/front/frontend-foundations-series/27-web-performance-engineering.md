# Web 性能工程：加载、交互与布局稳定性

商品图两秒后出现，点击购买又卡一秒，最后推荐位把按钮挤到别处，这是三种不同问题。减小 JS 文件可能有帮助，但不能同时证明图片更早显示、输入更快响应和布局更稳定。

![按用户现象选择加载、交互或布局证据](/front/frontend-foundations-series/ep27-flow.svg)

## 先固定量测条件

记录页面版本、设备与浏览器、网络、缓存冷热、数据量和操作步骤。一次高性能电脑上的本地分数，不能代表低端手机和真实网络。实验室测试方便复现，真实用户数据反映用户分布，两者需要配合。

截至 2026-10-20，Core Web Vitals 的核心指标为 LCP、INP、CLS。判断整体表现通常看第75百分位，并区分移动与桌面分组；不是把一次测试值当成全站结论。

| 指标 | 观察对象 | “良好”阈值 | 不能直接证明 |
| --- | --- | --- | --- |
| LCP | 视口中符合规则的最大内容元素出现时间 | ≤2.5秒 | 所有内容和业务数据都加载完成 |
| INP | 页面会话中按规则选取的较差交互响应 | ≤200毫秒 | 网络业务操作已经保存完成 |
| CLS | 按会话窗口规则聚合的非预期布局偏移 | ≤0.1 | 没有任何动画或滚动 |

INP 关注点击、触摸和键盘交互到下一次绘制的延迟，包括等待处理、事件执行和呈现延迟，不是所有事件耗时的平均值。CLS 不是把页面所有位移无条件累加；LCP 的候选元素也遵循专门规则。单次 Lighthouse 分数不能替代真实会话的 INP。

## 主要内容出现晚：拆开关键路径

先看文档响应和资源瀑布：服务端响应是否慢，主图是否直到脚本执行后才被发现，下载是否竞争，图片解码或主线程是否又推迟显示。

首屏主图通常不应懒加载。正确尺寸和合适编码减少下载与解码成本；必要时提前暴露关键资源，但不能把所有图片、字体和 chunk 都设为高优先级。预加载错误资源会占用带宽，甚至和真实请求无法复用。

SSR 可能提前提供主图引用，仍无法消除慢源站、过大图片或大量客户端激活。优化后应在同样冷热缓存条件下复测，而不是只比较一次请求文件大小。

## 点击卡顿：观察输入到绘制

主线程任务超过50毫秒称为长任务，可能推迟后续输入；它只是定位线索，不能直接等同于 INP。用 Performance 记录点击前后，区分排队、处理函数和后续样式布局的耗时。

若点击时同步过滤十万条数据，先检查能否减少数据、建立索引、分页或移到 Worker。Worker 不能直接操作 DOM，数据传递和初始化也有成本。把循环改成不断补 Promise 微任务仍可能饿死渲染，见 [事件循环](./14-javascript-event-loop)。

读取几何信息和写样式交错时，可能强制同步布局；先批量读再批量写通常更容易控制成本。`transform` 与 opacity 常有合成优化机会，但并非所有元素、所有效果都保证不绘制，过多图层还会占用内存。

## 页面跳动：给动态内容留空间

商品图应提供正确宽高比，异步推荐位应预留符合设计的空间，字体替换要检查字宽变化。为图片写 width/height 不要求固定屏幕显示尺寸，可以结合响应式 CSS 保留比例。

```html
<img src="/images/product.webp" width="800" height="600"
     alt="白色陶瓷茶杯">
<style>
img { max-width: 100%; height: auto; }
</style>
```

这是商品页资源示例，实际文件需存在。用户点击后预期展开内容也不应遮挡或丢失焦点；CLS 的部分输入排除规则不是让交互可以任意跳动的理由。持续加载内容要同时验证阅读位置和键盘目标。

## 用可回退的改动证明收益

| 证据 | 可能的改动 | 复验 |
| --- | --- | --- |
| 主图发现晚 | 将资源入口提前到HTML | 相同条件下LCP和请求起点 |
| 首次点击被大量计算阻塞 | 减少计算或有界分批、Worker | 相同交互的排队与呈现延迟 |
| 图片到达后推开按钮 | 提供正确比例和占位 | CLS、截图及点击目标 |
| chunk过大且多为非首屏功能 | 按实际使用边界分包 | 首屏与首次打开功能的两端耗时 |

一次只改变能解释证据的变量，保存修改前后记录，并检查错误率、可访问性和内存是否回退。没有真实用户样本时，可以报告实验室结果及限制，不能声称真实用户指标已经改善。更完整的排查入口见 [性能专题](../performance/)。

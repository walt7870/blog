# 跨端框架

跨端框架用于把一套业务逻辑或组件模型发布到多个运行环境，例如 iOS、Android、小程序、H5、桌面端。跨端的价值是复用工程能力和业务代码，但每个平台的能力、交互规范、发布流程和性能边界仍然不同。

例如“录音后生成订单备注”，文字校验和订单状态可以共享；麦克风权限、音频会话、文件路径、后台中断和上传恢复必须按平台实现。评估时应跑完整业务链，而不是只确认首页能显示。

## 主流方向

| 框架 | 主要目标 | 适用场景 |
| --- | --- | --- |
| React Native | iOS / Android 原生应用 | 有 React 经验，需要原生 App 体验 |
| Flutter | iOS / Android / Web / 桌面 | 统一 UI、高性能渲染、多端应用 |
| Taro | 小程序 / H5 / React Native 等 | 国内多小程序端和 H5 统一开发 |
| uni-app | 小程序 / H5 / App | 国内业务多端覆盖、Vue 技术栈 |
| Electron | 桌面应用 | 跨平台桌面工具、管理端、IDE 类应用 |

## 选型

如果核心目标是移动原生体验，并且团队熟悉 React，可以评估 React Native。如果希望 UI 渲染高度一致、团队接受 Dart，Flutter 更适合。国内业务如果重点是微信、支付宝、抖音等小程序和 H5，同一套业务多端发布时，Taro 和 uni-app 更常见。

Electron 不是移动跨端框架，它面向桌面端。它的优势是能复用 Web 技术和 Node.js 能力，代价是安装包体积和运行资源占用更高。

React Native使用原生宿主组件，不是把网页DOM直接放进手机；Flutter采用自己的组件与渲染体系，各平台还有输入、可访问性和插件差异。Taro与uni-app需要分别确认目标平台、框架版本及插件支持，不能根据“支持多端”推断任意第三方SDK都能通用。

## 共享逻辑与平台适配

在录音备注场景中，共享模块接收统一业务结果：录制完成得到可上传的音频句柄，拒绝权限得到可恢复错误，中断得到取消状态。平台适配器负责申请权限、启动与停止录制、处理系统中断及释放资源。业务层不应该拼Android文件路径或直接访问浏览器`MediaRecorder`。

| 情况 | 共享业务层 | 平台适配器 |
| --- | --- | --- |
| 正常录音结束 | 保存草稿、显示时长、允许上传 | 结束会话、交付文件句柄与格式 |
| 用户拒绝权限 | 保留文字输入，解释不能录音 | 返回拒绝状态，按平台规则引导设置 |
| 来电或切到后台 | 标记录音中断，不自动当成功 | 响应系统中断，关闭设备与文件 |
| 上传失败 | 保留草稿，允许重试并防止重复订单 | 提供可再次读取的文件，不提前删除 |

这里的音频句柄是业务约定，不意味着所有端都支持同一个文件URI。上传适配器需按平台读取实际数据；保存到草稿库前还要确认临时文件何时失效。设备权限拒绝、订单API拒绝和网络断开也应分别呈现，不能都归结为“未知错误”。

## 工程注意点

跨端项目最容易被低估的是平台差异。支付、登录、分享、定位、蓝牙、文件、相机、推送、审核和灰度发布都可能与平台强绑定。选型前要列出核心平台能力，做最小验证。

| 现象 | 检查点 |
| --- | --- |
| 某端样式异常 | 单位、布局引擎、平台组件差异 |
| 能力调用失败 | 权限、平台 API、运行环境和审核限制 |
| 包体积过大 | 依赖、图片资源、原生插件、运行时 |
| 发布流程复杂 | 多端证书、渠道包、审核、灰度和回滚 |

先制作一条最小业务链，在每个目标端验证“首次授权 → 录制 → 中断 → 恢复 → 上传失败重试 → 提交后回读”。记录真机型号、系统、目标端版本与插件版本，模拟器通过不能替代真机权限和音频验证。已有详细实践可以继续读[Flutter](../../flutter/)、[Electron](../electron-series/)；涉及平台能力时再进入对应运行时，避免在共享层堆条件分支。

# Flutter

Flutter用Dart描述界面，由框架维护运行时节点并通过引擎绘制。跨端共享UI和业务代码有价值，权限、签名、原生插件、平台交互与商店发布仍要逐端验证。

例如待办应用点击“完成”后，页面先显示提交状态，Repository向服务器写入，成功后更新列表；断网时则保留内容并给出重试。界面更新、数据事实、平台能力分别有自己的边界。

## 从一次操作理解整体

Widget是不可变配置，Element管理挂载位置与状态关系，部分Element关联RenderObject负责布局绘制。`setState` 同步执行回调并标记需要更新，框架在适当帧处理脏节点，不是立刻把整屏重新绘制。

网络等待可以异步，但同步大计算仍可能占住主isolate。页面重建也不应重新启动相同请求；请求Future、控制器和订阅要有明确创建与释放位置。待办返回结果后，还需检查页面是否仍有效、响应是否属于当前账号与筛选条件。

插件提供Dart到系统的适配，不会抹去权限、系统版本、后台限制和原生错误。相机插件在一个Android设备成功，不能证明iOS、Web或所有系统版本都具备相同能力。

## 选型与试点

| 需求 | 可获得的帮助 | 先验证什么 |
| --- | --- | --- |
| 多端交互式业务应用 | 共享界面、主题与大部分逻辑 | 返回手势、输入、无障碍和平台差异 |
| 高定制绘制与动画 | 统一绘制和动画体系 | 目标设备帧耗时、图片内存和启动 |
| 大量硬件或系统能力 | 插件、通道和FFI入口 | 维护状态、平台实现、权限与原生支持 |
| 内容站与搜索索引 | 可发布Web应用 | 首屏、文本索引与语义；传统Web通常更直接 |
| 存量原生系统 | 独立模块渐进接入 | 生命周期、包体、混合栈和发布成本 |

先用核心流程的小原型测试真实设备、长文本、字号放大、权限拒绝和弱网，再判断收益。不能仅凭“一套代码”承诺一致体验，也不能用debug模式的帧率评价最终性能。

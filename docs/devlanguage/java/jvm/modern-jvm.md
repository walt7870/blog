# 现代 JVM 发展

同一个订单服务从 JDK 8 迁到 JDK 25，变化不止是能使用新的语法。默认回收策略、容器资源识别、反射访问、native 库加载、线程调度和启动缓存都可能影响运行。升级应先保证行为和依赖兼容，再分别评估新能力的收益。

## 把版本与运行能力对应起来

下表聚焦 JDK 8 到 25 的迁移边界，不把发行商的支持周期与 OpenJDK 特性版本混为一谈。LTS 的维护期限、补丁和商业支持取决于选用的发行商。

| 版本 | 运行能力与迁移关注点 |
| --- | --- |
| JDK 8 | 元空间替代永久代；具体更新版本的容器支持与早期版本不同 |
| JDK 9 | 模块系统、统一日志；服务端默认回收器转向 G1，实际选择仍需核对运行参数 |
| JDK 11 | JFR 进入 OpenJDK，ZGC 以实验形式引入；不可照搬旧 GC 日志参数 |
| JDK 17 | 强封装影响依赖内部 API 的库；CMS 已移除，旧启动参数要清理 |
| JDK 21 | 虚拟线程正式可用；分代 ZGC 引入，但此版本需显式选择分代模式 |
| JDK 24 | ZGC 只保留分代模式；改进虚拟线程同步，JNI 加载与链接默认提示 native access；引入 AOT 类加载与链接缓存 |
| JDK 25 | 分代 Shenandoah 产品化但该版本仍非默认；AOT 缓存命令简化；紧凑对象头产品化但该版本需显式启用 |

例如旧服务携带 `UseConcMarkSweepGC` 升级时，先处理不受支持的启动选项，不能等应用启动失败后再改成一组网上的 G1 参数。语言编译目标、运行 JDK、依赖库和 native 库要作为一个组合验证，详见 [JDK 升级](../basic/jdk/upgrade.md)。

## 两种部署产物

![HotSpot 与 Native Image 的部署产物](/jvm/deployment-models.svg)

HotSpot 路径通常部署 JAR 与运行环境，保留解释执行和 JIT。CDS 可共享归档的类数据，AppCDS 扩展到应用类；JDK 24/25 的 AOT 缓存又把部分类加载与链接工作前移。这些机制仍运行在 JVM 中，不能把“AOT 缓存”当成已经生成独立 native 可执行文件。

Native Image 则在构建时根据可达性分析生成目标平台的可执行文件。动态反射、代理、资源与 JNI 需要相应的可达性元数据和验证，运行时动态加载能力也有边界。它适合评估短命任务和冷启动成本，但启动更快、内存更低和峰值吞吐都应在具体应用上测量，不能作为所有服务的固定结论。

例如每天只运行几十秒的报表工具，启动占比可能很高；持续运行数天的支付服务，则可能更关注稳定吞吐、诊断能力和热更新约束。先测启动到可服务时间、峰值 RSS、持续吞吐与故障恢复，再决定采用哪一种部署产物。

## 启动缓存需要与应用一起管理

JDK 25 的 HotSpot AOT 缓存可用下面的形式建立训练与使用流程。`app.jar` 必须是实际可运行应用，入口类需替换；训练会真正执行应用，因此应使用隔离的数据和可结束的训练负载。

```bash
# JDK 25：训练运行并创建缓存
java -XX:AOTCacheOutput=app.aot -cp app.jar com.example.App
# 同一兼容环境中使用缓存
java -XX:AOTCache=app.aot -cp app.jar com.example.App
```

缓存不是跨 JDK、跨架构和任意依赖变更都通用的文件。应用、JDK 或类路径改变时，应重新生成并检查是否实际使用缓存。一步训练与创建也可能额外占用资源；内存受限时可采用目标版本支持的分步流程。启动优化应保留未命中缓存时的正确运行路径，不能把训练时覆盖到的输入当成所有生产输入。

## 容器感知不等于自动完成容量规划

现代 HotSpot 可依据受支持的 cgroup 信息进行资源自适应，但具体能力依赖 JDK 更新版本、发行版和 cgroup 模式。部署后应检查实际识别结果与最终参数，而不是仅看 Pod 清单。

```bash
# 在目标 Linux 容器内检查识别信息与实际堆设置
java -XshowSettings:system -version
java -XX:+PrintFlagsFinal -version
```

例如容器上限 2 GiB，把最大堆直接设为 2 GiB，会挤压元空间、线程栈、Code Cache、直接内存、native 库和页缓存。`MaxRAMPercentage` 是堆自适应输入之一，不是整个进程内存的百分比上限；显式 `-Xmx` 还会改变判断。CPU quota 也会影响业务和并发 GC 的推进，低延迟回收器不能在 CPU 已耗尽时保证请求延迟。

确认资源识别后，以容器总用量、堆外分类和峰值负载建立预算。容器 `OOMKilled` 与 Java 抛 OOM 的证据入口不同，见 [诊断案例](./diagnostic-cases.md)。

## 虚拟线程与 native 边界

JDK 21 的虚拟线程适合大量阻塞 I/O 任务，让应用保持同步代码风格。它不能增加数据库连接数、下游容量或 CPU 核数。将 10 个平台线程换成数万条虚拟线程，却没有限制数据库并发，可能把排队从应用线程池推到连接池和数据库。

JDK 24 改进了 `synchronized` 场景下的卸载能力，不能把 JDK 21 的固定建议原样套到后续版本。native 回调 Java 后再阻塞等情况仍可能固定载体线程，需结合目标版本的 JFR 事件检查。锁范围、超时、取消和下游并发上限仍然需要设计。

升级还应检查 JNI/FFM 的 native access 提示。JDK 24 开始对相关加载和链接操作默认告警，应为实际调用模块配置所需 native access；这既不表示 JNI 被移除，也不证明 native 代码是安全的。具体加载和释放边界见 [JNI](./jni.md)。

## 分开验证升级与调优

先在目标 JDK 上保持可比的业务配置，完成启动、反射、序列化、数据库驱动、TLS、JNI 和关闭路径验证；再逐项尝试回收器、虚拟线程或启动缓存。每次保留运行版本、最终参数、容器限额、请求数据和结果，否则很难解释收益来自哪一项变化。

若目标是减少 GC 尾延迟，先从日志判断暂停是否覆盖慢请求，再按 [GC 选型](./gc/index.md#选型) 对比；若目标是冷启动，则记录进程启动到健康检查通过、首个真实请求成功的时间。JFR、统一日志和线程诊断应随升级验证，避免服务能启动却丢失排障能力。

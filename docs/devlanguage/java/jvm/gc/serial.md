# Serial GC

一个导入几十万条记录后退出的命令行工具，若堆较小、只能使用少量 CPU，Serial 可以作为简单基线。它在回收时暂停应用，用单个 GC 工作线程完成主要回收工作；资源少时省去并行协调成本，但也不能借助更多 GC 线程加速同一次暂停。

## 一次暂停里发生什么

![Serial 与 Parallel 的暂停工作方式](/jvm/gc-stw-workers.svg)

Serial 的年轻代使用复制方式，把存活对象送往 Survivor 或老年代；老年代主要做标记与整理。图只比较暂停中的 GC 工作方式，不表示两种回收器的暂停一定等长，也不表示只要加线程就按比例加速。

例如工具读完一页订单就写出并释放引用，存活数据较少，Serial 可能足够；若改成先保留全部订单再导出，存活对象越来越多，扫描和移动成本也会增加。此时先检查数据处理方式，不能仅因“单线程慢”就增加堆。

## 用同一输入建立基线

先编译 [GC 总览](./index.md#用有限实验认识日志) 的 `GcLoad.java`，再运行：

```bash
java -Xms128m -Xmx128m -XX:+UseSerialGC \
  '-Xlog:gc*:file=gc-serial.log:time,uptime,level,tags:filecount=3,filesize=10M' \
  GcLoad 20000
```

实验应正常结束并输出 `checksum=2546416`。日志中的 `Using Serial` 用于核对选择，后续暂停日志用于观察年轻代回收。这里限制小堆是为了产生可观察的 GC，不是在建议生产容量。

比较 Serial 与 [Parallel](./parallel.md) 时，保持堆、输入和 CPU 限额相同。记录总耗时、GC 总时间、最大暂停及回收后占用；这个短实验主要验证运行与日志入口，可靠的性能比较还需要预热、重复运行和真实数据。

## 什么时候应更换方案

如果工具已按批释放数据，回收后的存活量稳定，但暂停仍影响完成时间，可以在多核环境比较 Parallel；如果同一 JVM 还提供在线接口，需把接口延迟纳入验收，评估 G1 或并发回收器。

“小堆”“单核”“短任务”都不是自动选择 Serial 的充分条件。CPU 限额、对象存活率和任务等待成本共同决定结果；尤其不要把命令行工具里可接受的暂停直接套到支付接口。

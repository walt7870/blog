# ZGC

如果已经确认支付请求的长尾与 GC 暂停重合，可以评估 ZGC。它通过并发标记、并发转移以及指针和屏障机制，将大量工作放到应用运行期间完成。短 GC 暂停不意味着请求总延迟必然短，应用还要承担并发 CPU、内存带宽和分配等待成本。

## 先区分版本与分代模式

| HotSpot 版本 | ZGC 状态与启动方式 |
| --- | --- |
| JDK 11 | 实验引入，平台支持范围较早期受限 |
| JDK 15 起 | 产品化；不能据此推定所有发行版和平台均包含 |
| JDK 17 | `-XX:+UseZGC` 使用非分代模式 |
| JDK 21、22 | 分代模式需 `-XX:+UseZGC -XX:+ZGenerational` |
| JDK 23 | `UseZGC` 默认分代，`ZGenerational` 已弃用 |
| JDK 24、25 | 只保留分代模式；不再添加 `ZGenerational` |

分代模式利用年轻对象更易死亡的特性，年轻代可以更频繁回收，不等于把 Parallel 的 Eden/Survivor 日志原样搬来。分代 ZGC 同时使用加载和存储相关屏障等机制，不能把所有版本都概括成“只靠读屏障”。日志、JFR 和管理接口的内容会变化，迁移时必须一起验收监控。

## 并发工作也需要空间预算

![并发回收期间的分配余量](/jvm/concurrent-gc-budget.svg)

ZGC 的周期中包含短暂停顿与并发阶段，应用不是等到最后转移结束才重新运行。屏障帮助应用在对象移动期间取得正确引用，具体屏障和阶段细节取决于分代模式。图强调资源预算，不是 ZGC 或其他回收器的完整阶段时序。

例如突发导出在一个回收周期内产生许多新数组，即使暂停很短，空闲空间也可能先耗尽。`Allocation Stall` 是分配线程等待回收提供空间的信号，仍可能直接拖慢请求。需要同时观察分配速率、回收推进、存活量、CPU 配额与限流；不能只看暂停最大值宣布达标。

## 启动与有限验证

编译 [GC 总览](./index.md#用有限实验认识日志) 的 `GcLoad.java`。下列例子可用于支持 ZGC 的 JDK 17，观察的是非分代模式；在 JDK 24/25 同样的选择参数则启用分代模式：

```bash
java -Xms128m -Xmx128m -XX:+UseZGC \
  '-Xlog:gc*:file=gc-zgc.log:time,uptime,level,tags:filecount=3,filesize=10M' \
  GcLoad 20000
```

输出 `checksum=2546416` 说明实验完成，日志用于确认实际模式与周期。小堆实验可能放大分配压力，不适合用来决定生产堆大小或比较最终性能；不支持的发行版/平台应先检查支持范围，不能忽略启动错误继续宣称已切换。

## 如何评估迁移收益

先用目标版本的 GC 日志及 JFR，区分暂停、并发阶段与分配等待，再与端到端请求时间对齐。`jstat` 的列和管理内存池并非跨版本固定的分代视图，不宜沿用旧解析脚本直接告警。

与 G1 基线比较时保留相同负载、容器 CPU/内存预算和预热条件，记录业务结果、超时率、吞吐、P99/P999、GC CPU 与 RSS。若暂停下降但 CPU 限流更明显、吞吐不足或分配等待上升，应重新评估容量和对象创建模式。ZGC 不能释放被无界缓存强引用的对象，也不管理第三方 native 库的全部内存。

# G1 GC

订单查询服务既需要吞吐，也不能经常出现长暂停。G1（Garbage First）把堆划成等大的 Region，用历史成本估算安排暂停中的回收工作，并将部分标记工作并发执行。它是通用服务的常见基线，但停顿目标不是实时保证，回收仍需 CPU、存活对象的复制空间和合理的业务存活量。

## 分区不等于取消分代

![G1 分区、跨区引用与复制空间](/jvm/g1-regions.svg)

Region 可以充当 Eden、Survivor、Old 或 Humongous 区域，这些角色会随使用变化。年轻代和老年代是逻辑集合，不要求在地址空间里各自连成一整块。普通年轻代对象在暂停中复制到 Survivor 或老年代，老年代对象的转移目标则是其他老年代区域。

只扫描本次选中区域内部是不够的：区外对象也可能指向其中的存活对象。Remembered Set 记录区外指入的近似位置，写屏障和相关维护帮助构建这些信息；它不是“所有存活对象清单”。目标版本内部维护方式会变化，但用途都是让局部回收能发现区外引用，并在移动后更新引用。

## 从年轻代回收到 Mixed

正常年轻代回收通常以 STW 方式并行复制存活对象。老年代压力上升后，Concurrent Start 年轻代暂停启动标记工作，随后并发标记可以与应用及其他年轻代回收交错。G1 使用 SATB（初始快照）相关机制保持标记正确性，不能按业务实时快照理解：本轮已被视为存活、随后才死亡的对象可能留到下一轮。

标记通过 Remark、Cleanup 等阶段收尾，根据结果决定是否进入空间回收阶段；不会每次标记后都机械地出现固定次数的 Mixed。Mixed 暂停在年轻代之外加入部分老年代候选区域，选择还要考虑存活量、关联程度与预计成本，复制本身仍然 STW。无可观回收收益时，减少停顿目标也无法凭空产生可回收空间。

例如导出页数据临时生成后即释放，回收收益可能很好；若每页结果都被长期缓存，候选区里大多是存活对象，就需要移动更多数据才能腾出较少空间。应先检查缓存边界与分块处理，不能只追求更多 Mixed 次数。

## 参数从最少集合开始

编译 [总览实验](./index.md#用有限实验认识日志) 后，用同一输入运行：

```bash
java -Xms128m -Xmx128m -XX:+UseG1GC \
  '-Xlog:gc*:file=gc-g1.log:time,uptime,level,tags:filecount=3,filesize=10M' \
  GcLoad 20000
```

`MaxGCPauseMillis` 是暂停目标，不是每次暂停的上界。先使用默认自适应行为建立基线，再按真实日志评估是否需要调整；不要同时固定年轻代比例、Region 大小和并发线程数，让问题难以归因。实验堆不等于生产建议。

IHOP 控制启动并发标记的时机。启用自适应 IHOP 时，`InitiatingHeapOccupancyPercent` 主要用于早期预测不足的周期，之后会结合标记耗时和分配行为调整；不能说“堆到 45% 必定启动”。需要核查时在受控窗口增加 `gc+ihop=debug` 日志并确认目标 JDK 的输出。

## 大对象与转移失败

JDK 25 将大小达到半个 Region 的对象归为 Humongous，尺寸要按对象实际占用而非数组内容字节数判断；阈值边界应与运行版本一致。对象会占用连续的一组老年代 Region，最后一区剩余空间也可能不能供其他对象使用。大数组、大字符串拼接和一次性读取整个导出文件容易形成压力。

先看日志中的 Humongous 区域变化、分配触发原因和对象类型，再考虑分块读取或流式输出。直接改大 Region 会改变分区粒度和空间成本，不是无代价修复。

转移失败表示有些对象无法移动；空间不足是一种原因，现代版本的 JNI 固定区域也可能造成移动限制。它不一定立刻导致 Full GC。若回收无法释放足够空间，G1 可能进行全堆 STW 整理；显式 GC 请求也需从日志原因单独区分，不能把全部 Full GC 都归为“堆太小”。

## 验证是否解决了业务问题

把同一窗口的 Young/Mixed/Full、各暂停阶段成本、回收后占用和应用尾延迟对齐。若复制成本高且存活量大，先缩短对象持有时间；若并发周期追不上突发分配，再看容量、CPU 限流与批量大小。若 GC 暂停满足而请求仍慢，则回到线程和下游链路。

改动后在相同负载与容器限额下复测业务结果、吞吐、P99/P999、GC CPU 和 RSS。选择 [ZGC](./zgc.md) 或 [Shenandoah](./shenandoah.md) 也需要保留足够分配余量，不能把换回收器作为处理无界缓存的替代品。

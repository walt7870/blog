# Epsilon GC

Epsilon 处理分配，却不回收已经分配的对象。它适合研究分配压力、比较 GC 带来的部分成本，或运行总分配量有明确上限的短任务。普通常驻服务会不断创建对象，即使几乎没有长期存活对象，也会最终用尽堆。

## 预算看累计分配，不只看存活峰值

![Epsilon 累计分配与存活量的区别](/jvm/epsilon-budget.svg)

例如逐页处理订单，每页新建一块缓冲，写出后便失去引用。普通回收器可以复用已释放空间，Epsilon 则不会；最大同时存活量很小，累计分配仍然持续增加。预算还包括 JVM 启动和库创建的对象、对象头、对齐及分配缓冲损耗，不能用输入文件大小直接估算堆需求。

“执行很快”不意味着总分配少。一个两秒任务也可能创建数 GiB 临时数组；只有确定输入上限、依赖行为及分配预算后，才有讨论短任务适用性的基础。

## 一个正常结束与一个预期耗尽实验

Epsilon 在 JDK 11 引入为实验特性。使用支持它的 JDK 17，先编译 [GC 总览](./index.md#用有限实验认识日志) 的 `GcLoad.java`。以下命令只用于本地有限实验，先解锁再选择回收器：

```bash
# 少量分配，应正常结束
java -Xms32m -Xmx32m -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC \
  '-Xlog:gc*:file=gc-epsilon-small.log:time,uptime,level,tags' GcLoad 100

# 累计数组内容就超过32 MiB，预期非零退出
java -Xms32m -Xmx32m -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC \
  '-Xlog:gc*:file=gc-epsilon-full.log:time,uptime,level,tags' GcLoad 5000
```

第一条应输出 `checksum=4950`、`last=99`；第二条应因堆耗尽终止，具体异常或终止文本取决于实现，不能把它写成需继续运行的正常服务。不要在这里开启自动重启让失败循环制造更多日志，也无需为了实验生成大体积 heap dump。

两次运行仍只保留最近 64 块数组，第二次失败说明“此前分配过”与“现在还存活”不能混为一谈。可以另用相同 32 MiB 堆和输入选择 Serial，验证真实回收能够复用空间，而不是把差异误判为代码保留了所有数组。

## 实验结果能说明什么

Epsilon 去掉了实际回收及相关机制的部分干扰，仍有 JIT、线程调度、TLAB、系统内存和 I/O 成本。没有 GC 周期不等于没有抖动，也不能把 Epsilon 耗时当作其他回收器必然可达到的线上性能。

用分配实验估算代码开销时，要让对象确实逃逸或观察结果；否则 JIT 可能消除无用分配，测到的是优化后的不同工作量。分析出热点后，仍需回到真实回收器，用生产相近的输入验证业务正确性、累计分配、存活量、吞吐和尾延迟。Epsilon 是用于提出和检验假设的工具，不是解决内存泄漏的方案。

# CMS GC

CMS（Concurrent Mark Sweep）是历史上的低停顿老年代回收器，常与 ParNew 年轻代回收配合。它通过并发标记和清除减少长暂停，但通常不移动老年代存活对象，因此要面对碎片、并发 CPU 竞争，以及回收完成前空间耗尽的问题。CMS 在 JDK 9 被弃用、JDK 14 移除，本页用于解释旧系统与迁移。

## 应用什么时候可以运行

![CMS 标记清除与应用执行关系](/jvm/cms-cycle.svg)

图只保留初始标记、并发标记、重新标记和并发清除四个关键阶段。实际日志还包含预清理、可中止预清理和重置等工作，期间也可能发生 ParNew 暂停；不能把简图解释成“除两个点外整个 JVM 绝不暂停”。

初始标记建立老年代标记起点，并发标记继续沿对象关系识别存活对象；重新标记处理并发修改带来的遗漏，清除阶段把可回收空间放回空闲结构。某些对象在本轮被视为存活后才失去引用，会作为浮动垃圾留到后续周期，这与业务集合一直保留对象不同。

## 为什么有空闲总量仍然失败

例如老年代还剩若干块小空洞，但一次大数组需要更大的连续空间；总空闲量足够也未必能满足分配。CMS 正常并发清除没有把这些空洞自动拼成一块，不能只看老年代占用百分比。

另一类情况是导出请求同时增多，晋升速度上升，CMS 尚未完成就已经没有空间继续分配或晋升，可能出现 `concurrent mode failure` 并转入更重的回收。提前启动周期只可能增加时间余量，无法解决长期存活量接近堆上限、CPU 被限制或无限保留结果的问题。

| 日志与现象 | 进一步核对 | 处理方向 |
| --- | --- | --- |
| `concurrent mode failure` | 晋升速率、周期耗时、可用空间、CPU 配额 | 限制并发和存活量，评估容量与迁移 |
| 晋升或大对象分配失败 | 同期年轻代日志、连续空闲块、老年代持有链 | 缩小批次，处理无界数据，区分空间与碎片 |
| Remark 暂停偏长 | 对象关系、修改速率、引用处理及系统压力 | 先确认阶段成本，避免只改启动阈值 |

## 旧参数不能直接翻译成新配置

JDK 8 的历史配置可能为：

```text
-XX:+UseConcMarkSweepGC
-XX:CMSInitiatingOccupancyFraction=70
-XX:+UseCMSInitiatingOccupancyOnly
```

这里用于识别固定占用阈值触发的旧策略，不是推荐值。升级时移除 CMS 专属参数，验证目标版本是否启动、实际使用哪个回收器及日志是否可解析。不能把 `70` 直接抄给 G1 的 IHOP，后者的自适应逻辑与 CMS 不同。

## 迁移时保留可比较的证据

保存旧版本、最终参数、GC 日志、峰值负载和业务指标，以相同输入比较新方案。G1 可作为通用候选，严格延迟目标可评估 ZGC 或 Shenandoah，吞吐任务也可比较 Parallel；具体选择由业务约束决定。

验收既要看长暂停是否减少，也要看端到端延迟、吞吐、CPU 和 RSS 是否接受。换成带整理能力的回收器后，如果任务集合仍无限增长，内存最终仍会耗尽。诊断采集成本与证据入口见 [GC 总览](./index.md#从现象回到原因)。

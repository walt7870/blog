# Parallel GC

夜间对账要在规定窗口内处理全部订单，用户不等待每条记录的响应，这类任务可以优先比较总耗时。Parallel GC 用多个 GC 工作线程执行暂停中的复制和整理，目标是较高吞吐；它不会让应用在主要回收暂停中继续处理订单。

## 并行不等于并发

![Serial 与 Parallel 的暂停工作方式](/jvm/gc-stw-workers.svg)

现代 HotSpot 通过 `UseParallelGC` 选择年轻代与老年代的并行回收。多个工作线程可以分担扫描、复制和整理，但仍有同步、内存带宽和负载分配成本；CPU 只有很少配额时，更多线程可能增加竞争。

因此不要固定复制 `ParallelGCThreads=8`。先检查 JVM 识别的可用处理器和最终参数，再根据目标环境验证。容器 CPU 配额与机器物理核数不一定相同，线程数量也不等于实际同时获得的 CPU 时间。

## 先比较默认自适应行为

编译 [GC 总览](./index.md#用有限实验认识日志) 的 `GcLoad.java`，用与 Serial 相同的堆和输入运行：

```bash
java -Xms128m -Xmx128m -XX:+UseParallelGC \
  '-Xlog:gc*:file=gc-parallel.log:time,uptime,level,tags:filecount=3,filesize=10M' \
  GcLoad 20000
```

输出应为 `checksum=2546416`，日志确认 `Using Parallel`。这证明实验接线正确，不能凭一次短运行得出“Parallel 最快”。真实对账还要保持数据库、磁盘和任务并发可比，避免把 I/O 波动算成 GC 收益。

## 吞吐与暂停目标如何取舍

`GCTimeRatio=N` 对应 GC 时间占总时间的目标比例 `1/(N+1)`。例如 `N=19` 表示目标为 5%，`N=99` 为 1%；它不是允许暂停 N 毫秒，也不是硬上限。`MaxGCPauseMillis` 同样是自适应目标，回收器可能通过调整代容量改善暂停，却增加回收频率。

例如对账已提前完成，改小暂停目标却使 GC 更频繁、总耗时增加，就不一定符合任务目标。先记录总处理量、总耗时、GC 时间占比及最大暂停，确认到底是哪项超标，再逐项改参数。若同进程还承载实时查询，则必须单独检查查询尾延迟。

回收后的老年代持续上涨时，应查保留了什么数据；高存活量不是靠缩短暂停目标能消除的。若吞吐已满足但业务暂停不达标，使用同一负载比较 [G1](./g1.md) 或低延迟回收器，连同 CPU 和 RSS 一起验收。

# ParNew GC

在 JDK 8 老服务的日志里看到 `ParNew`，通常是在观察 CMS 组合中的年轻代回收。ParNew 使用多个 GC 线程复制年轻代存活对象，但复制期间仍然暂停应用。它与 Parallel GC 名字相似，承担的组合角色却不同：ParNew 常配 CMS，`UseParallelGC` 则选择另一套回收器组合。

## 年轻代暂停如何影响老年代

![Serial 与 Parallel 的暂停工作方式](/jvm/gc-stw-workers.svg)

图中的多线程 STW 也可帮助理解 ParNew 的年轻代暂停，但图不代表它的老年代由 Parallel 管理。年轻代分配触发回收后，存活对象复制到 Survivor 或晋升老年代；CMS 还要处理进入老年代的数据。如果导出任务把每一页结果都挂到一个总列表，年轻代即使回收很快，老年代仍会不断积累。

看到 `promotion failed` 应核对晋升量、老年代可用空间与碎片，以及同一时段 CMS 是否来得及完成。它不等于“年轻代一定太小”，也不能仅通过减少年轻代回收次数判断已解决。

## 旧参数的识别范围

JDK 8 HotSpot 的历史配置可能包含：

```text
-XX:+UseConcMarkSweepGC
```

在该组合中理解 ParNew 与 CMS 的分工即可，不应再给现代 JDK 配一套 `UseParNewGC` 模板。CMS 在 JDK 9 被弃用，并在 JDK 14 移除；不同后续版本对废弃选项的处理还可能从警告变为启动失败。实际运行版本和最终选择要从进程参数与日志确认，不能只看旧配置文件。

JDK 8 的日志开关也不同于 JDK 9+ 统一日志。诊断时先保存 `java -version`、进程参数及原始 GC 日志，找到同一时段的 ParNew 暂停、晋升和 CMS 周期，避免拿新日志解析器错误套列。

## 从维护走向迁移

例如服务原来使用 ParNew + CMS，升级到 JDK 17 时，先验证依赖、反射、驱动和启动选项，再明确选择新回收器并建立基线。旧参数中的线程数和 CMS 占用阈值没有直接对应的 G1 等价模板，应该逐项删除或重新评估。

迁移结果至少要覆盖业务结果、吞吐、请求尾延迟、GC 暂停、CPU、回收后存活量与 RSS。老日志用于解释原问题，新日志用于确认目标实现；原来的晋升失败不应简单改名成新的“Mixed GC 问题”。老年代细节见 [CMS](./cms.md)，升级入口见 [JDK 升级](../../basic/jdk/upgrade.md)。

# Shenandoah GC

Shenandoah 将标记、对象转移和引用更新等工作尽量与应用并发执行，以减少长时间暂停。在需要控制订单接口尾延迟的服务中，它可作为 G1 之外的候选；代价包括屏障、并发线程、内存带宽与额外空间，不能只比较一次暂停的毫秒数。

## 发行版与模式必须明确

并非每个 JDK 构建或平台都包含 Shenandoah。先保存完整 `java -version`，再用实际目标运行环境检查选择参数和日志。不能因为两个环境都写“JDK 17”，就认为回收器支持完全相同。

传统 Shenandoah 采用单代模式。分代模式在 JDK 24 作为实验特性引入，在 JDK 25 产品化；JDK 25 默认仍为单代。支持它的 JDK 25 构建可明确选择：

```bash
java -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational -version
```

这只检查启动能力，不是性能验收。JDK 24 的分代模式还需要在模式参数前解锁实验选项；不要把 JDK 25 的形式复制到 JDK 17，后者没有这套分代模式。后续版本的默认行为应重新核对。

## 并发转移如何影响应用

![并发回收期间的分配余量](/jvm/concurrent-gc-budget.svg)

传统模式可概括为初始标记暂停、并发标记、最终标记暂停、并发转移，以及引用更新和相应的边界暂停；实际是否执行每项工作由存活情况和策略决定，分代模式的年轻代/老年代周期也不同。应用在并发阶段继续运行，不能把“引用更新”全部画成应用恢复前的一次大暂停。

Shenandoah 用相关屏障协调应用访问与对象移动，成本不只是一个写屏障。图强调并发回收的共同空间约束，不表示它与 ZGC 的屏障和阶段实现相同。应用持续分配时，回收器需要足够时间和空闲空间完成工作。

例如导出任务突发增加，CPU 又被容器配额限制，回收推进不足可能触发 pacing，分配线程被节流；若无法继续并发完成，可能出现 Degenerated GC，在暂停中接手未完成工作，必要时再进入 Full GC。退化不等于每次都会 Full GC，pacing 等待也不能只靠暂停统计发现。

## 验证日志入口

在支持 Shenandoah 的 JDK 17 构建上，编译 [GC 总览实验](./index.md#用有限实验认识日志)，用传统单代模式运行：

```bash
java -Xms128m -Xmx128m -XX:+UseShenandoahGC \
  '-Xlog:gc*:file=gc-shenandoah.log:time,uptime,level,tags:filecount=3,filesize=10M' \
  GcLoad 20000
```

预期完成输出 `checksum=2546416`，日志核对实际回收器和周期。若启动提示不支持，先选匹配的发行版和平台；不能把该日志当成所有构建都已可用的证明。实验只检验入口，不给生产堆大小结论。

## 从长尾改善到容量验收

将实际版本的周期原因、暂停、pacing、退化和 Full GC 与业务时间线对齐，再检查回收后存活量、分配速率和容器 CPU 限流。若导出结果一直被缓存，先限制持有量；若并发回收因 CPU 不足追不上，调低暂停目标并不能创造 CPU。

与原 G1 或其他基线比较业务结果、吞吐、超时、P99/P999、CPU 与 RSS，并在突发负载和恢复阶段复测。监控采集与 `jstat` 列必须针对模式核对，不要固定期待 Eden/Survivor 数据。验收范围包括内存预算与恢复能力，不能只报告平均暂停下降。

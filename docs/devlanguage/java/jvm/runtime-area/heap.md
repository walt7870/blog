# 堆

堆保存 Java 对象实例和数组，由 GC 管理。排查堆内存时，要分清**分配速率、仍然存活的数据量和堆容量**：对象创建得快会增加回收工作；已完成的任务还被长期引用，才会让存活数据持续积累。堆使用率上升本身不能证明泄漏。

![订单导出中的对象保留与释放](/jvm/heap-export-retention.svg)

## 从订单导出理解引用

假设每个导出任务暂存 10 MiB 数据，同时执行 20 个任务，仅这些数据就约占 200 MiB，还没算列表、字符串和编码副本。即使没有泄漏，也可能超过容量。分批读写和限制并发，比把整个查询结果装进一个列表更直接。

另一种情况是导出已结束，但全局 `tasks` 表继续保存包含订单列表的任务对象。方法返回只消除了其中一条栈引用，全局表的引用仍然存在。GC 不理解“业务已经完成”，只知道对象仍可从存活入口访问。修复要让任务终态清理大结果、移除过期任务，或仅保存文件地址与少量元数据。

对象互相引用也不必然泄漏。两个对象形成环，只要整个环不再从 GC Roots 可达，就可以被回收。软、弱、虚等特殊引用还涉及不同的处理规则，不能把所有引用都当作强引用。

## 堆结构取决于回收器

传统分代理解适用于 Serial、Parallel、G1 以及分代 ZGC 等具体实现，但不要把所有堆画成固定比例的 Eden、Survivor、老年代。G1 使用 Region，并区分普通分配和 Humongous 对象；ZGC 的代际实现也有自己的布局。先确认 JDK 与回收器，再解释日志和晋升。

JIT 可能通过逃逸分析和标量替换消除某次对象分配。因此，“规范上创建对象”不保证优化后的运行中出现同样的物理堆对象；普通业务排障仍应以实际对象统计和引用为证据。

## 区分三种问题

| 现象 | 需要验证的假设 | 处理方向 |
| --- | --- | --- |
| 流量升高时使用量快速上升，流量回落后恢复 | 瞬时分配、并发任务或队列积压 | 控并发、分批、限队列，核算峰值 |
| 相同负载下，回收后的存活基线逐轮升高 | 已结束的数据被缓存、集合或 ThreadLocal 保留 | 查引用路径与业务生命周期 |
| 存活基线稳定，但接近容量且反复回收 | 合法工作集已接近上限 | 扩容或减少工作集，并验证延迟和容器余量 |

`Java heap space` 表示当前堆无法满足分配，不自动说明泄漏。`GC overhead limit exceeded` 是部分回收器的保护性表现，表示大量时间用于 GC 却回收很少；不能假设每种回收器都会以此报错。G1 的 Mixed GC 也不是 Full GC，日志必须按实际事件解释。

## 证据怎么收集

先看已配置的 GC 日志，并查询堆概况：

```bash
jcmd <pid> GC.heap_info
```

JDK 9+ 可在启动时保留带时间信息的 GC 日志：

```bash
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M
```

需要对象证据时，选择一次直方图或 dump，不要在未分析前连续抓多份大文件：

```bash
jcmd <pid> GC.class_histogram > /tmp/order-histogram.txt
jcmd <pid> GC.heap_dump /tmp/order-export.hprof
```

这两项默认行为可能请求 GC 并暂停应用，dump 还包含业务数据、需要足够磁盘空间。可先用 `jcmd <pid> help GC.heap_dump` 核对当前 JDK 的参数；加入 `-all` 会包含不可达对象并改变采集语义，不能与默认 dump 混着比较。

在 MAT 等分析器里先按 Retained Heap 找保留体积大的对象，再看到 GC Roots 的路径。直方图只能说明类的数量和总浅大小，无法单独证明是谁保留了它。对订单任务，要确认持有者是否仍在执行业务，以及终态后的清理时限。

## 参数与验收

`-Xms` 是初始堆大小，`-Xmx` 是上限。两者设成相同值可以减少堆容量调整，但不会自动预触碰所有内存页，也不能解决无界缓存。容器预算还须包含[直接内存](./direct-memory.md)、元空间、平台线程栈等开销。

修复后以相同数据量和并发反复执行导出：任务完成并经过适当回收后，任务表数量与存活基线应回到稳定范围；同时检查耗时、GC 停顿、队列和失败率。仅观察一次“堆下降了”，不足以证明长时间负载下已经稳定。对象分配和可达性细节见[对象生命周期](../object-lifecycle.md)，回收器差异见[GC](../gc/)。

# 虚拟机栈

虚拟机栈保存线程的方法调用现场。规范模型中，每次调用创建一个逻辑栈帧，方法正常返回或异常退出时销毁该帧。栈帧包含参数和局部变量、操作数栈，以及连接运行时常量池和恢复调用者的信息。JIT 内联等优化可能改变物理帧布局，不能把源码调用层数直接换算成固定字节数。

![订单调用中的栈帧与堆对象](/jvm/stack-frame-order.svg)

## 参数引用与对象本体

`Controller -> Service -> Repository` 是一条逻辑调用链。Service 把订单对象传给 Repository，传的是引用值；各帧可以引用同一个堆对象，并没有随参数传递复制一整份订单。实例方法的局部变量槽还包含 `this`，操作数栈则用于字节码的中间计算，与整条调用栈不是同一个概念。

一个局部变量仍在词法作用域内，不保证 GC 必须一直保留其对象；JIT 按活跃性分析处理已经不再使用的引用。反过来，方法返回也不保证对象可回收，因为全局集合或异步任务可能继续持有它。需要定位保留关系时应看实际引用链，不能只看大括号范围。

## 栈溢出先看出错现场

典型反例是订单的 `toString()` 输出明细，明细又输出所属订单，双方反复调用；另一种是树遍历缺少深度限制，面对异常链状数据递归数万层。前者要切断循环输出或记录必要字段，后者要确认输入约束，必要时改成显式工作队列并限制规模。

`StackOverflowError` 的关键证据是抛出时异常栈里的重复模式。线程发生异常后会展开栈帧，事后执行 `jstack` 未必还能看到递归现场；因此应保留原始错误日志，再在受控复现中采样。

```bash
jcmd <pid> Thread.print > /tmp/order-threads.txt
```

线程 dump 用于看当前调用和阻塞，不是历史记录。还要确认是否被日志采集截断、是否因重复日志丢失首个异常。

## 平台线程与虚拟线程

| 对象 | HotSpot 的存储与调参边界 |
| --- | --- |
| 平台线程 | 通常有独立 OS 栈，Java/native 调用帧共用其空间；`-Xss` 影响栈大小 |
| 虚拟线程（JDK 21 起正式提供） | 暂停的 Java 调用现场可保存为堆内 stack chunk，运行时挂载到 carrier；不为每条虚拟线程固定预留一份 `-Xss` native 栈 |

虚拟线程也可能栈溢出，也消耗堆和 carrier 资源；它不是无限并发许可。大量请求等待数据库时，即便平台线程数不高，挂起的调用仍可能保留订单、缓冲区和 ThreadLocal 数据。应限制稀缺下游的并发，并设置超时与取消。

传统 `Thread.print` / `jstack` 主要呈现平台线程视图；查看虚拟线程需要使用对应 JDK 支持的 dump，例如先用 `jcmd <pid> help Thread.dump_to_file` 核对命令和选项，不能把旧线程数指标当作全部任务数。

## 栈大小和线程容量

```bash
-Xss1m
```

这是平台线程栈的配置示例。1000 个约 1 MiB 的线程栈可以形成约 1 GiB 的地址空间预留，但已驻留页、JVM 额外线程和平台开销不同，不能直接断言 RSS 就是 1 GiB。`unable to create native thread` 还可能来自 OS 线程/PID 配额，不只由栈内存不足造成。

Linux 可用 `ps -L -p <pid>` 查看 OS 线程；macOS 对应 `ps -M <pid>`。`ulimit -a` 显示当前 shell 的限制，不保证它就是由 systemd 或容器启动的服务限制，还要核对服务和 cgroup 配置。

增大 `-Xss` 可容纳更深调用，但会减少可支持的平台线程容量；减小后也要验证正常深度、序列化和 native 调用。对循环递归先修逻辑，对合法深层输入再比较迭代与容量方案。验收使用原来失败的数据和最大受支持深度，同时观察线程数、错误率和内存，不能只以“不再报错”结束。

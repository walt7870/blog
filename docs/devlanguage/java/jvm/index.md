# JVM：Java 程序的运行系统

同一份订单服务 jar 为什么能在不同系统运行？为什么查询只多返回几万条数据，服务却开始频繁 GC？为什么堆还没用满，容器就把进程终止？JVM 连接字节码、执行引擎、内存和操作系统，这些问题需要沿着同一条运行链解释。

![JVM 从字节码到执行与回收的关系](/jvm/jvm-overview.svg)

`javac` 把源码编译为 `.class`；目标平台的 JVM 加载类型、校验字节码并执行方法。解释器可以启动执行，JIT 会把热点路径编译为机器码。Java 的跨平台输入是字节码，但仍要满足目标 JDK 的类文件版本、API 与依赖要求；如果 jar 携带 native 库，还要匹配 OS 和 CPU 架构。

## 跟随一次订单请求

以“创建一笔 199 元订单”为例，Spring 和业务代码负责路由、校验、事务与 SQL，JVM 负责这些代码的类型和执行环境。JVM 并不理解支付成功、订单有效或数据库回滚。

| 请求经过哪里 | JVM 在做什么 | 可观察的证据 |
| --- | --- | --- |
| 启动或首次使用订单类 | 加载、验证、准备，按需解析；触发条件满足时初始化 | 类加载日志、初始化错误 |
| Controller 调用 Service | 保存逻辑栈帧、参数和返回现场 | 异常栈、线程 dump |
| 创建订单和返回结果 | 分配对象与数组，维护引用关系 | 堆占用、对象统计 |
| 同一路径反复执行 | 收集运行信息，可能内联、编译或去优化 | JFR、编译日志、Code Cache |
| 请求完成 | 栈帧退出；失去可达引用的数据才可能回收 | GC 日志、存活基线 |

请求结束不等于相关对象立即消失：若缓存或异步任务继续保存订单，GC 仍认为它活着。数据库连接、direct buffer、native 句柄还需要各自的生命周期管理。

## 类、对象、机器码分别在哪

![JVM 运行时数据区与进程内存边界](/jvm/runtime-area-map.svg)

可以把类型信息理解为订单结构的说明，对象是某一笔具体订单，调用栈记录这次处理走到了哪里。HotSpot 的元空间主要保存类元数据，Java 堆保存对象，Code Cache 保存 JIT 机器码。线程归属与堆内/堆外位置不是同一种分类，详细边界见[运行时数据区](./runtime-area/)。

2 GiB 容器里设置 `-Xmx2g`，并没有给线程栈、元空间、代码缓存和缓冲区留出预算。另一方面，RSS 增长也不自动意味着泄漏：预热、文件页驻留、池化保留和真实工作集增加，都需要同一时段的指标区分。

## 哪些顺序不能机械理解

类加载的“加载、验证、准备、解析、初始化”适合解释职责，不是一条必须全部同步完成的流水线。验证和准备必须在初始化前完成，符号解析可以延迟到实际使用；普通静态字段先取得默认值，带 `ConstantValue` 的常量字段有单独的初始化规则。类的运行时身份还包含定义它的加载器，所以插件中的同名类可能无法互相转换。细节见[类加载机制](./class-loading.md)。

字节码的栈式模型也不等于 CPU 始终逐条解释。JIT 可以内联方法、消除分配或锁，但必须保持语言可观察的语义；运行时假设失效后可以去优化。判断“预热后会更快”，需要测量负载和编译过程，不能仅凭循环次数估计，见[执行引擎与 JIT](./execution-engine-jit.md)。

## GC 如何选阅读入口

先识别实际 JDK、回收器与业务目标。订单 API 看延迟分位数与停顿，批量结算看总吞吐，低配工具更关心额外内存。增大堆、换回收器都不能代替修复无界队列和对象保留。

| 回收器 | 主要取舍与版本边界 | 详细页 |
| --- | --- | --- |
| Serial / Parallel | 简单低开销 / 吞吐导向，停顿与负载有关 | [Serial](./gc/serial.md)、[Parallel](./gc/parallel.md) |
| G1 | Region 与停顿目标，目标不等于硬上限 | [G1](./gc/g1.md) |
| ZGC / Shenandoah | 以并发工作降低停顿，须核对版本、发行版、CPU 和内存成本 | [ZGC](./gc/zgc.md)、[Shenandoah](./gc/shenandoah.md) |
| CMS / ParNew | 历史系统维护；CMS 及其 ParNew 组合在 JDK 14 移除 | [CMS](./gc/cms.md)、[ParNew](./gc/parnew.md) |
| Epsilon | 不回收，适合限定时长实验等场景 | [Epsilon](./gc/epsilon.md) |

回收阶段、并发与 STW 的关系先看[GC 总览](./gc/)。不要把历史参数复制到新 JDK，也不要把“低延迟”理解成没有停顿或没有容量限制。

## 从现象进入排查

| 现象 | 优先保留的证据 | 继续阅读 |
| --- | --- | --- |
| 订单导出导致堆 OOM | 输入规模、并发、GC 日志，必要时对象 dump | [堆](./runtime-area/heap.md)、[对象生命周期](./object-lifecycle.md) |
| 热部署后元空间持续增长 | 当前类与加载器趋势、旧加载器的保留路径 | [元空间](./runtime-area/method-area.md) |
| 网络缓冲失败或 RSS 高 | 完整异常、direct/mapped 池、OS 与 NMT 同时段数据 | [直接内存](./runtime-area/direct-memory.md) |
| 递归或线程异常 | 出错时的异常栈、当前线程 dump、OS 配额 | [虚拟机栈](./runtime-area/vm-stack.md) |
| native 崩溃 | `hs_err`、库版本、平台、输入与符号 | [本地方法栈](./runtime-area/native-method-stack.md)、[JNI](./jni.md) |
| CPU 高、启动慢或停顿长 | JFR、GC 日志、线程和负载时间轴 | [诊断案例](./diagnostic-cases.md) |

诊断命令需在正确的进程、用户和 PID 空间内执行。heap dump 与某些对象统计会造成停顿；没有启用的 NMT 也无法事后补出历史。采集方式和边界放在各机制页，避免只凭一条命令下结论。

## 阅读路径

首次接触从[动手入门](./hands-on.md)运行最小程序，再沿[Class 文件与字节码](./class-file-bytecode.md)、[类加载](./class-loading.md)、[执行引擎](./execution-engine-jit.md)、[运行时数据区](./runtime-area/)、[对象生命周期](./object-lifecycle.md)到[GC](./gc/)建立运行模型。随后用[诊断案例](./diagnostic-cases.md)练习把证据与假设连接起来。

版本演进、容器感知、CDS、JFR、虚拟线程与 Native Image 的范围见[现代 JVM 发展](./modern-jvm.md)；配套视频按[JVM 深入视频系列](./video-series.md)浏览。阅读目标是能解释真实请求的类型、调用、分配和回收，而不只是记住内存区域名称。

# JDK 与 Java 版本

同一份订单源码在电脑上编译成功，放进服务器却提示 `UnsupportedClassVersionError`，通常意味着生成的 class 比运行时支持的版本新。另一个更隐蔽的情况是 class 版本正确，代码却调用了旧运行时没有的 API。判断 Java 版本，需要同时看编译工具、编译目标、依赖和实际运行时。

本页负责版本地图与工具链关系；具体升级步骤见 [JDK 升级实践](./upgrade.md)，语法练习见 [Java 基础](../index.md)，内存和类加载机制见 [JVM](../../jvm/index.md)。版本状态以 **2026-10-20** 为界：JDK 27 已正式发布，JDK 28 属于早期访问版本；最近的 LTS 是 JDK 25。日常教程采用 JDK 17 作为示例基线，不表示生产项目都应固定在这个版本。

## JDK、运行环境与 JVM

![Java编译目标与运行环境的关系](/java/jdk-toolchain-contract.svg)

JDK 包含 `javac`、`java`、`jar`、`javadoc` 和诊断工具，以及标准库与 JVM 实现。JVM 负责加载并执行 class；Java SE 规范、HotSpot 实现与某个厂商构建的 JDK 发行包也不是同一层概念。

运行环境由 JVM、所需模块和本地运行库组成。历史上常见单独安装的 JRE；现代部署也可以直接采用 JDK，或使用 `jlink` 按模块生成运行映像。不能把“所有现代发行商都没有 JRE”当成事实，也不能把开发电脑上的整个 JDK 目录视为应用必须携带的唯一形式。

| 位置 | 应检查什么 | 订单服务中的例子 |
| --- | --- | --- |
| 开发机 | IDE 项目 SDK、终端 `java/javac` | IDE 使用 21，终端可能仍使用 17 |
| 构建机 | Maven/Gradle 的运行 JDK、编译工具链、目标 release | 构建工具运行于 21，业务代码可按 17 编译 |
| 产物 | class 目标版本、运行依赖、预览标志 | 主类按 17 编译，第三方 JAR 仍可能要求 21 |
| 部署机或容器 | 实际 `java` 路径、发行商、补丁号、架构 | CI 中的 `JAVA_HOME` 不会自动进入运行镜像 |

`JAVA_HOME` 指向一个安装目录，`PATH` 决定输入 `java` 时先找到哪个可执行文件。IDE、构建工具的守护进程和容器又可能各用一套配置；调整一个环境变量后，仍应在实际执行位置核对。

```bash
java -version
javac -version
java -XshowSettings:properties -version
```

最后一个命令可查看 `java.home`、发行商和编码等属性，信息通常写到标准错误流。构建工具的运行版本检查见 [Maven](../../manager/maven.md) 与 [Gradle](../../manager/gradle.md)；工具运行 JDK 与业务编译目标需要分别确定。

## 六个月发布与长期支持

现代 Java 按六个月节奏发布功能版本，通常在 3 月和 9 月。LTS 表示发行商对特定版本提供长期维护的政策，不是一种不同的 Java 语法。Oracle 当前列出的 LTS 包括 8、11、17、21、25，后续计划按两年节奏提供 LTS；具体补丁期限、平台、费用和授权条件仍须按选定发行商确认。

例如，使用 Temurin 21 与 Oracle JDK 21 的项目可以实现同一 Java SE 版本，但更新渠道和授权条件不能互相套用。也不能因为某个旧补丁包曾允许特定用途，就假设这一主版本未来所有补丁的条件完全相同。项目选型应记录发行商、完整补丁号、操作系统与 CPU 架构，并让 CI 和运行镜像可追溯。

新项目先核对框架、构建插件、驱动和可观测性代理是否支持 25，再决定采用 25 还是继续使用已验证的 21。已运行的 17 项目则需要明确补丁供应和迁移计划。JDK 27 已发布不等于所有项目都适合立即跟进；采用非 LTS 版本时，应有持续升级与维护安排。

## 对工程有影响的版本地图

版本表用于定位变化，不是要求逐级安装所有历史版本。正式迁移可以直接面向目标版本，遇到问题再用中间版本定位引入变化的位置。

| 版本范围 | 关键变化 | 对已有代码的影响 |
| --- | --- | --- |
| 5–7 | 泛型、注解、枚举、并发工具；try-with-resources、NIO.2 | 奠定类型约束和资源关闭方式，旧例子仍需完整导入和异常处理 |
| 8 | Lambda、Stream、`java.time`、默认方法 | 函数式操作没有自动解决副作用、并发或时区问题 |
| 9–11 | 模块系统、JShell、局部变量 `var`、标准 HTTP Client；移除部分 Java EE/CORBA 模块 | 依赖 JDK 内置 JAXB 等模块的项目需要显式依赖；模块路径与 classpath 不同 |
| 14–17 | switch 表达式在 14 正式；文本块在 15 正式；record 和 instanceof 模式在 16 正式；sealed class 在 17 正式 | record 的访问器不是 JavaBean getter；对 JDK 内部成员的反射可能受强封装阻止 |
| 18–20 | 默认字符集调整为 UTF-8；虚拟线程等能力经历预览 | 老文件编码要显式声明，预览代码不能按普通稳定 API 跨版本搬运 |
| 21 | 虚拟线程、模式匹配 switch、record 模式、Sequenced Collections 正式 | 虚拟线程适合大量等待型任务，仍需数据库连接数和下游并发上限 |
| 22–24 | 外部函数与内存 API、未命名变量/模式在 22 正式；Class-File API 在 24 正式 | 本地互操作需要核对生命周期；字节码工具必须识别新 class 格式 |
| 25 | Scoped Values、模块导入声明、紧凑源文件与实例 main 方法正式 | 新能力有自己的适用边界，应用不需要为了升级运行时立刻改写全部源码 |
| 26–27 | 后续六个月功能版本 | 按实际目标版本核对移除项、预览特性、依赖及发行商维护范围 |

预览特性与孵化 API 不是“已承诺会正式发布”的功能清单。字符串模板曾在 21、22 预览，但未进入 23，不能编写成“23 第三次预览”或把它当作稳定字符串写法。结构化并发也需要按目标 JDK 核对当时的状态和 API，不能直接复制跨版本的示例类名。

## 编译目标不能只看 class 版本

下面的 `ReleaseProbe.java` 是完整程序；它特意使用 JDK 11 才提供的 `String.repeat`，用于观察 API 基线检查。

```java
public class ReleaseProbe {
    public static void main(String[] args) {
        System.out.println("单".repeat(2));
    }
}
```

在本页的 JDK 17 练习环境中运行：

```bash
javac --release 8 -encoding UTF-8 ReleaseProbe.java
```

编译应因找不到 `repeat` 方法失败。`--release 8` 同时限制相应的语言规则、class 目标和公开平台 API，能在构建时暴露这种错误。若只用 `-source 8 -target 8`，编译器仍可能看到当前 JDK 的新 API，生成版本 52 的 class 后，在 Java 8 运行才抛 `NoSuchMethodError`。使用的编译器必须支持所选 release；新 JDK 不承诺永远保留所有历史目标。

把调用改成 `System.out.println("单单");` 后再次编译，并检查：

```bash
javap -verbose ReleaseProbe.class
java ReleaseProbe
```

目标 8 的 class 应显示 `major version: 52`，JDK 17 可以运行这个基础例子。常见对应还有 11→55、17→61、21→65、25→69、27→71。仅检查主类不能证明所有依赖兼容；`--release` 也不会替你验证第三方 JAR、本地库、运行参数或完整业务行为。

## 性能与版本选择的验收

不能根据版本号写固定的“启动快 30%”或把 GC 画成单向替代链。G1、ZGC、Shenandoah 等方案服务不同目标，是否可用还取决于版本、发行包和平台。先保留真实服务的基线，再在相同 CPU、内存配额、数据和流量下比较冷启动、预热后延迟、吞吐、GC 暂停、堆外内存与错误率。

例如，订单服务升级后压测吞吐提高，但连接池等待也增加，不能只记录总请求数；需要同时观察数据库连接、下游限流与请求失败。迁移涉及部署、回退和数据合同，继续阅读 [JDK 升级实践](./upgrade.md)。

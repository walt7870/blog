# Java 构建与依赖管理

订单服务新增一个客户端库后，本地编译通过，部署却抛出 `NoSuchMethodError`。问题可能是最终运行包里选中了另一个版本。再下载一次 JAR 并不能解释它：需要还原依赖解析、编译、测试、打包和运行之间的关系。

Maven 与 Gradle 都负责组织这些构建动作。本专题先讲项目模型与任务，再讲最终版本和产物如何验证；应用配置、数据库容量和服务编排分别由运行环境及部署平台管理。

## 构建不止下载依赖

![Java构建中的模型、解析、任务与产物边界](/java/build-contract.svg)

例如，一个库存 SDK 的源文件没有变化，但依赖版本、编译 JDK 或代码生成器变化，结果也可能变化。可重复构建需要固定工具和输入，并识别外部仓库、时间戳、环境变量等影响；“都有同一个 POM”或“启用了缓存”本身不保证输出相同。

| 工具 | 核心模型 | 阅读与操作入口 |
| --- | --- | --- |
| [Maven](./maven.md) | POM、生命周期阶段与插件目标 | 查看有效 POM，沿 `verify` 找实际执行的插件，用依赖树核对选中版本 |
| [Gradle](./gradle.md) | Settings、Project、Configuration 与任务图 | 查看任务依赖和可解析配置，区分 `UP-TO-DATE`、构建缓存与配置缓存 |

后端项目已有 Maven 规范时，先沿用并固定插件与工具链。Android 或任务定制较多的工程常用 Gradle，但仍要核对插件与 Wrapper 兼容性。选型依据包括现有生态、实际任务关系和维护成本，不能仅凭 DSL 更短或一次冷启动更快决定迁移。

## 先区分五种版本

构建工具版本、运行构建工具的 JDK、业务编译工具链、编译 release 和部署运行时可能各不相同。例如 Gradle 8.11.1 在 JDK 17 上运行，业务也以 17 编译；升级部署镜像到 21，不会自动改变编译目标。反过来，把源码目标提高到 21，也不会自动更新服务器的 `java`。

完整关系见 [JDK 与 Java 版本](../basic/jdk/)。框架插件还有单独的支持范围；先选一组可工作的基线，再一次改变一个因素，保留 CI 的版本输出与产物标识。

## 从错误反推入口

| 现象 | 应查看什么 | 不足以证明修复的现象 |
| --- | --- | --- |
| 依赖下载失败 | 坐标、仓库路由、镜像后的 ID、认证与失败缓存 | 换了镜像但不知道用了哪个来源 |
| 编译和运行版本不一致 | 最终依赖图、打包内容、启动 classpath | 编译依赖树看起来正确 |
| 测试没有运行 | 测试发现、引擎、跳过参数与报告中的执行数量 | 命令退出码为 0 |
| 多模块找不到兄弟模块 | 实际项目依赖与选择范围 | 手工复制旧 JAR 后暂时成功 |
| 构建重复执行或错误复用 | 任务输入输出、外部状态和缓存命中原因 | 加大堆或清空整个用户缓存 |

两个工具页使用同一个 [订单构建示例](/java/examples/order-build-lab.zip)，可以比较相同源码与测试如何被不同构建模型组织。先确认测试报告有执行用例，再检查 JAR 内容和运行结果；不把打包成功等同于应用已经能独立启动。

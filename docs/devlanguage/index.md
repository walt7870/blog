# 开发语言与运行平台

一个订单系统可能同时包含 Java 服务、浏览器管理界面、Flutter 客户端、Python 对账脚本，以及 Rust 数据处理工具。它们解决不同位置的问题，选型应先明确运行位置、现有生态和交付约束，再比较语言特性。

![订单业务中的语言与运行位置](/devlanguage/runtime-selection-map.svg)

## 按任务进入专题

| 专题 | 主要问题 | 典型例子 |
| --- | --- | --- |
| [Java](./java/) | 服务端业务、类型、构建、框架与 JVM | 订单事务、数据库访问、部署与运行诊断 |
| [Python](./python/) | 脚本自动化、数据处理与工具交付 | 合并对账 CSV，校验字段，输出失败行 |
| [Rust](./rust/) | 所有权、资源、并发与原生程序 | 有界批处理 CLI、校验输入与整数金额 |
| [Flutter](./flutter/) | 多平台客户端的状态、布局与发布 | 展示订单，处理请求竞态与离线草稿 |
| [前端](./front/) | 浏览器 UI、网络、构建与框架 | 后台列表、表单校验、权限与异步状态 |
| [Electron](./front/electron-series/) | 桌面应用的多进程与系统集成 | 本地文件工具、窗口和安全的 IPC |

嵌入式设备的电气、外设和实时约束单独进入[嵌入式开发](/docs/embedded/)，不与通用业务语言语法混写。

## 同一个需求怎样拆开

“每天核对订单金额”若是一次批量任务，可以先用 Python 读取和校验；若是现有 Java 服务的事务规则，应优先复用业务合同。浏览器负责错误定位和确认操作，客户端离线提交则需操作 ID 与服务端版本检查。语言不会自动补齐这些跨边界语义。

Rust 可生成原生可执行文件，但“一个文件”不代表无目标依赖：平台、架构、系统库、动态链接、证书和外部资源仍需核对。Flutter 共享 Dart/UI 代码也不等于免除各平台权限、签名和真机验收。性能瓶颈应先测量，不能仅因语言标签重写整条链路。

## 阅读与验证路径

先从各专题总览了解对象关系，再进入基础、工程化和运行机制。学习时选一个可交付的小任务：固定运行时与依赖，准备正常/非法/重复输入，运行测试，生成产物并在目标环境重跑。出现问题时保留原命令、首条错误和版本，沿构建、运行或业务阶段定位。

能独立说明为何选该技术、如何复现构建、如何识别失败和恢复，才算形成可迁移能力。团队已有成熟栈时，除非测量证明现有方案不满足约束，否则优先沿用其工具与运维经验。

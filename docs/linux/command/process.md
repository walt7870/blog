# 进程定位、信号与后台任务

订单导出卡住后，先找对进程，再决定如何观察和退出。名称相同的进程可能属于不同实例，PID 会复用，后台运行也不等于服务托管。本页讲操作的作用范围；进程创建、等待与僵尸机制见[进程专题](/docs/linux/process/)，常用入口见[进程速查](./process-management.md)。

## 用身份与启动关系定位目标

![终端作业、进程组与服务管理器对应的操作范围](/linux/process-control-scope.svg)

`ps` 是快照，`top` 是多次采样，`pgrep` 负责筛选候选对象。procps-ng 的 `ps -ef` 使用标准风格选项，`ps aux` 使用 BSD 风格；混用选项可能改变筛选语义。只运行 `ps` 通常按当前有效用户和终端筛选，并不列出“当前用户的全部进程”。

```bash
ps -eo pid,ppid,pgid,sid,stat,etimes,comm
pgrep -a -x bash
```

`pgrep` 无匹配时返回 1，不是工具故障。默认名称匹配和 `-f` 完整命令行匹配范围不同，后者还可能匹配包装脚本及无关参数；先查看候选进程的用户、启动时间、可执行文件与管理归属，再采取动作。`comm` 不是完整命令行，名称有长度等限制。`ps -p 进程号 -o pid,ppid,user,lstart,stat,args` 能补启动与参数线索，但参数可能含秘密，不应直接公开整份输出。

PID、PPID、PGID、SID 分别代表进程、父进程、进程组与会话。`pstree -p` 便于看父子关系，`ps -L -p 进程号` 或 `top -H -p 进程号` 可看线程；进程树不自动等于服务完整成员集合。容器内外的 PID 也可能不同，需先确认 PID namespace。

## 状态描述等待位置，不直接给出处置

| 状态 | 常见含义 | 下一步 |
| --- | --- | --- |
| `R` | 正在运行或可运行 | 看CPU、队列与配额，不只看一行快照 |
| `S` | 可中断睡眠 | 可能正常等事件，需关联请求进度 |
| `D` | 不可中断等待 | 查内核等待、设备与I/O；不保证能立刻响应信号 |
| `T`、`t` | 作业停止或追踪停止 | 核对终端操作与调试器 |
| `Z` | 已退出但尚未被等待回收 | 查父进程的wait逻辑，不再向僵尸发终止信号 |

`STAT` 还可能附带 `s`、`l`、`+` 等标记，不能只按整串等于 `Z` 来筛选。孤儿进程不必然异常；它可能由 subreaper 或 PID namespace 的 init 接管。僵尸与孤儿的处理见[进程生命周期](/docs/linux/process/)。给父进程补发 SIGCHLD 不会自动补上缺失的 `wait`，定时杀父进程也不能替代根因修复。

`%CPU` 在 `ps` 中通常是进程生存期平均，RSS 是驻留内存线索、VSZ 是虚拟地址空间，二者都不是“泄漏大小”。需要趋势时按[系统监控](./system-monitoring.md)对齐时间窗；增长趋势与应用对象保留、映射或分配器证据结合后，才能判断是否泄漏。

## 信号是请求，退出要验证

`kill` 的职责是发送信号。TERM 的默认动作是终止，但程序可以捕获、忽略或延迟处理；发送成功不代表任务已退出，更不证明订单已经提交或回滚。HUP 的默认动作通常也是终止，只有程序明确实现时才表示重载。KILL、STOP 不能被捕获或忽略，但 KILL 也不保证不可中断等待立即结束。

下面的 Bash 实验只操作本脚本刚创建的 `sleep` 子进程，展示暂停、继续、终止和等待；不使用从全系统名称搜索得到的 PID：

```bash
sleep 60 &
blog_child_pid=$!
ps -p "$blog_child_pid" -o pid,ppid,stat,comm
kill -STOP "$blog_child_pid"
sleep 0.1
ps -p "$blog_child_pid" -o pid,stat,comm
kill -CONT "$blog_child_pid"
kill -TERM "$blog_child_pid"
if wait "$blog_child_pid"; then
  printf 'child_status=0\n'
else
  printf 'child_status=%s\n' "$?"
fi
```

通常会看到停止状态 `T`，并得到 Bash 中 TERM 对应的退出状态 143。实际服务要先停止接收新请求、排空在途工作、保存必要状态，再在约定超时内退出；超时后是否强制终止应由服务合同决定。收到信号和业务完成是两个独立事实。

负 PID 可代表进程组，`kill 0` 也有组范围语义；复制命令前必须明确作用域。`pkill`、`killall` 按匹配范围发信号，可能同时影响多个实例。服务优先通过管理器控制，例如 `systemctl stop order-api`，并核对自动重启、定时器、socket激活或编排控制器是否还会重新拉起它。`kill -0` 仅提供存在性与权限线索，PID复用和检查后变化仍然存在；严格身份绑定应由管理器或支持pidfd的程序处理。

## 后台作业、会话与服务各管一层

| 方式 | 解决的问题 | 不具备的保证 |
| --- | --- | --- |
| `命令 &`、`jobs`、`fg/bg` | 当前shell的作业与前后台切换 | 终端退出后的存活、失败重启 |
| `nohup 命令 >日志 2>&1 &` | 忽略HUP并处理相应终端重定向 | 重启、依赖、资源隔离和业务就绪 |
| Bash `disown` | 调整shell作业表或HUP处理 | 已有I/O安全、服务可靠性 |
| tmux / screen | 保留可重新连接的终端会话 | 机器重启后恢复、服务健康检查 |
| systemd / 容器管理器 | 监督服务生命周期与资源 | 业务本身自动获得幂等与正确性 |

交互 Bash 中 `jobs -l` 查看作业，Ctrl+Z 通常使前台进程组暂停，`bg %1` 让作业在后台继续，`fg %1` 调回前台；`%1` 是当前 shell 的作业编号，不是 PID。后台任务读取控制终端可能再次停止。Ctrl+C 通常向前台进程组发送 INT，而不是遍历所有子进程。

人工长任务可用 `tmux new -s order-lab` 创建会话，Ctrl+B 后按 D 分离，`tmux attach -t order-lab` 重连；screen 对应 `screen -S order-lab`、Ctrl+A 后按 D、`screen -r order-lab`。这些组合键是交互操作，不是可粘贴执行的 shell 命令。持续提供订单接口的进程应使用[systemd](/docs/linux/process/systemd.md)等管理器。

## 优先级与诊断工具要按瓶颈选择

`nice -n 10 命令` 以较低调度优先级启动普通调度任务；`renice -n 10 -p 进程号` 修改已有目标。普通用户通常只能在权限允许范围内降低自身优先级，调高需要相应权限或资源限制。nice 不预留CPU，也不突破cgroup配额；实时调度 FIFO/RR 在 Linux 的静态优先级通常为 1–99，不应把普通调度的0当作实时等级。

`taskset` 控制亲和性，不能凭绑定两个CPU就声称性能翻倍；必须在允许CPU集内验证迁移、缓存和并发影响。`ionice` 的效果依赖I/O调度器、内核和设备栈，不能当作统一的磁盘带宽限额。未经测量不使用实时CPU或I/O类别来“加速”在线服务。

卡住时先检查状态、日志和有限采样。`strace` 可观察系统调用，`perf` 可采样热点，GDB附加通常会暂停目标；它们受权限、内核支持与运行开销约束，应在允许的窗口使用。`pmap`、`smaps` 展示映射与内存线索，不能直接证明泄漏；Valgrind通常需要在受控环境重新运行程序。验证最终应回到同一导出输入、正确结果、退出状态和重试行为，而不是只看到PID消失。

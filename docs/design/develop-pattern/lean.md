# 精益开发：从价值流中减少等待和返工

精益开发关注从需求到实际使用的整体价值流。订单导出的编码只用了半天，但需求澄清、评审和发布排队各等数天，那么加快编码并不会显著缩短交付。先识别主要等待和返工，再调整工作方式，才有可验证的改善。

精益思想强调消除浪费、放大学习、在必要信息到位时作决策、快速交付、授权团队、内建质量和优化整体。“延迟决策”是保留可行选项并明确最晚决策点，不是一直拖延；“减少浪费”也不等于删除测试和评审。

## 把流程画成价值流

![订单导出的价值流、等待与改进反馈](/develop-method/lean-value-stream.svg)

对每个工作项记录进入、开始处理和完成时间，区分实际处理与等待。假设某次需求澄清花半天、等待确认三天，代码实现一天、等待评审两天，验证半天、等待发布三天。这是一组示例数据，说明应先解决确认和队列，而不是据此推导所有团队的比例。

统计时先定义边界：需求提出到上线可称需求前置时间，开始实现到验收完成可作为团队周期时间，提交到部署可用于交付链路度量。名称可以不同，起止事件必须稳定，不能把不同口径混在一条趋势线上。

| 浪费现象 | 订单导出的表现 | 改进动作 |
| --- | --- | --- |
| 过量在制品 | 三种导出格式同时开工，都没完成 | 先交付一种格式，限制同时进行的任务 |
| 等待和交接 | 字段问题在多个部门之间流转 | 明确决策责任人，以具体样本确认 |
| 多余功能 | 还未试用就做复杂自定义模板 | 先验证对账用途，再决定是否扩展 |
| 返工 | 实现后才发现租户隔离要求 | 在任务开始前写权限示例和验收 |
| 手工重复 | 每次人工核对相同 CSV 字段 | 将稳定规则转为自动化检查 |

## 拉动、批次和质量如何配合

拉动意味着有下游容量才开始新的工作。评审积压时，继续生成更多代码会增加未完成库存；协助现有变更完成验证，比开新功能更有价值。WIP 限制需覆盖真实工作，包括紧急任务和 Agent 产出的差异，不能只限制人工开发卡片。

小批量让错误更早暴露，但批次不能小到只有无法验收的内部碎片。一个带权限和文件校验的小范围导出是有效批次，孤立的查询函数则需要放回业务切片中评估价值。

内建质量意味着在源头减少缺陷：在写查询时验证租户条件，在字段转换时验证金额和编码，在发布前验证恢复方式。省略这些检查会把成本转移到事故和返工，局部工时变少而整体成本上升。

## AI 提效要测整体结果

如果 AI 让实现从一天降到半天，但评审从一天变成三天，端到端交付反而可能更慢。原因可能是差异过大、重复抽象、测试预期不清或上下文不足。应缩小任务、提供现有模式和验收场景，再比较周期时间、返工和运行质量。

一种改进试验是：连续观察若干同类任务，记录起止、等待、差异范围、返工原因和缺陷；只改变一个主要因素，例如将大任务切为独立验收的增量。比较时说明任务复杂度和样本限制，不能用一次成功就宣称固定提效倍数。

## 改进如何闭环

回顾时选择一个明确瓶颈，给出负责人、动作和观察窗口。若评审等待最长，可试行更小差异、固定评审时间和 WIP 限制；若主要是权限返工，先改善规格和测试。下一次回顾检查等待是否缩短，同时确认缺陷和维护负担没有上升。

精益适合持续产品开发和维护流程，不要求先建立复杂工具平台。先用简单时间记录识别瓶颈，再按需要自动化。最终证据是用户更早获得可靠能力，而不是开发者始终保持满负荷。

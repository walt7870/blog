# 面向服务的架构（SOA）

SOA（Service-Oriented Architecture）把能力以明确的服务契约提供给其他系统使用，关注能力边界、互操作和生命周期治理。服务可以封装已有系统，也可以是新实现；ESB、SOAP、API 网关都是可选技术，不是 SOA 的定义。

例如连锁书店已经有商城、门店系统和旧 ERP。线上下单需要预留库存，门店调拨也需要同一库存能力。与其让两个渠道各自理解 ERP 内部表和状态码，可以提供稳定的“预留库存”服务，明确谁有权请求、怎样判重、成功代表什么、超时怎样查询。

## 服务不是一层数据库接口

“更新库存表某字段”暴露内部实现，消费者必须了解表结构、状态与并发规则；“为订单预留两本书”表达业务意图，服务提供者可以保护库存不变量并隐藏 ERP 协议。粒度要足以表达可独立理解的能力，过粗的万能接口和过细的远程字段读写都会增加耦合。

服务契约除了输入输出，还要解释业务结果与失败。`200` 可以表示请求已受理，但不能在未完成预留时被解释为库存已锁定；异步接口应返回操作编号，提供状态查询或可靠结果事件。

| 合同部分 | 预留库存需要约定什么 |
| --- | --- |
| 身份与范围 | 哪个渠道、租户和门店可以操作哪些库存 |
| 请求语义 | 商品、数量、预留期限；不接受调用者随意覆盖可用量 |
| 幂等 | 相同业务操作使用稳定标识，不同请求内容复用标识应拒绝 |
| 业务结果 | 已预留、库存不足、处理中、冲突与权限拒绝 |
| 时间与容量 | 延迟目标、请求配额、超时预算、峰值承载范围 |
| 恢复与版本 | 查询、确认、释放、过期与新旧合同共存策略 |

服务级别目标和承诺必须有测量范围，例如只统计服务受理阶段，还是包括 ERP 真正完成。上游等待 2 秒、ERP 常需 30 秒的场景，需要重新设计受理与完成合同，不能单纯把网关超时调大。

## ESB、网关与防腐适配各做什么

API 网关常处理边缘路由、认证、限流与部分协议入口；ESB 常用于消息路由、协议和数据格式转换及集成编排。产品能力可能重叠，但两者不是同一个概念，也不保证安装后就有正确业务边界。

库存防腐适配负责把旧 ERP 状态码、货号和错误转换成服务合同中的概念。例如旧系统的 `LOCKED` 可能指盘点冻结，不能直接当作订单已预留。语义映射应由了解库存业务的负责人确认；纯 JSON/XML 格式转换无法解决含义差异。

集成编排可以协调多个步骤，但订单可否取消、库存可否释放等规则应由对应业务能力保护。若把所有规则、数据映射和补偿塞进中心总线，业务变化都要排队修改总线，中心也会成为共同故障和发布风险。路由与编排需要明确责任，不应成为无人维护的业务规则仓库。

同步请求、异步消息和批量文件都能承载服务协作，选择取决于业务承诺和系统能力，不必所有通信都经同一总线。批量文件同样要定义文件编号、重复检测、校验、部分失败与对账规则，不能因不是 API 就跳过合同治理。

## 超时与跨系统一致性

商城请求预留，ERP 已成功但回复丢失时，商城只知道结果未知。服务需通过稳定操作标识查询或核对；直接重试成一次新预留会多锁库存。若 ERP 不支持幂等或查询，中间适配器中的本地去重也不能消除“远端已成功、本地未记录”的窗口，需要补充可核对的业务标识、操作串行策略或人工处理，并写明能力边界。

编排器的事务通常不能覆盖旧 ERP、支付和消息系统。业务允许中间状态时，持久化流程进度、按合同补偿；补偿本身可能失败，应有继续处理和核对入口。已经发货或已收款不能被一个接口回滚成“从未发生”。详细协作机制见[微服务架构](./microservices-architecture.md)与[事件驱动架构](./event-driven-architecture.md)。

## 契约治理要落到负责人和证据

服务目录记录能力含义、维护者、使用者、接口版本、权限入口、运行目标与退役计划。它不必是昂贵平台，但必须能回答“这个字段由谁解释”“谁还在调用旧版”“失败由谁接手”。运行地址发现和业务目录是不同职责，健康检查通过也不证明一次预留能成功。

变更前用消费者清单与契约测试评估影响；新旧版本并行期间观察实际调用，再安排迁移和退役。不能只发一份接口公告就删除旧字段。共享词汇应有明确范围，不要强迫商城、会员和财务共用一个无限膨胀的 `Customer` 或 `Order` 对象。

认证身份需要在跨系统转换中保持可验证的调用责任；对象和租户授权由业务入口核验。共享账号或任意透传一个 `tenantId` 字段不能建立可信授权。审计至少关联业务操作、调用主体、决策、系统结果和恢复动作，避免记录密码、密钥或完整个人资料。

## 从一条能力开始改造

先选择预留库存这一条路径，记录现有调用者、接口和直接改表位置。建立能力合同与适配器，用受控样例验证 ERP 语义；逐个迁移调用入口，核对新旧路径的结果与写入归属。已有预留的确认和释放要保持生命周期归属，不能只切新建请求。

| 验收项 | 要看到的证据 |
| --- | --- |
| 结果未知后重试 | 原操作可查询或进入核对，不新增第二份预留 |
| 总线或 ERP 不可用 | 队列、并发与超时有界，失败状态可见且能恢复 |
| 一批请求部分失败 | 成功与失败可逐项定位，不整批静默覆盖 |
| 旧消费者继续运行 | 版本合同兼容，未未经确认删除旧字段或语义 |
| 停止新路径分流 | 存量操作仍能确认、释放或进入补偿 |

选择是否采用中心总线，应比较现有系统的协议差异、转换重复、治理需求和运行成本。系统很少、接口稳定时，清晰的直接服务调用可能已经足够。SOA 与微服务都可以采用轻量协议、独立部署和异步事件；前者常强调跨系统能力复用，后者常强调独立交付和数据所有权，不能只按服务大小或 SOAP/REST 划线。

REST 是架构风格，SOAP 是消息协议，GraphQL 是查询语言与执行体系，gRPC 是 RPC 框架，不能把它们都当作同层的“轻重协议”。技术选择应跟随既有客户端、消息语义、性能与安全约束。服务内部仍然可以使用[分层](./layered-architecture.md)或[六边形架构](./hexagonal-architecture.md)，无需为 SOA 再造一套固定技术层。

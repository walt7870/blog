# 软件架构设计导论

软件架构决定业务规则、代码依赖、数据所有权和运行责任如何分布。选型应从具体问题出发：一次订单修改影响哪些模块，一次支付失败由谁恢复，一个团队能否独立发布。不同方法回答不同问题，可以组合使用。

![架构决策的四个维度和对应方法](/architecture/architecture-map.svg)

## 先区分正在解决什么

分层与六边形组织代码依赖，DDD 分析语言和模型，微服务划部署与所有权边界，CQRS 分离读写模型，事件驱动传播事实，云原生管理动态运行和交付，TOGAF 连接企业目标与架构治理。它们不是同一条升级路线上的不同档位。

例如一家小书店只有三个开发者，但退换货规则已经复杂：可以在模块化单体内用 DDD 保护规则、用六边形隔离支付。活动期间访问量突增，可以对这个单体做容器化、容量治理和自动发布。只有某项能力确实需要独立扩容或独立交付时，才进一步评估拆服务。

![业务与组织复杂度下的候选起点](/architecture/selection-matrix.svg)

矩阵只是讨论起点。团队多不自动要求微服务，能接受延迟也不意味着必须引入消息系统。数据归属、强一致规则、运维能力和总成本会改变选择。

## 从约束到可验证决策

![围绕订单规则与发布约束逐步形成架构决策](/architecture/decision-flow.svg)

订单与明细总额必须同时正确，可以放在本地事务中；支付渠道收款和订单接受支付是跨边界事实，需要幂等、核对与补偿。若跨服务强一致成为主要瓶颈，应重新检查边界，也可以评估明确代价的协调协议，不能只靠“最终一致”标签回避业务要求。

每项决定记录触发问题、约束、候选方案、采用理由、失败模式和复验条件。例如“库存查询拖慢结账，所以增加读模型”的前提应包含允许陈旧多久、付款前如何确认库存，以及投影积压怎样被发现。完整验收要覆盖失败，而不只是正常请求吞吐。

## 演进由证据触发

![从明确边界出发按约束选择的演进分支](/architecture/evolution-roadmap.svg)

可以长期保留模块化单体，也可以先补观测和发布，再拆服务。DDD 不是每个业务都要采用，微服务也不是云原生的前置阶段。某个分支没有改善修改范围、交付等待、恢复时间或总成本，就应停下来重新评估。

上线前沿关键业务核对：谁能修改数据，哪个提交边界保护规则，网络超时代表失败还是未知，重试是否重复副作用，旧版本能否识别新状态，以及日志和事件能否关联到同一次操作。能解释这些问题的图和代码，才构成可执行的架构约束。

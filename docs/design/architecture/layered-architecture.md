# 分层架构（Layered Architecture）

分层架构按职责组织代码，并约定哪些依赖可以跨越边界。订单接口接收取消请求，应用服务加载订单并管理事务，订单判断是否允许取消，持久化代码把结果写入数据库。分层的价值是修改一项规则时能找到负责的位置，而不是目录中必须有四个文件夹。

## 用订单取消确定职责

客户取消尚未付款的订单时，接口先解析身份、订单编号和参数；应用服务检查客户是否有权操作这张订单，在事务中加载当前状态，调用订单的取消行为并提交。订单自身保护“已发货不能取消”等状态规则；仓储实现处理 SQL、版本条件和对象映射。

| 职责 | 取消订单例子 | 需要避免的问题 |
| --- | --- | --- |
| 表示层 | HTTP 参数转换、身份提取、错误响应 | 从请求体直接相信客户或租户身份 |
| 应用层 | 对象授权、加载、调用规则、事务编排 | 把状态规则分别复制到接口和定时任务 |
| 业务或领域层 | 订单能否取消、取消后的状态 | 为查询数据库而隐式打开连接 |
| 持久化与技术实现 | 条件更新、映射、Outbox、外部接口 | 用无条件更新覆盖其他事务的付款结果 |

简单后台可以用业务服务集中少量规则；规则复杂后，再把行为移入领域对象。四层 DDD 是一种可用组织形式，传统表示层、业务层、数据访问层也属于分层架构。层数取决于实际职责，不能用是否存在 `domain/` 判断设计质量。

## 调用方向与源码依赖

传统分层常让业务服务直接依赖数据访问接口或实现，调用大体从表示层到业务层，再到持久化层。采用依赖倒置时，核心定义仓储契约，基础设施实现契约，装配入口把实现注入用例。两者在运行时都可能访问数据库，但源码依赖方向不同。后一种组织与[六边形架构](./hexagonal-architecture.md)可以结合。

下面采用核心拥有仓储契约的形式，先按业务模块组织，再在模块内分层，避免整个项目只有几个巨大技术目录：

```text
order/
  interfaces/CancelOrderController.java
  application/CancelOrderService.java
  domain/Order.java
  domain/OrderRepository.java
  infrastructure/JdbcOrderRepository.java
bootstrap/OrderConfiguration.java
```

`OrderRepository` 定义取回与保存订单所需的业务合同，`JdbcOrderRepository` 实现数据库细节。数据库本身是运行组件，不是一个必须与代码层逐层对应的软件包。若 ORM 映射直接放在领域对象上，应评估会话、懒加载与注解是否把隐式 I/O 带入规则；使用独立持久化对象也会增加映射成本。

## 事务必须保护竞争条件

把代码移到不同层不会自动保证付款与取消互斥。两个事务都可能读到“待付款”，因此应在保存时使用状态条件或版本检查。下面是同一数据库中取消动作的 SQL 机制片段，参数绑定和完整事务代码省略：

```sql
UPDATE orders
SET status = 'CANCELLED', version = version + 1
WHERE id = :order_id
  AND tenant_id = :tenant_id
  AND status = 'WAITING_PAYMENT'
  AND version = :expected_version;
```

影响行数为 1 才表示这次状态变更成功；为 0 时应重新加载并判断是重复取消、状态不允许还是版本竞争，不能直接返回“已取消”。对象授权仍需由用例完成，SQL 中的租户条件是额外保护。若取消后需要释放库存，应在同一事务记录可靠发送意图，提交后再投递；不能把远程库存调用误认为本地事务的一部分。完整竞争与 Outbox 机制见[订单支付实践](./DDD/practice.md)。

事务入口通常在应用用例，数据库约束与仓储提交共同落实规则。不要为了“业务逻辑集中”把慢速网络调用包进长事务，也不要让每个仓储方法各自提交而破坏一个用例的原子性。

## 严格分层与开放分层

严格分层只允许调用约定的下一层；开放分层允许某些场景跨越中间层。是否允许跨层应按用例说明。例如报表查询可以走专门的查询服务，直接组合数据访问结果，不必加载用于状态变更的完整订单聚合；但仍然要经过授权、查询范围和资源限制。

跨层不必然提升性能。相同进程内的普通方法调用通常不是主要瓶颈，重复查询、过量映射、序列化和网络往返更值得测量。若接口绕过业务入口直接改表，节省的几行代码会让状态规则失去统一保护。读写模型差异较大时可进一步阅读 [CQRS](./cqrs-architecture.md)，无需先拆成两个数据库。

## 分层不等于分布式部署

代码分层与运行部署是两种边界。一个微服务内部也可以分层；单体中的多个业务模块可以在一个进程内共享部署。不要为了与目录对应，把 Controller、Service、Repository 分别部署为网络服务，这会让每次请求增加远程依赖，并让事务和发布更难协调。

是否拆服务，应看业务所有权、独立交付与扩缩容需求，见[微服务架构](./microservices-architecture.md)。是否容器化和自动发布，应看运行合同和恢复能力，见[云原生架构](./cloud-native-architecture.md)。分层本身不要求固定技术栈，也不承诺故障隔离或自动扩容。

## 验证与排错

从一次取消请求沿调用链检查：接口有没有只信任服务端身份，用例有没有核对订单归属，状态决策有没有唯一入口，保存有没有竞争保护，事务提交后有没有留下跨系统任务。看到“层都齐了但规则失效”，优先检查是否存在绕过用例的批处理、直接改表和重复状态判断。

核心规则可用内存对象验证；仓储必须另测真实数据库的条件更新、约束和回滚；关键路径再验证付款与取消同时发生、重复请求以及提交后进程退出。内存替身通过不能证明生产 SQL 正确，HTTP 成功也不能代替核对最终订单状态与库存处理记录。

当 Service 很长时，先判断混合的是协议、规则、查询还是流程，不要只把一个大类拆成几个同样耦合的类。规则简单、变更集中、测试能覆盖主要失败场景时，保持清晰分层即可；只有证据显示边界失效，才投入更复杂的建模或服务拆分。

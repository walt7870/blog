# 事件驱动架构（Event-Driven Architecture）

事件驱动让系统围绕已经发生的事实作出响应。书店订单接受付款后，库存确认预占，积分系统发放权益，通知系统发送消息。订单不必知道每个后续动作的实现，但发布者与消费者仍然依赖事件合同、数据语义和失败处理。

事件可以在同一进程内同步分发，也可以经过消息系统异步传递。本页讨论持久化消息支持的跨模块、跨服务协作；选择异步表示允许处理延迟，并不自动获得可靠性、实时性或完整审计。

## 事实、命令与通知

`OrderPaid` 表示订单已经接受一笔付款，`ConfirmReservation` 请求库存确认预占，后者仍然可能被拒绝。事件的发布者负责事实含义，命令的接收者负责决定是否执行。消息是传输载体，可以装事件，也可以装命令，不能只凭“走 MQ”判断语义。

支付渠道已收款与订单已接受支付是两个事实。订单关闭后收到迟到付款，系统应记录核对或退款任务，不能发布一个并未成立的 `OrderPaid`。如果名称只写 `PaymentProcessed`，消费者不知道它表示收款、核验、入账还是退款；应把状态含义写清。

事件通知可以只带标识，让消费者查询详情；这样消息小，但消费者依赖查询服务，且查询到的可能是最新状态。事件携带所需的事实快照，可以降低回查依赖，但会增加数据副本、敏感信息和版本演进成本。两者都不应未经判断复制整个数据库行。

## 事件合同要包含什么

下面是业务事件示例，不绑定某个消息中间件，也不是完整的 CloudEvents 规范实现。金额用整数分，编号、时间和数量均为示例数据：

```json
{
  "eventId": "evt-order-1042-paid-1",
  "eventType": "OrderPaid",
  "schemaVersion": 1,
  "occurredAt": "2026-10-19T08:00:00Z",
  "tenantId": "tenant-demo",
  "orderId": "order-1042",
  "orderVersion": 8,
  "paymentId": "payment-2048",
  "amountMinor": 5000,
  "currency": "CNY",
  "correlationId": "checkout-demo-17"
}
```

`eventId` 在发送重试时保持稳定；同一事件投到不同订阅者，各自拥有独立消费进度。`orderVersion` 是业务对象版本，不是 JSON 结构版本；它能提供排序线索，但如果此订阅只接收部分订单事件，版本跳号不一定表示漏消息。发生时间也不保证可按全局时钟严格排序。

新增可选字段仍需验证旧消费者是否允许未知字段；删除、改名、单位或含义变化通常需要新版本及迁移期。事件记录不应被静默改写；事实更正用新的更正事件或明确的业务修复表达。个人数据的访问、保留与删除还需独立设计，不能用“不可变”无限保留敏感数据。

## 先可靠提交，再可靠投递

先提交订单再直接发消息，进程可能在两步之间退出；先发消息再提交，消费者可能收到最终回滚的事实。常见做法是在订单同一个数据库事务中写入 Outbox，再由独立投递器发送已提交记录。也可以用合适的 CDC 读取可靠变更，但原始行变化不天然等于稳定业务事件。

投递器得到消息系统确认后标记已发送。确认或标记丢失会重发，因此消费者仍须幂等。发布确认只表示消息系统按配置接收了消息，不代表所有消费者完成业务动作。完整时序见[订单支付实践](./DDD/practice.md)，中间件的确认与消费机制见[消息队列](../../tools/mq/)。

消费者处理数据库内业务效果时，可以把去重记录与业务更新放入同一事务。机制顺序如下，具体唯一约束与错误分类由实现决定：

```text
开始事务
  尝试记录 (消费者名称, eventId)，已有记录则结束重复处理
  核验租户、业务标识、事件版本和当前状态
  提交业务变化；必要时同时写下一步 Outbox
提交事务
确认消费完成
```

如果先记“已消费”再执行另一个独立事务，进程退出会永久跳过业务；先执行效果再独立记去重，则可能重复执行。远程发短信、扣款等不在本地事务中，还需要接收端幂等、稳定操作标识和结果核对，不能靠一个去重表获得跨系统原子性。

## 订阅、顺序和积压

同一个工作队列的多个消费者通常分担消息；需要库存和积分都收到同一事实，应创建独立订阅、队列或消费组。增加同组消费者不能突破分区数量、串行规则、数据库锁或下游配额的限制。

订单状态有先后要求时，可以按订单标识选择分区或分组，并在消费者核对当前状态。局部顺序不等于所有订单的全局顺序；重试、重放和多个来源仍可能造成重复或乱序。对于状态快照可以按对象版本拒绝旧快照覆盖新状态；对于“增加积分”这样的增量动作不能简单跳过旧版本，需要处理缺口或核对源记录。

瞬时网络失败可做有限重试与退避，格式错误、未知版本和违反合同的消息应隔离并告警，避免毒消息无限阻塞整条链。死信只是保存失败的入口；还需明确谁修复、怎样重放、怎样避免副作用重复。积压应同时看数量和最老消息年龄，后者更接近用户等待时间。

## 重放不是自动回滚

有保留期、权限和偏移控制的事件日志可以支持重放，普通消息队列并不都提供历史查询。即使能读取旧消息，重放也不等于恢复任意时点状态，更不能撤销已发送的邮件、优惠券或资金操作。

重建报表时优先写入新的投影并比较水位与校验结果，确认后切换查询；不要直接把历史付款事件重新送进生产发券入口。需要给一个历史订单补发遗漏权益时，应有明确业务操作标识、去重策略、范围和审计记录。重放逻辑要区分纯计算与外部副作用。

[CQRS](./cqrs-architecture.md) 可以通过事件维护读模型，也可以采用同库独立模型；事件溯源把事件流作为状态的事实来源；复杂事件处理关注窗口、聚合和模式识别。它们都不是事件驱动必须依次升级的阶段。若业务只需要付款后发一条通知，可靠任务表可能已经足够。

## 从用户现象排查

用户看到已支付却没有积分时，先核对订单是否接受付款、对应事件是否同事务写入，再检查投递确认、订阅路由、消费位置、去重记录与权益结果。用订单号、事件号和关联号串起证据；队列为空不能单独证明消息从未产生，也不能证明处理成功。

| 失败场景 | 必须能解释的结果 |
| --- | --- |
| 订单提交后进程退出 | Outbox 仍在，重启后继续投递 |
| 消息已接收但发送确认丢失 | 可以重发，同一订阅业务效果不重复 |
| 消费事务已提交但确认丢失 | 重投被正确识别，不能再次发放权益 |
| 先收到新状态，再收到旧状态 | 不倒退状态；增量事件按缺口策略处理 |
| 消费者持续失败 | 有隔离、告警、修复和可控制的重放入口 |
| 事件合同升级 | 新旧消费者在迁移期可按约定运行 |

这些是需要实际执行的验收条件。只验证正常消息能到达不足以证明可靠性。必须立即给出权威结果或维持同一事务的规则，应保留同步或本地提交边界；允许延迟、需要独立后续响应的部分，再考虑异步事件。

# 微服务架构（Microservices Architecture）

微服务围绕业务能力划分可以独立交付的运行单元，每个单元有明确的数据责任和维护者。目标是让需要独立变化的部分能够独立发布、扩容和恢复；进程数量、代码行数和使用多少种语言都不是判断标准。

例如书店的订单规则每周变化，仓库对接系统只能在夜间发布，商品搜索又需要单独扩容。如果这些约束长期互相阻塞，可以评估拆开相应能力。三个开发者维护的小书店，通常先把模块和写入权理清，比立即引入多套部署更有收益。

## 先确定数据和规则的主人

订单负责成交快照与订单状态，库存负责预占、扣减与释放，支付负责渠道交易和核对。订单调用库存能力，而不是直接修改库存表。支付服务确认渠道已经收款，也不代表订单一定可以接受该付款：订单可能已关闭，需要进入核对或退款流程。

“每服务一库”首先强调数据所有权，不要求每个服务单独购置数据库服务器。可以在同一数据库实例上使用隔离的数据库或 schema、账号和权限；仍需评估资源争用、备份和故障的共享范围。多个服务共写同一核心表、跨库直接 JOIN 内部表，会使发布和模型变更重新绑在一起。

| 划分线索 | 需要核对的证据 | 容易误拆的方式 |
| --- | --- | --- |
| 独立变化 | 业务规则、发布节奏、负责人长期不同 | 按 Controller、Service、DAO 各建服务 |
| 独立容量 | 某能力持续消耗不同资源，整体扩容成本高 | 仅因一个接口慢就拆网络服务 |
| 数据责任 | 谁解释事实，谁能提交状态，谁处理异常 | 按每张表或每个聚合各建一个服务 |
| 故障范围 | 可以接受哪些功能降级，资源是否真正隔离 | 进程拆开但共享无限连接池和重试风暴 |

[DDD](./DDD/) 能帮助发现语言与规则边界，但限界上下文、聚合与部署单元不必一一对应。同一上下文可以先保留在模块化单体中；拆分应同时交付接口、数据归属、运行责任和恢复方案。

## 同步与异步取决于业务承诺

如果下单必须立即知道是否预占成功，可以调用库存的预占接口，设置整体超时预算，并保留预占编号。如果权益发放允许稍后完成，可以在订单接受支付后可靠发布事实，由权益服务异步处理。查询不总是同步，写入也不总是异步。

同步调用超时只说明调用方未及时得到结果，不能断定远端未执行。写操作应有稳定的幂等键和结果查询路径；相同键对应不同请求内容时应拒绝。异步消息也不会自动保证成功，需要发送意图持久化、重试、去重、状态检查和长期失败处理，见[事件驱动架构](./event-driven-architecture.md)。

下面是接口合同示意，不是可直接部署的 OpenAPI 文件：

```text
POST /reservations
身份：服务身份 + 经授权的业务/租户上下文
幂等键：同一订单、同一预占尝试保持不变
请求：订单编号、商品数量、预占策略
结果：已预占 / 资源不足 / 处理中 / 请求冲突
恢复：按幂等键查询；明确过期、确认与释放条件
```

不要把所有失败都映射为“库存不足”。权限拒绝、参数冲突、明确资源不足和结果未知需要不同决策；在结果未知时生成新幂等键重试，会创建第二份预占。服务端也必须核对调用者是否有权操作对应租户和资源，网关认证不能替代对象授权。

## 跨服务事务与补偿

订单和库存各自在本地事务保护规则；两个服务的本地事务不会自动合成一个原子事务。业务允许中间状态时，可以记录流程状态并用 Saga 协调步骤和补偿，例如预占成功但订单创建失败后发起释放。补偿是新的业务动作，可能失败、延迟或受规则限制，并不等于数据库回滚。

若业务必须跨边界立即保持严格一致，应先检查边界是否划错；确有需要时评估有明确参与者和故障处理的协调协议，不能单靠“最终一致”放宽业务承诺。CQRS 和事件溯源分别解决模型组织与状态保存问题，也不是跨服务事务协议。

流程记录需要关联订单、预占、支付和消息标识，支持超时扫描与人工核对。只有记录“当前执行到哪一步”，重启后才知道应继续、查询、补偿还是停止。付款已发生但订单被关闭时，不能靠回滚订单对象抹掉资金事实，见[支付与超时关闭实践](./DDD/practice.md)。

## 独立部署需要兼容契约

独立发布依赖生产者与消费者在一段时间内兼容。新增可选字段通常比删除字段容易，但还要验证旧客户端是否拒绝未知字段、空值语义是否变化、枚举扩展是否安全。数据库迁移可以先扩展兼容结构，部署新旧都能运行的代码，完成迁移和观察后再收缩旧结构。

服务发现解决地址定位，负载均衡分配请求，网关处理边缘路由和部分认证，配置管理分发有版本的配置。它们都不能定义业务接口是否兼容。微服务不强制 Kubernetes、Service Mesh、注册中心或多语言；已有 DNS、负载均衡和自动部署足够时，无需先叠满组件。

回退镜像前要验证旧代码能否读取新数据和事件。已经扣款、发券或发送通知的副作用不会随镜像回退撤销。发布验收应同时核对协议、数据迁移、权限和恢复路径，而不只看容器是否启动。

## 故障隔离要靠资源和失败策略

拆进程提供隔离机会，但长同步调用链、共享数据库和无界重试仍会传播故障。调用方应设置超时预算、并发与连接池上限，对允许重试的操作做次数限制、退避和抖动；避免网关、客户端和服务层同时无限重试。

熔断可以暂时阻止继续压向失败依赖，不能修复业务数据。推荐服务不可用时可以展示默认列表；付款结果未知时应返回处理中并继续核对，不能“降级”为支付成功。降级策略必须尊重每条业务的承诺。

观测从业务操作出发：用订单与事件编号关联日志，用 trace 串起同步和异步链路，用错误率、延迟、队列年龄和核对积压判断影响。指标标签不要直接使用海量订单号或用户标识；日志也不应保存密钥和完整敏感支付资料。

## 渐进拆分与验收

先在现有应用内建立模块接口和数据写入边界，再选择独立收益明确的一项能力。旧入口可以路由到新实现，但同一订单的回调、查询、关闭和补偿必须保持处理归属。数据迁移应有快照与增量衔接、重复处理和核对水位，避免用未经设计的双写维持两个主人。

| 验收场景 | 要验证的结果 |
| --- | --- |
| 新旧版本同时运行 | 契约兼容，旧消费者不会丢失关键字段语义 |
| 远端成功、响应丢失 | 稳定标识可查询，不重复扣款或预占 |
| 一个依赖持续超时 | 超时与并发受限，其他业务仍有可测的服务能力 |
| 消息重复和进程重启 | 业务效果不重复，流程可以继续或进入核对 |
| 停止向新服务分流 | 已接管订单仍能完成生命周期，回退数据兼容 |

同一套内存单元测试不能证明网络、数据库和消息系统的合同正确；需要契约验证、适配器集成与失败路径验收。拆分后应比较发布等待、变更影响、恢复时间和总成本。如果协作成本增加却没有独立交付收益，应重新合并边界或保留模块化单体。

SOA 同样关注面向能力的服务契约与复用，不能简单按“微服务轻协议、SOA 重协议”区分。需要跨企业现有系统集成时继续阅读 [SOA](./soa.md)，需要动态交付与恢复机制时阅读[云原生架构](./cloud-native-architecture.md)。

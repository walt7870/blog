# 领域划分与遗留改造笔记

老交易系统里，“改订单”可能同时更新价格、库存、支付和发货表。新需求一来，所有模块都要跟着改。拆分的起点是找出这些修改为什么一起发生：是业务必须同步成立，还是旧代码顺手放在一起。前者需要保护一致性，后者才可能通过边界拆开。

## 用变化证据确定边界

以“下单后修改地址”为例，未出库时可能直接改收货快照，已出库后则要向物流申请改派。这两种动作名称相近，权限、状态和失败处理却不同。订单负责购买承诺与快照，履约负责包裹和承运规则，不能用一个通用 `updateAddress` 绕过它们。

| 证据 | 应追问的问题 | 不能直接得出的结论 |
| --- | --- | --- |
| 两组规则经常独立变更 | 是否使用不同语言、生命周期和验收方式 | 每组规则都要独立微服务 |
| 多张表每次一起写 | 是业务不变量，还是调用方式造成耦合 | 一起写过就必须同一聚合 |
| 两部门使用同一个名词 | 含义是否相同，谁拥有最终解释权 | 组织架构就是上下文图 |
| 报表组合多个模型的数据 | 刷新延迟、历史口径和授权由谁负责 | 报表不创造价值，必须独立子域 |
| 需要调用第三方服务 | 外部状态和内部规则如何转换 | 直接复用第三方 DTO 为领域模型 |

子域按业务能力分析，限界上下文按语言和模型划分。报表可以是简单投影，也可以是承担风控或经营决策的核心分析能力。读写分离是一种模型与负载设计，不能单独决定子域的重要性。详细对象关系见 [模型说明](./model)。

## 选择一条可切换的用例

先改“接受支付事实”这样的窄用例，比同时重写整个订单系统更容易验证。旧接口前增加明确路由，新模块通过防腐层把旧状态码转换为业务概念。它可以仍在同一进程，优先让状态修改入口和事务边界清楚。

![从遗留用例证据到分段切换与恢复的改造步骤](/architecture/ddd-legacy-migration.svg)

绞杀者改造逐步把入口转向新实现，但路由切换必须考虑已有订单仍处在旧生命周期中。可以按订单来源或稳定分组确定处理者；同一订单的回调、查询、关闭任务和补偿必须遵守同一归属，不能每次请求随机选择写入系统。

影子验证阶段让新模型读取脱敏回放或受控副本，比较领域决策；不允许它重复扣款、发券和发通知。若需要迁移数据，先定义标识映射、快照与增量的衔接、重复事件处理和校验水位。不要用“新旧系统双写”掩盖半成功状态。

## 处理写入权和回退

切流前要明确哪个实现拥有订单状态，另一个只能通过接口或只读投影使用。两边都直接写同一张表，或者一边更新一边用同步脚本覆盖，会让领域边界只停留在目录里。跨边界协作用契约表达，可靠投递和幂等机制见 [支付实践](./practice)。

回退需要区分流量和数据：停止给新模块分配新订单，不代表已经由它接管的订单可以马上交回旧程序。旧程序若不能识别新状态或事件，就应让新模块继续处理已有生命周期，或经过兼容转换后再移交。数据库结构迁移、外部扣款和已发权益也不能靠回滚镜像撤销。

## 以失败场景验收

至少验证支付与关闭竞争、重复回调、提交后进程退出、消息确认丢失、切流中同一订单重试以及旧数据回放。核对状态、版本、Outbox、支付流水和业务效果是否可关联；不能只比较接口返回码。

当一个窄用例能独立解释规则、证明并发正确并完成恢复，再扩大改造范围。长期没有变化且运行可靠的模块可以继续保留。领域设计的收益应体现在修改范围和故障恢复能力上，而不是新建了多少服务。

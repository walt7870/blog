# 领域驱动设计总览

DDD（Domain-Driven Design）用于把复杂业务规则变成可讨论、可实现、可验证的软件模型。它首先回答“订单、支付、库存各自拥有什么事实”，再决定规则放在哪个对象、模块和提交边界里。目录中出现 `domain` 并不能证明建模已经完成。

![从业务事实到边界、聚合和验证的建模路径](/architecture/ddd-overview.svg)

## 用一次购买理解两层设计

小林买两本书。下单时订单记录商品名称、成交价和收货地址快照；库存按本场景规则先预占两本；支付系统确认收款后，订单接受支付事实，库存确认扣减，履约开始准备包裹。库存不足、迟到的支付回调、重复通知，都需要有明确的处理者。

**战略设计决定模型在哪里成立。**“商品”在商品中心是可售资料，在库存中是某仓库的库存单位，在订单中是成交快照。子域分析业务能力及其重要性；限界上下文划定语言与模型的适用范围；上下文映射说明它们通过什么契约协作。核心域、支撑域和通用域取决于企业竞争力，不能照搬另一家公司的分类。

**战术设计决定边界内部怎样保护规则。**订单是有身份的实体，金额可以是值对象；订单与明细形成聚合，通过根的方法保护总额和状态。仓储负责取回和保存聚合，应用服务编排用例，领域事件记录已发生的事实。库存和支付有独立生命周期，不应因为参与一次购买就全部放入订单聚合。

![订单聚合与支付、库存上下文的边界](/architecture/ddd-model-map.svg)

图中的箭头表达上下文之间的业务协作，不代表一次跨系统原子事务。订单接受支付后产生待发送事件，消息可能重投；库存仍要检查预占状态。支付已到账但订单已关闭时，需要核对或退款，不能靠回滚订单内存对象撤销资金事实。

## 根据当前问题选择入口

| 当前问题 | 先看什么 | 会得到什么 |
| --- | --- | --- |
| 术语很多，不知道如何联系 | [概念导读](./domain-driven-design)、[基础概念](./basic-concept) | 术语边界与订单例子 |
| 想把需求放到代码里 | [模型详细说明](./model) | 语言、对象、职责和可靠提交的位置 |
| 明细被随意修改、规则难以集中 | [聚合与聚合根](./Aggregate) | 修改入口、不可变快照、并发版本控制 |
| 业务人员对流程有不同理解 | [事件风暴](./event-storming) | 按事实梳理时间线、争议和边界 |
| 支付回调和关闭任务竞争 | [实践指南](./practice) | 条件更新、Outbox、幂等与失败验证 |
| 遗留系统无法一次重写 | [领域划分与遗留改造笔记](./learn-note) | 以业务证据划边界，分段切换写入权 |
| 需要画出结构或状态 | [UML 建模](../uml/) | 类图、时序图、活动图与状态机的分工 |

旧 [DDD 与 UML 入口](./uml/uml) 保留跳转说明。阅读时先选一条用例，不必先记住所有术语。拿“支付成功后订单已关闭”这样的反例检查模型，比为每种模式先建一个空目录更有效。

## 何时值得投入

当同一条业务规则散在接口、定时任务和 SQL 中，同一个状态由多个模块修改，或“客户”“订单”等词在不同团队里含义冲突时，领域建模能帮助定位责任。规则很少的录入、展示和短期原型，清晰命名与模块分层往往已经足够。

DDD 不要求微服务、CQRS 或事件溯源。可以先在一个进程中明确模块和数据访问边界，再按独立发布、扩容和团队所有权评估部署拆分。验收看实际变更：新增部分发货时，能否指出受影响模型；重复支付时，能否解释状态和资金如何恢复；并发提交时，能否从数据库结果证明规则没有被绕过。

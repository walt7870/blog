# DDD 实践：订单支付与超时关闭

订单等待支付时，支付回调和超时关闭任务可能同时到达。如果两段代码都只做“查状态、改状态”，就会出现支付成功后订单仍被关闭、重复发券或库存被错误释放的问题。DDD 在这里的作用，是明确谁拥有订单状态、哪些规则必须在一次提交中成立、跨模块失败由谁恢复。概念关系见 [模型详细说明](./model)，本页沿这条业务线讨论实现。

## 先写清业务事实和边界

“支付成功”表示支付系统已经确认收款，“订单已支付”表示订单系统已经接受该支付事实。两者不一定在同一时刻完成。订单还在等待支付时，可以接受支付；订单已经关闭时收到迟到的成功回调，应进入核对与退款等补偿流程，不能把资金已经到账解释成支付没有发生。

| 对象或事实 | 谁负责解释 | 需要保持的规则 |
| --- | --- | --- |
| 支付流水与支付成功回调 | 支付上下文 | 验证签名、商户、金额和流水，确认可信的支付事实 |
| 订单与订单项 | 订单上下文 | 只有待支付订单可被支付或超时关闭；金额必须匹配 |
| 库存预占与释放 | 库存上下文 | 同一预占不能既确认扣减又释放 |
| 发券记录 | 营销上下文 | 同一订单、同一发券规则不能重复产生权益 |

限界上下文界定模型含义，聚合界定需要一起保护的业务规则，微服务界定部署和运行边界。它们没有一一对应关系。初期可以在一个进程内按模块实现订单、支付和库存；只有独立扩容、团队所有权或发布节奏等约束需要时，再评估服务拆分。

## 把规则放回订单，把并发留给提交边界

应用层先通过可信支付适配器得到已核验的事实，再加载订单，调用领域方法。订单聚合负责判断能否接受支付，而不是由 Controller、定时任务和消息消费者各写一套判断。

```java
PaymentDecision acceptPayment(VerifiedPayment payment) {
    if (!payment.matches(orderId, amount, currency)) {
        return PaymentDecision.REJECT;
    }
    if (status == PAID && paymentId.equals(payment.id())) {
        return PaymentDecision.ALREADY_APPLIED;
    }
    if (status != WAITING_PAYMENT) {
        return PaymentDecision.NEEDS_RECONCILIATION;
    }
    status = PAID;
    paymentId = payment.id();
    return PaymentDecision.APPLIED;
}
```

这是领域决策片段，`VerifiedPayment` 来自完成验签和交易核对的适配器，不能由请求体直接构造。`REJECT` 和 `NEEDS_RECONCILIATION` 必须形成可追踪的异常记录；同一订单收到另一笔成功支付时，也要核对是否重复收款。

领域方法仍不能独自阻止两个进程同时读到旧状态。仓储需要使用版本号或条件更新，在数据库提交时再次守住边界。例如下面这条语句只有在旧状态和版本都匹配时才成功：

```sql
UPDATE orders
SET status = 'PAID', payment_id = :payment_id, version = version + 1
WHERE id = :order_id
  AND status = 'WAITING_PAYMENT'
  AND version = :expected_version;
```

超时关闭也使用同样的待支付条件和版本检查，并核对到期时间。两次更新竞争时，只有一个能成功；影响行数为 0 的一方重新读取后再作判断，不能继续发送自己原先准备的成功事件。领域模型表达规则，持久化并发控制保证规则在多个执行者之间成立。

## 本地提交与跨上下文协作

![订单支付在本地事务中写入状态与 Outbox，提交后异步投递并幂等消费](/architecture/ddd-payment-transaction.svg)

订单状态和待发送的 `OrderPaid` 事件写入同一数据库事务。只有订单条件更新成功，才插入带唯一事件编号的 Outbox 记录；任一步失败都回滚。这样不会出现“订单提交了，但进程在发消息之前退出，事件永久丢失”的窗口。

独立投递器读取已提交的 Outbox，收到消息系统确认后标记投递结果。确认丢失或投递器中断会导致重发，因此库存和营销消费者仍须幂等处理。发券可以用 `(order_id, rule_id)` 唯一约束，库存则在预占记录的状态转换中防止重复扣减。去重标记与业务效果必须一同提交，不能先记“已消费”再执行发券。

这里实现的是可恢复的最终一致性。投递器要有重试上限、失败告警和补偿入口；积压时间过长时，用户可能已经看到订单已支付，但权益尚未到账。页面应表达真实处理中状态，运维应能用订单编号和事件编号追踪链路。消息确认与消费细节见 [MQ 投递机制](/docs/tools/mq/)。

## 两种容易失败的实现

先提交订单、再直接发消息，进程可能在两步之间退出；先发消息、再提交订单，消费者可能处理到最终回滚的事实。把消息发送放进数据库事务里也不能让两个独立系统自动具有原子性，还会延长持锁时间。Outbox 用本地事务保存发送意图，再把跨系统的不确定性转成可重试任务。

另一种错误是将订单、支付、库存和优惠全部塞进一个大聚合。它们虽然出现在同一次购买中，却有不同的生命周期和并发热点。订单聚合应拥有订单状态和订单项规则，通过支付流水编号、库存预占编号及事件契约与其他模型协作，不直接修改它们的内部表。

## 用失败场景验证模型

| 场景 | 预期结果 | 核对证据 |
| --- | --- | --- |
| 同一支付回调重复到达 | 订单保持已支付，不重复产生业务效果 | 支付流水、订单版本、Outbox 和发券记录 |
| 支付与超时关闭同时提交 | 只有一个条件更新成功，另一方重新判断 | 两个事务的影响行数和最终订单状态 |
| 订单事务写 Outbox 失败 | 订单状态同时回滚 | 数据库事务结果，不能只有消息日志 |
| 提交后、投递前进程退出 | 重启后仍能从 Outbox 找到待发送事件 | 未投递记录、重试过程及消费结果 |
| 消费完成但确认丢失 | 重投后不重复发券或扣减库存 | 去重约束与业务效果的共同提交 |
| 已关闭订单收到收款事实 | 留下待核对任务，按业务规则退款或人工处理 | 订单、支付流水及补偿任务可关联 |

规则很少的后台录入系统可以继续使用清晰的 CRUD 分层；需要付出这套建模成本的信号，是同一业务规则已经散落多处，状态竞争和异常恢复难以解释。落地效果应看规则是否有唯一入口、失败是否可恢复，而不是目录里是否出现了 `domain` 和 `aggregate`。

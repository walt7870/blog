# Linux ARM 平台与迁移

Linux ARM 指 Linux 在 Arm 架构机器上的运行环境。常见 64 位目标为 AArch64，在 Linux 工具中通常显示 `aarch64`，容器平台常写 `arm64`。32 位 Arm 的 ABI、指令状态和系统库与其不同，不能仅凭文件名含有 `arm` 认定兼容。这里讨论服务器和具备相应内存管理能力的应用处理器，不把 Cortex-M 微控制器与普通 Linux 服务器视为同一部署环境。

把 x86-64 图片处理服务迁到 arm64，工作重点不是修改几个架构字符串，而是确认编译目标、原生依赖、运行库和 CPU 特性。Arm 与 x86 的性能和能耗取决于具体芯片、内存、负载、编译优化与价格，RISC/CISC 标签不足以推导结果。

## 指令集、ABI 与 CPU 特性

AArch64 使用 A64 指令集，指令为固定 32 位；AArch32 中的 A32 与 T32 是不同指令状态，Thumb/T32 包含 16 位与 32 位编码，不能把所有 Arm 指令概括成“16 位或 32 位固定长度”。架构版本规定可用能力，具体处理器是否实现某项可选扩展还要单独检查。

二进制兼容还需要调用约定、对象格式、字节序、动态加载器和系统库匹配。`aarch64-linux-gnu` 与 `arm-linux-gnueabihf` 面向不同目标；后者不是 64 位 Arm 的通用工具链。glibc 与 musl 的加载器及依赖也不同，复制同架构文件后仍可能加载失败。

NEON/Advanced SIMD、SVE 等能力可影响多媒体与数值运算，但不能假定所有 arm64 机器都有 SVE，也不能把所有加速都归为“改成 NEON”。先确认目标支持，再选择库已有实现、运行时分派或专门构建版本，避免优化后的产物在较旧 CPU 上触发 `Illegal instruction`。

## 先确认现有产物

```sh
uname -m
file ./image-worker
readelf -h ./image-worker
readelf -l ./image-worker
readelf -d ./image-worker
```

这些命令在安装了相应工具的 Linux 环境执行。`uname -m` 查看内核报告的机器架构；`file` 和 ELF header 查看产物格式；program headers 中的 interpreter 查看所需加载器；dynamic section 列出直接声明的动态依赖。它们不证明所有间接依赖和运行时加载插件都存在，仍需核对实际加载结果与启动日志。不要对不可信文件直接使用会执行其代码的探测方式。

Java、Python 或 Node 服务也要检查 JNI、wheel、原生 addon 及推理库。纯源码部分能复用，不等于预编译依赖能复用。容器多架构清单只能选择已有的目标镜像，不能修复其中混入的 x86-64 `.so`。

## 原生构建与交叉编译

原生构建在 arm64 目标或相近构建机上运行工具链，容易发现目标依赖缺失；交叉编译在另一架构的宿主机生成目标代码，需要正确的目标编译器、sysroot、头文件和链接库。下面仅演示 C 文件的工具链入口，前提是已安装匹配目标运行环境的工具链：

```sh
aarch64-linux-gnu-gcc --sysroot=/opt/target-sysroot -O2 hello.c -o hello-arm64
readelf -h hello-arm64
```

sysroot 必须来自受支持的目标环境或 SDK，不能随意把宿主 `/usr/lib` 加到目标链接路径。构建系统若在配置阶段执行探测程序，交叉编译时还需要提供正确结果、受控模拟器或调整探测方式，不能把“程序无法在宿主运行”误判为目标不支持该功能。

QEMU 用户态模拟可以帮助执行部分目标程序，但不会验证真实外设、宿主内核差异、硬件加速和时延。最终产物需要在实际支持的最低 CPU 与系统库环境测试，再到代表性硬件做性能和稳定性验证。

## 内核、设备树与用户空间

普通服务迁移通常不需要改内核。开发板适配才需要确认启动固件、内核配置、设备描述、驱动和根文件系统之间的合同；设备树用于描述不能自动发现的硬件，部分 arm64 服务器使用 ACPI 等机制，并非所有 Arm Linux 都必须手写设备树。

驱动与设备树也不是独立于 Linux 内核之外、能让所有 SoC 自动一致的万能 HAL。GPIO、I2C、音频和加速器是否可用，需要确认控制器驱动、板级连接、固件和设备权限。AArch64 用户态通过 `svc` 指令进入系统调用处理；一般应用应调用受支持的 libc 或运行时接口，不沿用“所有 ARM 都用 SWI”的说法或手抄其他架构寄存器约定。

## 迁移验证与故障闭环

图片服务先在新旧平台运行相同输入，比较解码成功率、图像尺寸、颜色处理和输出容差，再按固定线程数、并发、内存限制与热身条件测延迟和吞吐。JPEG 等有损编码输出可能因实现不同而字节不同，验收需定义内容指标，不能只比较压缩文件哈希；无损合同要求精确一致时则应按该合同验证。

| 现象 | 优先检查 | 下一步证据 |
| --- | --- | --- |
| `Exec format error` | ELF 架构、脚本解释器、模拟执行配置 | `file`、ELF header 与实际启动命令 |
| 文件存在却报找不到 | ELF interpreter、依赖加载器路径 | `readelf -l` 与目标根文件系统 |
| 缺失版本符号 | libc、C++ 运行库与依赖版本 | 动态依赖及加载日志，回到构建基线 |
| `Illegal instruction` | CPU 特性与编译选项 | 最低支持 CPU、故障指令和库分派路径 |
| 功能正常但明显变慢 | 模拟执行、SIMD、线程与内存瓶颈 | 原生运行确认、profiling 和同条件对照 |

镜像应分别标识架构与版本，保留旧平台回退能力。若新版本改变数据格式或外部接口，切回旧镜像前还需验证数据兼容；处理器架构迁移不会自动消除这些应用层约束。

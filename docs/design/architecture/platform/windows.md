# Windows 应用与服务边界

Windows 应用开发需要同时确定 UI 框架、进程架构、运行时、系统 API、设备驱动和安装方式。现代 .NET 的部分能力可以跨平台，但 WPF、Windows Forms 和大量 Win32 API 仍面向 Windows；WinUI 3 属于 Windows App SDK 体系，也不等于把原有桌面程序直接改成 UWP。

以办公室的“收据扫描与上传”为例：桌面界面让用户选扫描仪、预览和确认；后台处理负责转换图片与上传；厂商 DLL 和驱动接入外设；升级程序安装文件并保留待处理数据。管理员权限、用户登录状态、DLL 位数或网络身份中任意一项变化，都可能让同一份程序表现不同。

## 先选应用模型

| 方案 | 常见用途 | 需要确认的边界 |
| --- | --- | --- |
| WPF / Windows Forms | 现有 .NET 桌面应用、业务工具 | Windows 运行环境、UI 线程、DPI、无障碍与升级 |
| WinUI 3 / Windows App SDK | 需要其界面与系统集成能力的桌面应用 | 支持系统范围、部署依赖与打包模式 |
| Win32 / 原生 C++ | 设备、系统 API 或既有原生工程 | API 合同、资源句柄、字符编码、ABI 与运行库 |
| 控制台 / Worker / Windows 服务 | 无交互批处理与后台任务 | 服务身份、会话隔离、停止恢复与可观测性 |
| Web 或跨平台框架 | 需要复用多端业务与部分界面 | 外设、系统集成与分发能力仍需逐平台验证 |

应用模型、UI 框架与打包方式是不同维度。桌面应用可以有不同打包形式，不能把 MSIX、UWP 和 WinUI 3 当作三个同义词。.NET Framework 与现代 .NET 的目标框架、API 和部署合同也不同，升级要先检查依赖支持，不通过简单改名字完成迁移。

## 构建与依赖核对

在 Visual Studio Installer 中选择项目所需 workload、Windows SDK 和工具集，或使用已有的受控命令行构建环境。固定项目 SDK、依赖和配置，CI 与本机使用相同的构建入口；开发机预装的软件不能成为未声明依赖。

```powershell
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes
Get-CimInstance Win32_OperatingSystem |
    Select-Object Caption, Version, OSArchitecture
```

前三条检查 .NET 环境；最后一条在 Windows 上检查系统信息。PowerShell 7 与 Windows PowerShell 5.1 的可用命令不同，不能把已从 PowerShell 7 移除的 `Get-WmiObject` 当作通用入口。SDK 是构建环境，安装了 SDK 的开发机成功也不能证明只有运行时的用户机器成功。

原生 DLL 必须与加载它的进程架构及 ABI 匹配。在 Visual Studio Developer Command Prompt 中，可用 `dumpbin /headers vendor.dll` 与 `dumpbin /dependents vendor.dll` 检查 PE 头和依赖；仍需核对间接依赖、运行时加载插件、MSVC 运行库和设备驱动。`AnyCPU` 不会让 32 位厂商 DLL 自动进入 64 位进程，Arm64 上的模拟执行也不能替代驱动与原生组件的支持确认。

## UI、进程与服务分工

扫描和大图解码不能长时间阻塞 UI 线程。异步 I/O 可以减少等待时占用线程；CPU 密集转换还需要合适的后台执行和有界并发，再把界面更新交回 UI 线程。给方法加 `async` 或在每项工作里再套一层 `Task.Run`，都不会自动得到正确取消、背压和退出行为。

普通进程内后台任务随进程退出而结束。只有需要无用户登录持续运行等明确条件时，才考虑独立 Windows 服务；服务通常位于非交互会话，不能直接展示当前用户桌面的窗口。后台扫描是否可用还取决于厂商 SDK、驱动、授权和设备会话支持，不能默认把 UI 代码搬到服务就能使用外设。

桌面进程通过受控 IPC 提交任务时，服务端验证调用者身份、路径、权限和操作范围。服务使用自己的账号和环境，用户映射的网络盘、当前目录、用户证书和凭据不一定可见。避免为了方便将所有组件都提升为管理员；权限边界应围绕具体文件、设备和操作设计。

## 任务提交、停止与恢复

把扫描结果写入应用管理的数据目录，并登记稳定任务标识、文件版本和账号范围，之后再开始上传。命名管道收到请求、Channel 入队或 UI 显示完成，不等于远端业务已提交。服务器幂等确认后才登记完成；未知结果先查询，避免重复报销或重复创建记录。

服务停止时，先关闭新任务入口，再等待执行中的任务完成或保存恢复点。关闭队列写入与立即取消所有消费者不是同一种退出策略：前者可以用于排空，后者可能留下未处理任务。应明确退出期限、超时处理和重启后如何找回任务，不能吞掉异常后永久丢失工作。

缓存与对象池也要明确边界。并发缓存清理若先判断过期、再仅按 key 删除，可能误删期间刚更新的新值；需要按版本或对象身份条件删除。缓存不应成为任务唯一持久化位置，对象归还池后也不能再被异步操作引用。

## 安装、升级与回退

.NET 的依赖框架部署要求目标机具有匹配运行时；自包含部署携带所需 .NET 运行时，但仍受操作系统、架构、原生库和驱动约束。单文件、裁剪、AOT 也各有反射、动态加载及平台限制，应按实际依赖验证。选择仍在支持周期内的版本，不能把历史 .NET 6 镜像作为持续维护项目的默认基线。

程序文件与配置、任务数据和日志分离，避免升级复制覆盖唯一业务数据。先将新版本放到独立目录，验证签名、哈希与依赖；确认进程或服务停止后再执行切换。停止超时必须终止切换并处理原因，不继续覆盖正在使用的文件。备份还需考虑数据一致性，恢复程序文件不能撤销已经发生的远端业务效果。

升级后验证服务账号、启动路径、配置迁移、首次操作和代表性外设。服务管理器显示 `Running` 只说明服务状态，文件数量正确也不是业务验收。新版本失败时，按照经过验证的数据与配置兼容范围恢复旧版本，并核对未完成任务归属。

## 容器与排错

Windows 容器需要匹配宿主、基础镜像与隔离方式的兼容条件。进程隔离与 Hyper-V 隔离不同，不能把 Linux 数据库镜像直接放进只支持 Windows 容器的运行环境，再用一份通用 bridge 配置假定它们自然互通。需要混合系统时，应明确各自宿主或虚拟化边界与网络，不把桌面容器工具的切换能力当作任意混跑合同。容器也不自动提供交互桌面和扫描仪支持。

启动失败先看事件查看器、应用日志和实际退出错误；加载 DLL 失败再用依赖工具和 Process Monitor 定位查找路径与拒绝访问。UI 卡顿用 profiling 定位主线程，服务无法访问文件则核对服务身份与 ACL。日志保留任务标识和错误原因，凭据由适用的凭据存储或密钥系统管理；密码验证与加密使用成熟库及明确参数，避免自制填充密钥、无完整性保护的加密封装。

最后在干净目标机器或受控虚拟机验证安装、普通用户运行、外设、离线重试、升级和卸载。至少覆盖支持的系统版本、CPU/进程架构与运行时组合，并保留符号定位崩溃。开发机上一次 Debug 运行成功，不足以代表最终交付包可用。

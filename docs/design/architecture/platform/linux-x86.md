# Linux x86-64 构建与运行

Linux x86-64 平台同时包含 Linux 系统接口、x86-64 指令集及用户空间运行库。发行版、glibc、C++ 运行库、最低 CPU 特性和第三方插件都会影响兼容性。`x64`、`amd64`、`x86_64` 常用于指代这一 64 位架构；32 位 x86 程序还需要对应的内核支持和用户空间库，不能仅因机器是 64 位就认为一定能运行。

例如订单导出服务在开发机编译成功，复制到服务器后报 `GLIBCXX_* not found`。这通常指向 C++ 运行库版本或加载路径，不应先去调整线程数和 TCP 缓冲。平台页先建立从产物、加载、进程到服务可用的检查链，具体 Linux 命令、容器和网络机制分别链接到对应专题。

## 构建基线决定交付范围

选择发行版时确认所需包、支持周期、硬件驱动和软件供应商支持范围。商业支持期限通常还涉及版本、订阅和扩展维护条件；CentOS Stream 与 Rocky Linux 的发布定位也不同，不能合并为一个固定兼容结论。项目应记录自己的构建基线和最低运行环境，而不是只写“支持 Linux”。

C/C++ 工具链需要同时确定编译器、标准库、链接方式和 CPU 基线。`-march=native` 会针对构建机支持的特性生成代码，不能作为跨机器分发的默认优化；启用 AVX 等扩展时，应有最低硬件要求或受验证的运行时分派。`-ffast-math` 可能改变浮点语义，不能在未核对数值合同前当作通用加速开关。

下面用一个独立小程序验证 CMake 入口。目录中放入两份文件，要求安装 CMake 3.20 或更高版本和可用的 C 编译器：

```cmake
# CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(platform_probe LANGUAGES C)
add_executable(platform_probe main.c)
set_property(TARGET platform_probe PROPERTY C_STANDARD 11)
```

```c
// main.c
#include <stdio.h>

int main(void) {
    puts("platform-probe: ok");
    return 0;
}
```

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 2
./build/platform_probe
file ./build/platform_probe
```

这是构建链验证，不是订单服务实现。Linux 上生成 ELF，其他平台通常生成自己的目标格式；在 macOS 编译成功不能证明 Linux 二进制兼容。发布前应在目标构建环境产生制品，并检查实际依赖。CMake 负责生成并驱动所选构建后端，Make、Ninja 和编译器不是同一种工具。

## 从 ELF 到进程启动

```sh
uname -m
file ./export-worker
readelf -h ./export-worker
readelf -l ./export-worker
readelf -d ./export-worker
```

在 Linux 目标机检查架构、ELF interpreter 和动态依赖，再核对运行时加载的插件。`libstdc++` 的符号版本、glibc 基线和库搜索路径都可能导致“本地能跑、服务器失败”。给目标机随意覆盖系统 libc 会影响其他程序，通常应回到合适的构建基线、匹配的运行环境或受控依赖打包方案。

容器把部分用户空间依赖放进镜像，但仍使用宿主内核并受 CPU、驱动和设备权限限制。多阶段构建可减少运行镜像中的工具，不能凭一个 `COPY` 保证所有 `.so` 都带齐；镜像标签也不是不可变版本。构建与制品身份见[镜像构建与供应链](../../../container/docker/image-build-supply-chain.md)，架构迁移见 [Linux ARM](./linux-arm.md)。

## 进程存在与服务就绪不同

订单导出进程启动后，需要读取配置、访问任务存储、初始化依赖，再开始接收任务。进程管理器报告运行不一定表示这些步骤已完成。systemd 的 `Type=simple` 与 `Type=notify` 有不同启动语义；后者还要求程序真实发送就绪通知，不能只改 unit 类型。配置位置、unit 关系和重启策略见 [systemd](../../../linux/process/systemd.md)。

服务账号、工作目录、环境变量、可写数据目录与交互式 shell 可能不同。程序不应依赖登录用户的当前目录，也不应把结果写进会被升级替换的安装目录。按任务需要授予目录、网络和设备权限，进程内主动降权还需要处理附加组、capabilities 等状态；简单调用一次 `setuid` 不构成完整隔离。

停止服务时，先停止接收新任务，再对正在执行的任务完成提交或保存可恢复状态，最后释放连接与文件。超过退出期限被终止时，重启必须能区分已提交结果与未完成任务。单纯配置 `Restart=always` 不会恢复业务，也可能让错误配置不断重启。

## 并发与性能先找证据

导出变慢时，先分别观察任务排队、数据库查询、序列化和文件写入，结合 CPU、内存、I/O、网络和 cgroup 限额判断瓶颈。主机还有空闲 CPU，不代表容器没有被 CPU 配额节流；RSS 增长也不等于一定发生泄漏，还需区分缓存、分配器和持续持有。常用观测入口见[系统监控](../../../linux/command/system-monitoring.md)。

`epoll` 负责报告 I/O 就绪，不会自动处理 TCP 消息边界和应用写缓冲。非阻塞写可能只完成一部分，读写可能遇到 `EINTR`、`EAGAIN` 或连接关闭；边缘触发还需要正确排空及重新安排处理。生产 HTTP 服务宜使用已有协议实现，不把“收到任意字节就回一次 HTTP 响应”的示例当作完整服务器。机制见 [TCP、UDP 与 Socket](../../../basic/protocol/transport-socket.md)。

优化线程数、内存池、大页、网络缓冲或调度策略之前，保存基线、负载和回退值。普通匿名 `mmap` 不等于明确申请了 HugeTLB；池化也要处理对齐、溢出、并发和生命周期。只有在相同输入与资源条件下，验证正确性、尾延迟、吞吐和资源代价，才能判断优化是否成立。

## 发布与故障核对

用版本目录保存只读制品，配置和业务数据分离。新版本完成依赖检查后再切换入口或进程，旧进程退出要有明确判据；健康检查不仅查看 PID，还要执行有代表性的导出请求。回退前核对配置、数据格式与外部副作用兼容，文件复制成功并不等于服务升级完成。

| 现象 | 先看什么 | 如何闭环 |
| --- | --- | --- |
| 运行即退出 | 加载器、库符号、配置、权限与退出码 | 修复后以实际服务账号和启动入口重试 |
| 进程在但接不了任务 | 就绪状态、监听地址、下游连接与授权 | 从调用方执行代表性请求并核对提交结果 |
| 容器里被终止 | 进程信号、cgroup 内存事件、内核与运行时日志 | 区分 OOM、人工终止与程序崩溃，再验证资源范围 |
| 高负载或响应变慢 | 排队位置、配额、热点与 I/O 等待 | 固定输入与资源做对照，不一次改多组系统参数 |
| 重启后重复导出 | 稳定任务标识、提交状态和结果登记 | 校验幂等与恢复逻辑，不以自动重启代替事务恢复 |

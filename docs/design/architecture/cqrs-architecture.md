# CQRS：命令与查询模型分离

CQRS（Command Query Responsibility Segregation）把“改变业务状态”和“读取展示数据”交给不同模型。支付订单时，写模型检查订单状态、金额和支付流水；展示订单列表时，读模型只返回列表需要的字段。这两个模型可以在一个进程、一个数据库内实现，也可以分别部署、使用不同存储。

它解决的是模型职责冲突。数据库主从复制解决存储负载分担，缓存解决热点读取，消息队列解决异步传递；这些机制都可以与 CQRS 组合，但不能替代模型划分。CQRS 也不要求采用微服务、消息队列或事件溯源。

## 从订单支付看两种模型

运营列表需要商品摘要、买家显示名、支付状态、金额和配送进度。如果每次都加载完整订单聚合，再跨服务读取用户和配送数据，列表查询会被领域对象结构和远程依赖拖慢。可以给列表单独定义 `OrderSummary`，直接查询适合展示的结构。

支付操作仍然必须经过写模型。它不能以列表里的“待支付”为依据直接扣款，因为列表可能过期；必须在写端重新校验身份、租户、订单状态和支付事实，并在持久化时保护并发条件。

| 操作 | 模型承担的责任 | 返回内容 |
| --- | --- | --- |
| `PayOrder` 命令 | 验证是否可支付，登记付款，保护状态约束 | 成功/失败、订单 ID、提交版本或任务 ID |
| `GetOrderSummary` 查询 | 按授权范围读取列表数据，分页与排序 | 展示 DTO，不暴露可修改的聚合内部对象 |
| `OrderPaid` 事件 | 记录已完成的业务事实，供投影或其他流程消费 | 事件 ID、订单 ID、聚合版本及必要事实 |

命令可以返回新建对象 ID、执行结果或版本；“命令必须返回空”不是 CQRS 的硬性规则。查询不应产生业务状态变更，但记录访问日志并不使它变成命令。重复查询仍可能读到新数据，**幂等不意味着数据永远不变**。

## 先在同一个数据库内拆职责

多数项目可以先保留一套数据库。写端通过领域方法和事务修改 `orders`；读端使用独立 SQL/DTO，不必加载整棵对象图。两端共享数据表也可以是 CQRS，关键是业务规则与查询结构分别演进。

```text
orders/PayOrderHandler       校验身份 → 加载订单 → pay() → 条件更新
orders/OrderQueryService     校验身份 → 查询授权范围 → 返回 OrderSummary
```

如果读端从主库读取已经提交的数据，就不必引入异步投影延迟。是否能立即看见新状态，还取决于事务隔离级别、读取副本、缓存和请求时序。CQRS 本身既不保证强一致，也不强制最终一致。

这一阶段先测慢查询、索引命中率、数据库负载和对象加载开销。如果独立 SQL 已满足需求，就停在这里；“完整 CQRS”并不意味着必须继续增加事件存储和搜索集群。

## 需要独立读存储时再增加投影

订单量增长后，列表检索可能需要搜索索引，经营看板可能需要按天预聚合。下面是**异步投影的一种实现**：写端在同一个本地事务内保存订单状态和 Outbox 事件，转发器提交后投递，投影器更新读存储。

把“保存订单”和“直接发 MQ”写成两行代码，会留下数据库成功、消息失败的窗口。Outbox 使业务状态和待发事件一起提交；转发器可能重复投递，因此消费者仍需去重。数据库 CDC 也是可选方案，但要明确业务事件如何从表变更得到，不能把所有字段变更都当领域事实。

以下是关系库写端的机制片段，省略鉴权、支付事实核验和参数绑定，不能直接作为支付接口：

```sql
BEGIN;
UPDATE orders
SET status = 'PAID', version = version + 1
WHERE id = :order_id AND tenant_id = :tenant_id
  AND status = 'PENDING' AND version = :expected_version;
-- 应用检查受影响行数必须为 1，否则回滚并处理冲突。
INSERT INTO outbox(event_id, aggregate_id, aggregate_version, event_type, payload)
VALUES (:event_id, :order_id, :next_version, 'OrderPaid', :payload);
COMMIT;
```

投影器以事件 ID 去重，并明确同一订单的顺序策略：按订单分区、版本检查或缺口补取。处理订单版本 8 后再收到版本 7，不能无条件覆盖；版本 9 先到时，也不能简单跳过版本 8 的累加事件。携带完整状态的覆盖投影与“金额加一笔”的增量投影，需要不同的重放规则。

投影的去重记录和视图更新应能原子提交；跨存储做不到时，要用幂等写入、可重试检查点和对账修复弥补。消息中间件声称的交付语义不能自动保证外部数据库副作用只发生一次。

## 支付成功后，列表为什么还是待支付

写事务提交成功，并不意味着异步读模型已经追上。支付响应应带回确认结果，页面先展示“支付已受理/已完成”的确定状态，再按约定刷新列表；需要严格读己之写时，可返回提交版本，让查询等待投影达到该版本，超时则明确提示处理中或回读权威状态。

不要在命令返回前随意等待所有读视图更新，否则报表投影故障会反过来拖住支付。决定是否等待、等待哪个视图、最长多久，应以业务用例为单位。

查询模型不是越权例外。搜索索引、报表和缓存里同样要保留租户及授权所需字段，服务端按当前身份约束结果。删除敏感数据时，还要追踪它在索引、缓存、旧投影与备份中的生命周期。

## 投影失败与重建

| 现象 | 核对顺序 | 恢复与验收 |
| --- | --- | --- |
| 订单已支付，列表长期未更新 | 写端版本 → Outbox 待发 → MQ 积压 → 投影检查点 | 修复后补投；对比同一订单写端与读端版本 |
| 消费重试后统计翻倍 | 事件 ID、去重提交边界、增量计算 | 修复幂等策略，重放重复事件，确认金额不重复累计 |
| 状态从已支付退回待支付 | 分区键、事件版本、乱序处理 | 保护旧版本覆盖；测试重复、乱序和版本缺口 |
| 新索引缺少历史订单 | 快照边界、回放起点、增量衔接 | 在新索引重建并追平，核对数量和业务汇总后切换 |

“读模型可重建”要有数据来源。若写库保存完整当前状态，可用一致性快照加增量日志重建；若需要历史变化，必须保留足够事件或审计事实。只保留当前订单和短期 MQ 消息，不能重建去年每天的状态。

重建应写入新版本索引，追平变更后再切换查询别名，保留旧版本供回退。监控不仅看消息有没有消费，还要看最旧未处理事件年龄、投影版本差、重试/死信数量及关键业务对账差异。

## 与事件溯源的边界

普通 CQRS 可以把数据库里的当前订单作为事实来源；事件只是更新投影的通知。事件溯源则把完整事件流作为状态依据，当前聚合通过重放得到，快照用于加速加载。

采用事件溯源后，还要处理事件模式演进、历史数据修正、快照失效、重放的外部副作用以及敏感数据留存。不能因为需要一个订单列表索引，就顺带引入整套事件溯源。

## 选型与验收

当复杂业务规则与多种展示视图彼此牵制，或读写负载需要独立优化时，CQRS 有价值。普通 CRUD、数据量小且结构一致的后台通常先用清晰服务层和 SQL。读多写少只是负载特征，不能单凭这个比例决定架构。

上线前至少验证：并发命令不会破坏不变量；重复和乱序事件不会污染视图；投递中断后可补齐；页面能解释同步延迟；读模型执行相同授权；新视图可重建并回切。读写职责分开后，系统才获得独立演进空间，而同步与恢复成本也必须有人维护。

# TOGAF 企业架构

TOGAF 是 The Open Group 的企业架构框架，提供架构开发方法、内容模型与治理方法。它适合处理跨团队、跨系统的变化：企业想获得什么能力，核心事实由谁负责，现有系统如何共存和退出，以及怎样证明投入产生了结果。

例如一家商店同时接入门店收银和网上商城，两边各自售出“最后一件商品”。重新开发订单页面无法解决这个问题。团队还要决定谁承诺库存、断网门店能卖多少、旧收银系统如何接入、退款与对账由谁处理。TOGAF 帮助组织这些决策；数据库事务、接口和部署仍需具体工程设计。

## 用同一件事理解四个架构域

四个域描述同一次变化，需要反复校正，不是依次交付四份互不关联的文档。

| 架构域 | 商店需要回答的问题 | 深入阅读 |
| --- | --- | --- |
| 业务 | 能否让客户跨渠道购买、自提和退款，谁对结果负责 | [业务能力与价值流](./business-architecture.md) |
| 数据 | 实物、预占和可售库存分别是什么，谁能修改，多久可信 | [事实责任与生命周期](./data-architecture.md) |
| 应用 | 商城、POS、库存和订单系统分别负责什么，如何协作 | [应用边界与契约](./application-architecture.md) |
| 技术 | 并发抢购、断网和重复付款通知下，如何保持业务约束 | [质量属性与运行机制](./technology-architecture.md) |

“库存平台拥有预占裁决权”不等于所有数据只能存在一个库。门店、客服和分析系统可以有副本，但副本不能绕过权威方承诺同一份库存。按渠道逐步迁移时，还要隔离各自可承诺的库存额度；两套系统独立看到同一件实物仍会超卖。

## 从现状到目标，中间状态也要能运行

Baseline 描述实际状态，Target 描述希望成立的条件，Gap 表达两者之间的具体变化。比如现状是商城与 POS 各自预占；目标是指定库存池只有一个裁决入口；差距包括商品映射、预占接口、权限收回和旧任务停用，不能只写“建设库存中心”。

迁移可以先做只读对账，再接管一个隔离库存池，最后扩大范围。每一步明确新旧写入权、在途订单、数据追平、暂停条件与回退边界。工作包将这些业务、数据、应用和技术变化组合成可验证结果，服务上线只是其中一部分。

## ADM 怎样组织这些工作

ADM（Architecture Development Method）将架构工作组织为可迭代的方法。Preliminary 建立角色、原则与决策机制；A 明确愿景和范围；B/C/D 分析业务、数据与应用、技术；E/F 形成解决方案、过渡架构和迁移计划；G 检查实施一致性；H 依据变化与运行证据调整架构。需求管理贯穿各阶段。

例如影子运行发现商品映射错误，就应返回数据模型和业务规则处理，再决定能否接管。阶段名称不要求项目一次走完，也不保证每家企业采用相同系统、委员会或文档模板。

## 什么时候需要这套方法

一个团队给稳定模块增加普通字段，通常只需局部设计、测试和发布检查。多个渠道共享库存、并购后合并客户身份、旧账务系统迁移等变化，会同时改变责任、数据和运行边界，适合用企业架构方法梳理依赖与证据。工件规模随风险裁剪，保留足以支持决策的内容。

完成标志也应具体：能从“降低缺货取消”追到库存承诺能力、预占事实、应用责任、并发要求、迁移工作包以及超卖和对账指标；旧写入口确实退出，业务流程能运行，才说明变化已经发生。

# UML 类图关系

类图表达类型、属性、行为和静态关系，连线不是请求日志。`OrderService` 调用了 `Order`，可以画依赖；订单包含订单项，可以画组合；订单记住客户编号，则表达业务关联。画图前先说明当前讨论的是领域概念还是代码结构，避免把数据库外键、对象引用和所有权混成同一种箭头。

## 依赖与关联

依赖表示一个模型元素的定义或实现需要另一个元素，使用虚线加开放箭头，箭头指向被依赖者。它不限于“临时调用”：参数、局部变量、静态调用、模板参数等都可能形成依赖。一个类长期持有另一类型的字段，也存在类型依赖，但如果图要表达实例之间的稳定联系，应考虑画关联，而不是重复堆线。

关联用实线描述实例间的联系，可以标注角色、多重性和可导航方向。`Order` 对应一个客户、客户可以有零到多个订单，是一个具体模型选择；游客下单、匿名化或历史数据保留会改变这些约束，不能套用固定多重性。没有箭头不等于一定双向可导航，图中省略导航方向时应保持这一解释。

```java
final class Order {
    private CustomerId customerId; // 保存关联标识，不要求加载 Customer
    private List<OrderLine> lines;
}
```

这段仅说明字段关系，省略构造、不变量和行为。跨聚合保存标识可以缩小加载与事务范围，但一条数据库外键不会自动赋予对象组合语义。应用服务通过构造器持有仓储接口时，代码图可以画可导航关联；当前图关注源码依赖，因此用虚线说明接口方向。

## 整体与部分

共享聚合用空心菱形，菱形位于整体一端。UML 对共享聚合的精确语义没有给出适用于所有领域的统一约束；团队必须说明“共享”“移除”和生命周期分别意味着什么。部门和员工若只是任职关系，普通关联通常更直接，不能仅因名字中有“包含”就加菱形。

组合用实心菱形，菱形同样位于整体一端。它强调一个部分实例在同一时刻最多属于一个组合整体，以及整体销毁对仍属于它的部分的生命周期影响。部分可以先从整体脱离，具体创建顺序、持久化删除策略和资源释放方式仍由模型与实现约定。

订单项在本例中只属于一个订单，外部通过订单行为修改明细，因此采用组合。取消订单只是业务状态变化，不代表物理删除订单或级联删除明细；历史订单可能需要长期保留。Java 的垃圾回收、ORM 的 `cascade` 和数据库的 `ON DELETE` 都不能单独证明业务组合关系成立。DDD 聚合还要求一致性边界与不变量，不能只靠一枚实心菱形定义，详见[聚合边界](../DDD/Aggregate.md)。

## 泛化与实现

泛化使用实线与空心三角，三角指向更一般的类型，表示特殊类型是一般类型的一种。除了语法上的 `extends`，还要检查调用者能否按父类型的约定使用子类型。为了复用几行代码创建继承层次，可能导致子类拒绝父类允许的操作；这种情况下应重新检查分类，或改用组合与委托。

实现使用虚线与空心三角，三角指向规范或接口。图中 `SqlOrderRepository` 实现 `OrderRepository`，应用服务依赖接口，运行时可以调用 SQL 实现。这解释源码依赖倒置，不表示 SQL 无事务、无连接池或无故障。接口应由需要该能力的一侧定义；`OrderDao` 等名字本身并不错误，是否属于领域仓储取决于它承诺的操作和边界。

## 从代码核对关系

阅读 `cancel(orderId)` 时，先看参数、字段和调用确认类型依赖，再看订单如何获得客户标识、如何创建和修改明细，最后看仓储接口由谁实现。图上 `1` 和 `1..*` 必须对应构造与提交约束；允许空草稿订单时，明细多重性就不能仍写 `1..*`。

复核组合时可尝试把同一个 `OrderLine` 交给两个订单，复核封装时可尝试从外部直接修改明细集合，复核依赖倒置时可替换内存仓储执行同一用例。这些检查分别验证对象归属、修改入口和契约替换能力，不把“图里有接口”当作可测试性的证明。图中省略的映射、异常和并发控制需由对应实现页补足。

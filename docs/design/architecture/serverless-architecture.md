# 无服务器架构（Serverless Architecture）

Serverless 把更多服务器配置、调度和扩缩容责任交给平台，开发者仍然负责业务正确性、权限、数据和成本。函数即服务（FaaS）是常见形式，托管容器、工作流及部分后端服务也可以采用 Serverless 运行方式，不能把它等同于“一个接口一个函数”。

例如用户上传头像后，平台触发处理函数生成缩略图；原图和结果放在对象存储，处理状态持久化到任务表。函数实例可以复用，也可能随时被替换。系统必须在重复事件、并发处理和超时后仍能找到同一份任务及结果。

## 上传缩略图的完整链路

应用先授权上传，限制用户、对象前缀、文件大小和可接受类型。上传成功后，对象事件进入工作队列，函数根据受信任的存储事件读取指定版本的原图，校验实际文件格式与解码尺寸，生成固定变换规则的缩略图，再登记结果。

处理标识可以由对象身份、不可变版本与变换版本共同组成，例如 `头像对象 + 对象版本 + thumb-v3`。相同事件重投保持同一标识；用户覆盖上传或变换算法升级则产生新的任务。没有对象版本能力时，应使用应用产生的不可变对象键，不能仅用可被覆盖的文件名判重。

输出放到独立 Bucket 或专门结果前缀，并配置输入事件过滤，避免“生成缩略图又触发缩略图函数”的递归。对象存储事件可能重复或乱序；不能直接相信来自公共 HTTP 请求的对象路径和租户标识。

任务完成包含两个可独立失败的操作：结果对象写入与状态登记。应使用稳定结果键、校验和、条件更新及核对任务处理“文件存在但记录失败”，并防止旧任务覆盖新头像。临时认领还需租约和崩溃恢复，不能一写 `PROCESSING` 就永久阻止重试。

## 状态不应依赖某个实例

“无状态”表示不能把权威业务状态只放在某个函数实例内，不表示函数没有内存、缓存或临时磁盘。SDK 客户端、连接和只读模型可以在实例内复用来降低开销，但实例可能销毁，连接可能失效，缓存也可能过期。

订单进度、去重结果、工作流状态和用户文件应放到合适的持久化服务。跨调用保留的内存和临时目录不得混入其他用户资料；复用连接时设置连接数量、有效性检查和超时，避免大量实例同时挤满数据库连接。

复杂长流程可以交给持久化工作流协调短步骤，或使用更适合的托管容器和批处理。工作流服务能持久化执行进度，但外部扣款、发信等副作用仍需幂等和核对，不能因编排器会重试就认为恰好执行一次。

## 触发方式决定重试合同

以 AWS Lambda 为例，下列调用方式的行为不同；其他平台也应按具体产品和触发器核对，不能把某种默认配置套到所有函数。

| 方式 | 谁负责重试 | 失败时需要配置什么 |
| --- | --- | --- |
| 同步直接调用、HTTP 代理 | 调用者或上游服务决定，函数错误不会统一自动重试 | 超时预算、幂等键、错误响应与查询入口 |
| 平台异步调用 | 平台异步队列按错误类别和配置重试 | 最大事件年龄、重试条件、失败目的地或死信 |
| 队列事件源映射 | 事件源映射配合队列可见性和重驱策略 | 可见性超时、批大小、部分批失败与死信策略 |
| 流事件源映射 | 按流、分片和批处理配置重试 | 毒记录隔离、重试/年龄限制、积压年龄与恢复 |

队列投递成功不代表函数执行完成；函数执行返回成功也不能代替验证业务结果。如果一个批次有少数记录失败，要按平台支持的部分批响应协议报告，不能无条件确认整个批次，也不应让已成功的外部副作用在整批重试时重复发生。

超时可能发生在结果已经写入之后。重试前先根据稳定任务标识核对结果；超时不能解释为“什么都没有执行”。可靠业务处理的通用机制见[事件驱动架构](./event-driven-architecture.md)。

## 容量、冷启动与成本

自动扩容受账户、函数、事件源和下游配额限制。平均在途并发可按“每秒到达量 × 平均处理秒数”初估：每秒 20 张图片、平均处理 0.5 秒，大约需要 10 个在途执行。这只是平均容量估算，还要留出突发、长尾、重试和下游限额的余量。

在 AWS Lambda 中，**预留并发**限制函数最高并发并保留账户内的相应并发额度，不会预先启动环境；**预置并发**维护预初始化环境以降低冷启动影响，并产生额外费用。两者解决的问题不同。定时发送“保温请求”也不能保证每个新实例都已预热。

函数变慢会增加在途并发，进而增加数据库和存储压力。限制最大并发、批大小和下游连接数，把可接受的积压保留在持久化队列；同时监控最老任务年龄，避免只控制费用却让任务永远完不成。

| 成本项 | 头像例子中的来源 |
| --- | --- |
| 执行与请求 | 分配内存、运行时长、调用与重试数量 |
| 常驻或保留资源 | 预置并发、最低实例、托管工作流或数据库能力 |
| 数据与网络 | 原图/缩略图存储、请求次数、出口与跨区传输 |
| 可观测与运维 | 日志量、保留时间、追踪、告警与失败处理 |

没有调用不等于整套系统零费用；持续高负载也不保证函数比常驻服务便宜。选型要用真实图片大小、解码峰值内存、处理长尾和完整账单估算，而不是只比较单次调用单价。

## 配置入口与验证

配置通常涉及触发器、执行超时、内存/CPU、临时空间、并发、网络、执行角色以及失败目的地。下面两条为 AWS CLI 只读核对命令，替换示例名称和映射编号后使用；输出中的环境配置可能含敏感值，不应直接公开：

```bash
aws lambda get-function-configuration --function-name thumbnail-demo \
  --query '{Runtime:Runtime,Timeout:Timeout,Memory:MemorySize,Role:Role,Vpc:VpcConfig}'
aws lambda get-event-source-mapping --uuid EXAMPLE-MAPPING-ID \
  --query '{State:State,BatchSize:BatchSize,Responses:FunctionResponseTypes,Source:EventSourceArn}'
```

角色只允许读取被授权的输入前缀和写指定输出范围，密钥通过合适的密钥服务提供并限制读取权限；环境变量本身不等于安全的密钥治理。网络隔离还要验证出口、存储端点与数据库访问，不能仅勾选 VPC 就认为完成安全配置。

验收至少包含重复对象事件、并发重投、非法图片、超大解码尺寸、结果写入后进程退出、单条毒记录、账户限流及下游数据库不可用。检查原图版本、任务标识、结果对象、最终状态、死信和账单指标能否关联。纯本地处理测试无法证明云端 IAM、触发器和重试策略正确。

## 适用边界

事件触发清晰、任务可分段、负载波动大并能接受平台运行约束时，函数托管往往方便。交互请求也可采用，但需实际测量冷启动与端到端延迟。长连接、长任务、固定硬件或持续高吞吐场景，应比较产品限制、托管容器和批处理能力，不必一律判定 Serverless 不适用。

微服务描述业务与交付边界，Serverless 描述更多运行责任由平台托管，两者可以组合；容器也可以运行在 Serverless 平台上。选型从处理合同、状态、失败恢复、延迟和成本出发，避免把所有业务都拆成细小函数形成长串同步调用。
